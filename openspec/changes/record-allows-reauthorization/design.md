- F1 — Verified fact: `contractAnchorPlan` (`src/core/gates.js:106-120`) scans the selected task's line range for `/^(\s*)-\s*Contract:\s*pending(\r?)$/` and returns `null` for anything else, so an already-recorded anchor and a wholly absent anchor are indistinguishable to the caller. Basis: the function body.
- F2 — Verified fact: `taskStart` (`src/core/gates.js:132-145`) turns that `null` into a `record-refused` problem whose message names both causes at once — "the anchor is already recorded or missing" — and the surrounding comment states the intent: "an overwrite would destroy the recorded start evidence drift detection depends on". Basis: the function body and its comment.
- F3 — Verified fact: the anchor read path is `recordedFingerprint` (`src/core/context.js:58-64`), matching `/^\s*-\s*Contract:\s*.*?keel-task-capsule\/v1.*?sha-?256[\s:`]*([a-f0-9]{64})/im`. It reads whatever the line currently holds; it has no memory of a previous value. Nothing in the repository stores a prior fingerprint, so "the recorded start evidence" F2 protects is exactly one line of `tasks.md` — the same line the manual workaround rewrites by hand. Basis: the function body and a repository-wide search for any other fingerprint store.
- F4 — Verified fact: `keel guard status` emits `fingerprint-drift` with "reauthorize through `keel gate task-start` and `keel guard start`" (`src/core/guard.js:235-240`), and `authority-drift` says the same (`src/core/guard.js:208-213`, `:245-250`). Following that instruction with `--record` hits F2's refusal. The tool's own remediation is unreachable as written. Basis: both call sites.
- F5 — Verified fact: the refusal clears no execution evidence. The workaround it forces is a single-line edit of the `- Contract:` line; the task's `M<n>` Evidence lines are untouched, and `task-complete` then accepts evidence produced under the previous contract. Basis: the shape of the workaround, performed five times in the 2026-07-27 session recorded in issue #13.
- F6 — Verified fact: `tasks.md` holds one `- Contract:` line per task, all identical in form and differing only in a 64-character hex value. Basis: the archived `2026-07-27-diagnostics-must-not-mislead/tasks.md`, six tasks, six such lines.

## Decisions

- D1 — `--record` replaces the selected task's `- Contract:` anchor whatever its current value, and refuses only when the selected task has no such line. Recording the current fingerprint is an idempotent statement of fact, not a once-only claim; the state that must not be silently destroyed (F2's stated intent) is not stored anywhere the gate could destroy (F3). Refusal is kept for the missing-anchor case, which is a malformed capsule rather than a normal reauthorization. Rejected: adding a separate `--rerecord` flag, because choosing between the two flags requires the caller to first read the anchor's current state — the same lookup the refusal already forces, moved one step earlier. Basis: F1, F2, F3, F4.

- D2 — Replacing a *different* fingerprint is reported, not refused. `result.record.status` distinguishes `recorded` (previous value `pending`), `rerecorded` (any other previous value), and `unchanged` (the anchor already carries this exact fingerprint); `result.record.previous` carries the replaced text; and a `rerecorded` outcome whose previous value parsed as a different fingerprint pushes a warning naming it and stating that execution evidence produced under the previous contract is stale. This is the risk the refusal gestured at without enforcing (F5), stated at the moment it arises. Rejected: making a differing re-record `needs-review`, which would re-block the path this change exists to unblock, and which the deterministic gate cannot judge — whether prior evidence is still valid is a semantic question the current agent answers in Review.

- D3 — The `unchanged` outcome writes nothing. Re-running `task-start --record` to re-establish a cleared guard is the common case where the contract has not moved, and rewriting a byte-identical line would touch `tasks.md` for no reason. This keeps the write-bounded property in `keel-core-gates` strictly stronger than before, not weaker. Basis: D1, plus the guard-clear/re-start loop in the archive evidence.

## Risks

- A1 — Risk: broadening the matcher from the literal `pending` to any `- Contract:` line widens what the scan can hit, since the scan covers the whole task line range rather than the Evidence block alone. Mitigation: the pattern still requires a line whose entire content is a `- Contract:` list entry, the scan takes the first match as the current code already does for `pending`, and the replacement writes the same anchor form the read path in F3 consumes. A task carrying two `- Contract:` lines is already ambiguous under the current code.
- A2 — Risk: removing the refusal removes a signal that a fingerprint had already been recorded, which an author might have been reading as "this task is already under way". Mitigation: `result.record.status` reports `rerecorded` or `unchanged` explicitly, and the human-readable line reports it too, so the signal is stated rather than inferred from a failure.
- A3 — Assumption: no valid task changes its compiled fingerprint, since this change touches only the anchor write path and never capsule compilation. Resolve by: the existing `core-gates` scenario already asserts that recording does not drift the recompiled fingerprint; keep that assertion and run the full suite.
