## Context

`updateClaudePlugin` in `bin/keel.js` refreshes the Claude marketplace and then runs `claude plugin update keel@keel-marketplace`. The marketplace entry is read from Git and names the npm package at exactly the release version, so it advances the moment the release commit lands. Claude Code then resolves that exact version from the npm registry the machine reaches. `updateGlobalCli` runs `npm pack @christang/keel`, which resolves `latest` through the same registry.

The publish job in `.github/workflows/publish.yml` runs `npm publish`, then tags and creates the release. Nothing waits for the registry's read side.

## Facts

- F1 — #421 body: on 5.171.0, 5.172.0 and 5.173.0, the Claude line was `failed - \`claude plugin update keel@keel-marketplace\` exited 1: ✘ Failed to update plugin "keel@keel-marketplace": Could not resolve @christang/keel@5.17y.0 from the npm registry: E404 No match found for version 5.17y.0`, while `npm view @christang/keel dist-tags --prefer-online` on the same machine still showed the old version.
- F2 — #421 comment, 2026-10-20: for 5.177.0, `npm view @christang/keel version` returned the new version about 3 minutes after the release; a rerun updated all three components. 5.175.0 behaved the same.
- F3 — #153 (comment in `publish.yml`): the registry's read side has reported published versions as missing for several minutes after a burst of publishes. The write side ("cannot publish over the previously published versions") is the trustworthy answer for "was it published"; the read side is the answer for "can a user install it", which is what this change waits for.
- F4 — `hostFailure` keeps only the last stderr line. The E404 text is on that line in F1, but the match below reads all of stdout and stderr so a trailing line cannot hide it.

## Decisions

- D1 — Registry lag is recognized, not assumed. After `claude plugin update` exits nonzero, `updateClaudePlugin` searches its stdout and stderr for `E404 No match found for version <X>`. Only then does it run `npm view @christang/keel version --prefer-online`, with the host-query limit (30 s, `KEEL_UPDATE_QUERY_TIMEOUT_MS`), through the npm executable the CLI step uses. When that answers a version Y and X is newer than Y by `compareVersions`, the line reads `pending - the npm registry here does not serve X yet (its latest is Y); rerun keel --update in a few minutes`, and the component does not count as failed. In every other case — no E404 text, `npm view` failing or answering nothing, or Y not older than X — the line is the `failed` line it is today.
- D2 — `pending` does not fail the command. The issue's acceptance asks that this case is not reported as a failure, and the spec's exit rule ("nonzero only when a step that ran failed") is kept: nothing broke, and the owner's next run completes it. The line carries the rerun instruction, so a reader of an unattended run still sees the work is not done.
- D3 — The CLI line names the registry's latest when the source is the default registry package: `current Y - the npm registry's latest here is Y; applies to the next command that runs keel`, and the same clause after an `updated` change. With an explicit `--source` or `KEEL_UPDATE_SOURCE`, the packed version is not the registry's latest, so the clause is left out.
- D4 — `scripts/await_registry.js <package> <version>` polls `npm view <package>@<version> version --prefer-online` until it prints exactly `<version>`, every 15 s for at most 15 minutes by default (`--interval-seconds`, `--timeout-seconds`; npm from `KEEL_AWAIT_NPM`, default `npm`). A nonzero `npm view` — npm's E404 for a version it cannot see — counts as "not yet". It prints how long the version took to appear and exits 0, or names the version and the limit and exits 1.
- D5 — The publish job runs it as its own step between `Publish` and `Tag and release the landed version`, under the same `skip` condition as `Publish`. A timeout fails the job before the tag, which the workflow already treats as "not released": a re-run publishes nothing new (the write side says it is there), waits again, and tags. A hand-made release (the `release` event) waits too; there the release already exists and the wait only makes the job's result honest.
- D6 — It is a script rather than inline shell so its behavior can be exercised locally with a fake npm. Its placement in the workflow is asserted by reading `publish.yml`, as the other publish checks do, because the workflow runs only on GitHub.
