## Context

`runProjectInit` in `bin/keel.js` runs `openspec init --tools <target> --force`, then the Python installer, then `openspec update --force`, then refreshes the Keel overlays. `keel openspec <args>` passes through to the pinned OpenSpec and, after `update`, restores the overlays. Neither sets any environment for OpenSpec, so OpenSpec reads the user's global configuration.

The overlay is projected onto each managed action's skill and, on Claude and OpenCode, its command file (`openspecOverlaySurfacesForTarget`); a file that does not exist is skipped. Doctor's "OpenSpec commands" line counts five command files on Claude and OpenCode and reports `missing` when any is absent, and the overlay line counts eight surfaces on Claude.

## Facts

- F1 — OpenSpec 1.14.0 reads `delivery` only from its global configuration, `$XDG_CONFIG_HOME/openspec/config.json` when `XDG_CONFIG_HOME` is set on any platform, otherwise `~/.config/openspec/config.json` (macOS, Linux) or `%APPDATA%/openspec/config.json` (Windows) (`dist/core/global-config.js`). `project-config.js` has no `delivery`; `init` takes only `--tools`, `--force`, `--profile`. Accepted values are `both`, `skills`, `commands`; a missing or invalid file falls back to the defaults, `both` among them.
- F2 — With `delivery: skills`, `init` and `update` generate skills for every tool, remove every workflow's command files for adapter-backed tools (Claude and OpenCode are; Codex is skills-invocable and never had command files), and rewrite `/opsx:<id>` in the skill bodies to `/openspec-<skill>` (`dist/core/command-surface.js`, `init.js`, `update.js`, `dist/utils/command-references.js`). Switching back regenerates them, so the setting reconciles in both directions.
- F3 — The owner's machine has `delivery: both`, `profile: custom`, and five workflows explicitly; `keel openspec config list` prints `delivery: both (explicit)`.
- F4 — `#406`: in kaiwu-ip the duplicate pair costs about 570 tokens of listing per session, and a protocol refresh touches eight overlay files on Claude instead of four.
- F5 — The archive overlay text names `/opsx:sync` (`bin/keel.js`), and README, three Keel skills (`keel-review-checklist`, `keel-debug-failure`, `keel-align-expectations`), the Keel schema, and this repository's `AGENTS.md` name `/opsx:*` commands. Under skills delivery those commands do not exist.
- F6 — This repository tracks `.claude/commands/opsx/{propose,explore,apply,sync,archive}.md` and `.claude/skills/openspec-*`, generated by OpenSpec 1.6.0 under `delivery: both`.

## Decisions

- D1 — Owner's decision (#406, 2026-10-21): Keel guarantees skills only and does not write the user's global configuration.
- D2 — `openspecEnv()` builds the environment for an OpenSpec run Keel starts: it reads the global configuration from the path F1 names (an unreadable or non-object file reads as `{}`), sets `delivery` to `skills`, writes it as `openspec/config.json` under a fresh temporary directory, and returns the process environment with `XDG_CONFIG_HOME` pointing there. Every other field — profile, workflows, telemetry — is kept, so the user's workflow selection still applies. The directory is removed after the run. `runProjectInit` uses it for `init` and `update`; the `keel openspec` passthrough uses it when the first argument is `init` or `update`, and runs every other subcommand unchanged, so `keel openspec config list` still reports the user's own configuration.
- D3 — The setting is per run, not per tool (F2), so a repository with OpenCode installed loses OpenCode's command files too. That follows from D1 rather than extending it: OpenSpec offers no way to keep one tool's commands while dropping another's, and OpenCode reads the skills under `.opencode/skills`.
- D4 — Doctor, Claude and OpenCode: the "OpenSpec commands" line reads `ok - none; Keel generates OpenSpec's workflows as skills only (#406)` when no command file exists, and `duplicate - <n> command files under <location> duplicate the skills; run keel --init --target <target> to remove them` when any remain. Codex keeps its lines unchanged. The overlay surfaces for Claude and OpenCode are the skills plus the command files that exist, so a repository that still holds them keeps them overlaid until the next `keel --init` removes them, and a skills-only repository reads `4/4` rather than `4/8`.
- D5 — Guidance names the workflow by its skill, for example "the `openspec-sync-specs` skill", not by a target's invocation spelling, because Claude, Codex, and OpenCode spell skill invocation differently and the overlay text is shared.
- D6 — This repository: remove `.claude/commands/opsx/` and rewrite `/opsx:<id>` in `.claude/skills/openspec-*/SKILL.md` to `/openspec-<skill>`, using OpenSpec's own mapping (F2), which is what regenerating them would produce. The skills are not regenerated under 1.14 here: that would rewrite their whole bodies and move `.codex/skills` to `.agents/skills`, a separate migration. `.codex/skills` keeps its text, because Codex's skills already use skill references in 1.14 and this repository's legacy Codex layout is not in scope.
