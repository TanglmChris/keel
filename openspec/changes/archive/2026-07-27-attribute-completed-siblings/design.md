## Verified facts

- F1 — Verified fact: `scopeEvidence` (`src/core/gates.js:319-373`) builds `changed` from `git diff --name-only <base>` plus the dirty paths, then attributes everything not matched by the selected task's Touch, with exactly two exemptions — the literal `keel/guard.json` and the change's own `openspec/changes/<change>/` prefix. Nothing consults any other task. Basis: the function body.
- F2 — Verified fact: `taskComplete` (`src/core/gates.js:472-486`) already holds `selection.tasks`, the full parsed task list for the change, and passes only the selected task into `scopeEvidence`. The sibling information needed is therefore already in memory; no new read, no new state. Basis: `loadSelection` and the call site.
- F3 — Verified fact: `touchEntries(task)` called without a compiled contract (`:292-298`) parses the raw `Touch` field and drops entries failing `isConcrete`, and `isConcrete` returns false for `none`. A `Touch: none` sibling — `diagnose-only` or `repo-action` — therefore claims no paths. Basis: both function bodies.
- F4 — Verified fact, reproduced in this repository on 2026-07-27: completing task 1.2 of `retire-follow-up-backlog` with `--base HEAD` reported `outside-touch: AGENTS.md` solely because task 1.1's edit to that file was uncommitted, and 1.1 had already passed its own `task-complete`. Basis: issue #13's transcript.
- F5 — Verified fact: `keel-core-gates / Dirty-worktree attribution is conservative` already states the principle this extends — Keel "MUST NOT attribute dirty paths to a selected task unless the caller supplies a trustworthy comparison base", and the requirement already carries two exemption scenarios plus a rename-attribution scenario. Basis: the live spec.

## Decisions

- D1 — A changed path outside the selected task's Touch is not attributed to it when a **completed** task in the same change declares that path in its Touch. The answer is derived from `tasks.md`, which the gate has already parsed (F2). Rejected: issue #13's first option, recording the base at `task-start` and reusing it at completion — it needs durable new state that the gate is not permitted to write, and putting a Git ref in the capsule would make the fingerprint depend on repository history rather than on task authority. Rejected: issue #13's third option, improving only the diagnostic — the failure is false, and a well-worded false failure still blocks a correct task. Basis: F1, F2, F4.

- D2 — The exclusion is reported, not silent. A warning names the path and the completed task whose Touch covers it. `--base HEAD` genuinely cannot tell who wrote a path, so where two tasks could own it the honest output is "attribution was ambiguous and resolved to the other task", not silence. This keeps the gate's own principle from F5 — conservative attribution — pointing the same way in both directions: it does not blame the selected task, and it does not pretend the question did not arise.

- D3 — Only a **checked** sibling counts. An unchecked task's Touch is a plan, not a record: it has not been authorized, run, or reviewed, so it cannot vouch for a change already in the worktree. Admitting unchecked siblings would also gut the check, since the task about to run next commonly declares overlapping paths. Basis: F2 and the meaning of the checkbox in `keel gate task-complete`.

## Risks

- A1 — Risk: the selected task might itself have written a path that a completed sibling happens to declare, and the exclusion would hide that. Mitigation: three-fold. The warning names it, so it is visible rather than dropped; the write guard denies out-of-Touch writes at the moment they happen on the Claude target, which is the control that can actually attribute authorship; and `--base HEAD` never could disambiguate this, so nothing that previously worked stops working.
- A2 — Risk: a sibling's Touch is read from the raw field rather than a compiled capsule, so a sibling whose contract does not compile still contributes path claims. Mitigation: accepted and deliberate — refusing to read a non-compiling sibling's Touch would resurrect the false failure whenever any other task in the change is mid-edit, which is common. The claim is only ever used to *withhold* blame from the selected task, never to grant it authority.
- A3 — Assumption: no existing task changes its compiled fingerprint. Basis: this touches only completion-time attribution and adds no capsule field. Resolve by: the fingerprint-stability scenarios in the full suite.
