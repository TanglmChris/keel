## Decisions

- D1 — A scenario that cannot run because an **external runtime is absent** exits `3` and reports a skip; `--all` counts those separately, names them in the summary, and does not fail. `3` is chosen because `2` already means "unknown scenario or usage error" (F3) and conflating an unavailable runtime with a caller mistake would hide both. The skip reason is narrow on purpose: **absence of an external runtime only.** A scenario may not skip because an assertion is inconvenient, a fixture is hard, or a platform differs — those are failures. Rejected: returning `0` on skip, which makes an unverified scenario indistinguishable from a passing one in any consumer that only reads the exit code. Rejected: dropping the two scenarios from the registry on CI via an environment variable, which moves the decision into workflow YAML where no spec or review sees it. Basis: F1, F3.

- D2 — Platform-dependent path assertions normalize the captured output rather than branching on the host. The doctor output's separators are folded to `/` before comparison and the expected strings are written with `/`. Rejected: asserting `os.sep`-built strings, which makes the assertion read differently from the thing a human sees in the output; and rejected: asserting both spellings, which passes on a platform that prints neither correctly. Basis: F2.

- D3 — The workflow runs the full gate on `ubuntu-latest` for push and pull_request, and does not touch the release path. `publish.yml` keeps its own tag/version guard and stays free of the suite, because a release is cut from a commit CI has already verified. This implements the CI half of the split `keel-verification-layering` already documents (F7); it does not redefine the convention or replace the local fast check.

- D4 — Task 2.1's verification strategy is `evidence-first`, with a real CI run as its evidence, because Linux behavior cannot be proven from the authoring machine. **The first run is expected to surface platform assumptions inspection did not find**, and fixing those is inside that task rather than deferred: the task is not complete on "the workflow file exists", it is complete on "the run is green". A single Linux job is deliberate for now — a Windows matrix leg would only re-prove what the pre-push hook already proves on that platform.

## Risks

- A1 — Risk: a skipped scenario is an unverified scenario, and CI green could be read as "all 70 passed". Mitigation: the summary names every skip with its reason and reports the verified count separately, so the number that appears in evidence is the number actually run; and both scenarios still execute on the author's machine, where the pre-push hook exercises them before any tag is pushed.
- A2 — Risk: the two native-runtime scenarios could rot unnoticed, since only one machine ever runs them. Mitigation: unchanged from today — that is already the status quo for all 70 — and the skip line makes their absence visible on every CI run instead of invisible. Narrowing it further needs a CI runner with those CLIs, which is a separate decision.
- A3 — Risk: exit code `3` is new, so a caller treating any nonzero result as failure would newly read a skip as a failure. Mitigation: the only invocations in the repository are `package.json`'s `--all` and the pre-push hook that calls it, and `--all` maps `3` to skipped internally; the code is stated in the spec so a future caller can handle it.
- A4 — Assumption: no scenario silently depends on case-insensitive path lookup, which Windows provides and Linux does not. Basis: not verifiable by inspection at reasonable cost. Resolve by: the first CI run, per D4 — this is exactly the class of assumption CI exists to surface.
