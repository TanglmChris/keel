## Context

`invalidationProblems()` and `expectationProblems()` in `src/core/gates.js` each locate their heading and slice to the next `## ` heading. That bound is correct for a document of headings and wrong for a document of lists, which is what a tasks.md is. The consequence is not one bug but two with opposite signs: entries a task declared under `Covers` are judged as section entries and reported unclosed, and a task field spelled `none` is read as the section's `- None.` and closes the whole declaration.

This change is the second half of a repair the repository already made once. `parseTasks()` ends a task's body at the next task or the next `##` heading, and `keel-task-capsule / A task body ends at the next task or the next heading` publishes that boundary along with the sentence "Every consumer of a task's extent MUST use that same boundary rather than recomputing one." The section readers hold the mirror of that boundary and were not brought along.

## Goals / Non-Goals

**Goals:**

- A change-level section's extent is the section the author wrote, wherever it sits in the file.
- A declaration is never silently closed because a line inside a task body looked like its `- None.`.
- Both readers get the fix through one computation rather than two that agree today.
- The tail position — the shape every archived change uses — is provably unchanged, by assertion rather than by argument.

**Non-Goals:**

- Requiring or documenting a section position. D2.
- Changing what closes an entry, or any diagnostic code or message. `Covered by:`, `Updated by:`, `Durable owner:`, and `Discard reason:` are untouched.
- Tightening the entry patterns to demand top-level indentation. #71 offers this as an alternative; D3.
- Unifying the *heading* half of the two boundaries. D5 — the owner's decision, and the reason this change is a second attempt rather than the first.
- #65, #51, #52. Different mechanisms, separately owned on their issues.

## Decisions

- **F1** — reproduced 2026-08-04 at 5.25.0 on the current tree, in a scratch repository built by one script. With `## Expectation Coverage` above the task list and both entries closed by `Covered by:`, `keel gate change-close --change demo --action archive` reports `E1 lacks behavior coverage, durable owner, or discard rationale.` and the same for `E2`. With the identical section moved to the file's tail, both problems are gone and no other verdict moves. The entries the gate judged are the `- E1:`/`- E2:` lines the tasks declare under `Covers`. *Basis: direct execution of `node bin/keel.js`.*
- **F2** — the same slicing produces a silent false negative, which #71 does not report. In a scratch repository where `## Invalidates` sits directly above a `repo-action` task whose `Touch` is a bare `- none`, and `I1` closes with nothing at all, `keel gate task-start --change demo --task 1.1` returns **`pass`**. The identical section moved to the tail returns `fail` with `invalidation-closure`. The `- None.` early return matched inside the task body. *Basis: direct execution, both positions, one script apart.*
- **F3** — the two slices are duplicated, not merely similar. `gates.js:924-925` and `gates.js:1027-1028` are character-identical, and so are the `- None.` early return and the shape of the entry pattern beneath each. *Basis: the source at 5.25.0.*
- **F4** — the mirror boundary is already implemented and already required. `parseTasks()` (`src/core/task-contract.js:76-91`) ends a task's body at the next task or the next `##` heading, whichever comes first, and `openspec/specs/keel-task-capsule/spec.md:313` states that boundary and adds that every consumer of a task's extent must use it rather than recomputing one. *Basis: the source and the published spec.*
- **F5** — the position that avoids the defect is stated nowhere. `grep` over `AGENTS.md`, `assets/bootstrap/AGENTS.md`, both copies of the tasks template, the schema, and both diagnostics finds no requirement, recommendation, or mention of where either section goes. Across 49 archived tasks.md it is nonetheless uniform: both sections sit in the tail in every one. *Basis: that grep.*
- **F6** — no archived change flips verdict under the new boundary. Of 156 archived task checkboxes, 0 are indented; of 277 `E<n>` and 139 `I<n>` entries, 0 are indented; exactly one archived tasks.md carries a standalone `- none` inside a task body — `2026-08-01-declare-who-runs-the-task:104`, the `Touch` of the `repo-action` task at line 96 — and that file's two sections start at lines 380 and 394, after it, so the old slicing never reached it and the new bound does not change where either section ends. *Basis: `grep` over `openspec/changes/archive/*/tasks.md`.*
- **F7** — both readers already receive the parsed task array. `invalidationProblems(repo, selection.content, selection.tasks)` at `gates.js:246` and `expectationProblems(...)` at `gates.js:1178` are each passed the result of `parseTasks(content)`, whose entries carry `line`. Neither needs a new argument. *Basis: the source at 5.25.0.*
- **F8** — the owner decided the heading half on the issue, in the open, before this change existed. https://github.com/TanglmChris/keel/issues/71 records the choice as option (a): leave the section's heading test as `/^##\s+/m` and fix only the task half. The measurement behind it: unifying on `parseTasks()`'s `/^\s*##\s/` made a section in the **tail** whose body contains an indented `## …` line truncate there, and an unclosed `- I2:` after that line stopped being reported at all — a new instance of the exact failure class this change exists to remove. *Basis: the issue thread, and the branch `origin/a-section-ends-where-the-tasks-begin` where that code is left in place as the evidence.*

- **D1** — one `sectionBody()` helper computes both section bodies, ending at the next `##` heading or the next task, whichever comes first. Fixing only `expectationProblems()` — which is all #71 reports — would leave F3's identical lines in the other reader, and F2 is the half that lives there. A defect repaired in one reader and left in its copy is how a fixed defect comes back. *Basis: F2, F3, F4.*
- **D2** — section position becomes irrelevant, not required. #71 offers both endings. Requiring the tail would refuse a layout nothing has ever documented as wrong (F5), would need a new diagnostic to say so honestly, and buys nothing: what the checks judge is the section's content. Cancelling an undocumented rule costs no author anything, because no author was following it deliberately. *Basis: F5.*
- **D3** — the entry patterns are left alone. #71's second candidate — require `E<n>` at the section's top-level indentation — would fix F1 but not F2, whose `- none` an indentation rule would still have to exclude by position. Two mechanisms where one suffices is F3 repeating itself, and the indentation rule would newly refuse an author who indents a real entry. *Basis: F1, F2, F6.*
- **D4** — the boundary tests each line against the task lines `parseTasks()` already returned, rather than re-matching a checkbox pattern. A second pattern that must agree with `parseTasks()` is exactly the duplication F3 describes; identity against `line` cannot drift. *Basis: F7.*
- **D5** — the heading half stays `/^##\s+/m` and is **not** unified with `parseTasks()`'s `/^\s*##\s/`. This is the owner's decision (F8), taken against the recommendation's own measurement: the two patterns are not interchangeable, and unifying them buys a spelling consistency at the price of a new silent skip in the tail position. What the published requirement (F4) demands is that a consumer of *a task's extent* use the task boundary, and D4 satisfies that literally — the task half here **is** `parseTasks()`'s task list. A section's heading bound is the section's own, not a task's extent, so leaving it alone contradicts nothing. *Basis: F8, F4, D4.*
- **D6** — verification drives `keel gate change-close` and `keel gate task-start` on real repositories, asserting four cells per section: closed and unclosed, section-above-tasks and section-in-tail. The tail cells are the regression F6 argues for, asserted instead of argued. A unit test of the slice would prove the half that was never in doubt. *Basis: F1, F2, F6.*
- **D7** — the two tail cells pass before the change as well as after, so each is proven able to fail by aiming it at a mutation rather than by being watched to go green. *Precedent applied: `an-assertion-that-never-failed-proves-nothing` — a check that passes because two things agree also passes when the mechanism producing both is broken.*

## Hidden Knowledge / Assumptions

- **A1** — no tasks.md nests a task checkbox inside a change-level section entry. 0 of 156 archived checkboxes are indented (F6), and `parseTasks()` already reads an indented `- [ ] 1.1 …` as a task, so such a line is a task by the repository's existing definition. *Basis: F6. Owner: this change — if wrong, the section ends early and its later entries are reported unclosed, which is a refusal an author can see rather than a silent pass.*
- **A2** — nothing outside this repository parses the text of `expectation-closure` or `invalidation-closure`. Neither code nor message changes here, so a consumer keying on either is unaffected in any case. *Basis: the diff. Owner: this change.*
- **A3** — a suite fixture that passes today only because its section absorbed the task list is asserting something untrue, and is repaired at the assertion rather than by preserving the boundary. None is known: `write_gate_fixture` puts a `## Tasks` heading between its coverage section and its tasks, and `task_contract_fixture`'s `## Invalidates` carries its own `- None.` line. The full run is what would surface one anyway. *Basis: the two fixtures at `scripts/validate_plugin.py:3046` and `:3953`. Owner: this change — the failure mode is a red suite, which is visible.*
- **A4** — the owner's decision at F8 is recorded on the issue and not in the declared precedent store. The store is a separate repository, and writing to it is outside this run's authority; the issue is a durable owner this repository already accepts. *Basis: `keel/config.yaml` `precedents:`, and the issue thread. Owner: the owner, if the reasoning is worth promoting beyond this one decision.*
