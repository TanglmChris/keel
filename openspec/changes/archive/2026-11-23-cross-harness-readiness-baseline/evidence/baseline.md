# Cross-harness readiness for Keel #544

Checked on 2026-11-23 against the Keel 5.231.4 candidate. Local CLI versions are Codex 0.171.0, Claude Code 2.1.325 and DSH 0.2.2-rc.1. OpenCode was not on PATH. Local `keel capabilities --target <target> --json` reports Claude guard and post-compaction reinjection advisory, the corresponding other targets manual, and Codex managed roles manual until verified for the actual endpoint. Installation and capability declarations do not establish production readiness.

| Required observation | Codex | Claude Code |
| --- | --- | --- |
| Busy, idle and waiting | Managed adapter reads native thread status. Active work cannot migrate. Explicit migration separately checks native input queue, Goal and terminals. | CLI shift uses background jobs status. Published host evidence shows distinct busy, idle and owner-input waiting; the shift waits for busy and waiting. No queue API equivalence established. |
| Persistence and working directory | Native thread ID, bound worktree and full history. Delivery tracks immutable chat record IDs and unknown claims; the source and target endpoint checks have native and fixture evidence. | Role binding and host session/job IDs, shift note and transcript ownership. Job cwd may describe the original checkout, so existing shift code separately reads native worktree metadata. |
| Release and recovery | Same native writer boundary. #550 requires source-side unload before requesting acquisition. Unknown outcomes can be inspected and explicitly reconciled without rewriting original claims. | Existing shift waits on host state and branch locks, and starts a new Claude session after claiming a handoff. Same-harness retry/adoption is scoped to the persisted shift entry. |
| Approval and progress | Native reviewer and sandbox policy checked on the managed thread. An accepted turn or delivered chat record does not establish requested task completion. | Native owner waiting is visible in job status. A recorded chat todo, shift note, job status or terminal model message alone cannot certify the requested task behavior. |
| Exhaustion | No existing task-level policy for model usage exhaustion and choosing a different harness. | Tick's existing quota file feeds patrol decisions rather than providing authoritative per-task exhaustion, resource eligibility or failover. |

Current `tick` uses separate routes: managed Codex wake, Claude ended-session wake, then Claude shift claims. A managed Codex role is explicitly excluded from the Claude fallback. DSH and OpenCode have target-specific delivery surfaces without verified integrations into these dispatch paths.

A Keel chat todo already carries a durable ID and role, and host receipts already identify activity. The first implementation slice can reuse those references while defining independent task and execution generations and a single projected state for an upper client. Key distinctions are planned, running, waiting for review, waiting for resources, unknown effects and verified completion. Keep the current candidate and authority stable through a normal tick. During exhaustion, identify which effects landed and which receipt is still ambiguous, prove the old executor cannot continue writing, then select a preconfigured eligible executor. A blank or failed status read is insufficient to revoke the old executor or replay side effects.

Existing OpenSpec coupling needs explicit migration. `context` infers work from OpenSpec change and task ownership. Core gates compile scope and acceptance from the selected capsule. Session hooks and manual projection reconstitute this state, and generated protocol assets package those paths. Optional OpenSpec needs a separate source for authority, evidence and recovery state while in-flight OpenSpec capsules continue operating.
