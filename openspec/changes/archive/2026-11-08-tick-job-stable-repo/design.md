## Facts

- F1 — `patrolWorktrees(where)` in `src/core/tick.js` reads `roles.json` on every run and takes the first sorted worktree bound to each declared role; `tick()` fetches and spawns `keel patrol` with that worktree as `cwd`. A job that names any checkout of the repository therefore reaches the role's current worktree, and rebinding needs nothing re-rendered.
- F2 — `task()` writes `patrolWorktree(where).worktree` as the argument after `--repo` and as `WorkingDirectory`; `renderTask` says "the tick runs the patrol of the worktree …". The label uses `where.project`, which every worktree of a repository agrees on.
- F3 — `readPatrolDeclarations(repo)` reads `<repo>/keel/config.yaml`, and `tick --repo <path>` sets `where.worktree` to that path, so the path the job names decides which `patrol:` is read. A worktree's checked-out branch can carry a newer config than the main checkout's.
- F4 — Measured 2026-11-08: `~/Library/LaunchAgents/dev.keel.tick.keel.plist` names `keel-optimization-maintenance-0cb8d4` for `--repo` and `WorkingDirectory`, while `roles.json` binds `keel-maint` to `keel-maint-cli`; `dev.keel.tick.kaiwu-ip.plist` names `.claude/worktrees/cbb_dmc_iecc_pm`; `dev.keel.tick.ChipSTRIDE.plist` names the main checkout. All three directories exist today, so nothing is failing yet.
- F5 — The main checkouts of keel, ChipSTRIDE and kaiwu-ip are on `main` and each declares `patrol:` (measured 2026-11-08), so D1 applies to every job on this machine.
- F6 — `inspectJobs()` in `src/core/launchd.js` reads only `ProgramArguments[0]`; `printLaunchdJobs()` in `bin/keel.js` prints one problem line per missing node or a single `launchd: ok`, and does not change the exit status. `src/core/chat/wake.js` and the bridge write neither `WorkingDirectory` nor `--repo`.
- F7 — `locate()` in `src/core/chat/store.js` returns `common` (the real git common directory). The main checkout is `dirname(common)` when `basename(common)` is `.git`; for a bare repository there is none.
- F8 — Text that says the job names the bound worktree: the scenario "The launchd job is printed, not installed" in `openspec/specs/keel-coordinator-patrol/spec.md`, `renderTask` in `src/core/tick.js`, and the `keel tick task` paragraph in `docs/cli-team.md` and `docs/cli-team.zh-CN.md`.
- F9 — Issue #503 proposes four things: a stable name in the job (1), re-render on rebind as the alternative (2), a doctor check on `--repo` and `WorkingDirectory` (3), and the rule in the docs plus `keel tick install` / `uninstall` (4).

## Decisions

- D1 — `task()` names the main checkout, `dirname(common)`, as `--repo` and `WorkingDirectory` when `basename(common)` is `.git`, that directory exists, and `readPatrolDeclarations` of it yields at least one declaration. Otherwise it names the bound worktree as before and `renderTask` adds one sentence saying which condition failed. The JSON form gains `repo` (what the job names) and keeps `worktree` (where the patrol runs now). Issue suggestion 2 is not needed once D1 holds.
- D2 — `inspectJobs()` also returns the directories a job runs in: `WorkingDirectory` and the argument after `--repo`. `printLaunchdJobs()` prints a `launchd: problem` line for each that does not exist, and for each that lies under a `.claude/worktrees/` directory, naming the file, the path and the `recreate` command it already carries; `launchd: ok` is printed only when no job has any problem, and its wording says nodes and directories. Exit status unchanged, as for the node check.
- D3 — `patrolWorktrees()` keeps, per role, the bound worktrees whose directory exists, and takes the first of those. When a role has bound worktrees and none exists, the entry's `why` names them, says they no longer exist, and points at `keel chat role --prune`; the tick runs no patrol for it and exits 0, as it does for a role with no binding.
- D4 — The docs state the rule once, in the `keel tick task` paragraph of `docs/cli-team.md` and `docs/cli-team.zh-CN.md`: a launchd job must not name a path under `.claude/worktrees/` or inside a `.venv`, because both are regenerated, and `keel tick task` now names the main checkout for that reason.
- D5 — Not done, with the reason: `keel tick install` / `uninstall` (suggestion 4, second half) would make Keel register a host job, which the published requirement forbids ("MUST create nothing") and the protocol states ("Keel schedules nothing"); that is a product decision for the owner and is put to them with the release. Installed plists are not rewritten for the same reason: the owner re-runs `keel tick task` and its install commands.
- D6 — Out of this repository: the downstream `flow/*_agent.sh install` scripts that write their own plists under a worktree. The rule in D4 is what they can follow; `kaiwu-flow` is told through the usual single dm after the release.

## Risks

- R1 — A job now reads `patrol:` from the main checkout, which can lag a worktree's config until a change merges. D1 falls back to the bound worktree only when the main checkout declares none; a changed `patrol:` takes effect for the job when it reaches the main branch and the main checkout is updated, which the kaiwu repository already keeps current with a `main-ff` job.
- R2 — A machine whose main checkout sits on another branch reads that branch's `patrol:`. Accepted: it is the checkout the owner chose to keep, and `keel tick task` prints which directory it named.
