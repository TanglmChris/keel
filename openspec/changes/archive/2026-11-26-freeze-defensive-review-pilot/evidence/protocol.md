# Synthetic pilot for Keel #533

These four Python workloads test internal transformation, untrusted JSON input, uncertain external delivery and supported legacy behavior. All inputs are synthetic. The base condition uses the existing scope sentence from Keel's AGENTS.md at 597ff22e. The treatment adds one traceability instruction. The experiment evaluates adding that instruction to this excerpt. Generalizing to all installed Keel guidance would require another experiment.

Run `python3 pilot.py calibrate` to check the positive and targeted negative for each workload. Run `python3 pilot.py assignments` for the controller's fixed execution order, opaque IDs, exact prompts and their SHA-256 hashes. Run `python3 pilot.py review` for the separate reviewer's score sheet, ordered by ID. The program uses the Python standard library and performs no model dispatch.

## Sampling and review

1. After budget authorization, run each of the 16 assignments once. Use the same installed client version, reasoning effort (medium), synthetic context, tool-free configuration and read-only isolated working directory for all runs. Record the resolved model if the host reports it. Record any discrepancy, timeout, missing usage, truncation or unsupported option. A failed cell stays missing. Further attempts require a revised budget.
2. Keep the assignment key, actual prompt, raw reply, runtime, model identifiers and native input/output token counts in the controller record. Mark unavailable values unknown. Preserve the original response. Apply a fixed extraction rule: strip a single enclosing Python or plain Markdown fence if present, then use the entire remaining text as the candidate module. Non-code output that still fails parsing is an unsuccessful answer.
3. Give a separate reviewer only the fixture requirements, candidate modules labelled with their run IDs, and the review sheet. Keep model, condition, run order, latency and usage out of that packet. The controller who has seen the key cannot claim a blind review. Store each patch as the diff from the supplied starter. Run candidate code only in a disposable offline environment, with time limits and no credentials or user files.
4. Record every failing behavior assertion. For each added defensive path, cite the candidate line and the task requirement, fixed input contract or observed failure that justifies it. Count a path as unsupported when none applies. Record hidden failures if errors turn into apparent success, and a lost safeguard if required validation, error propagation or single-effect behavior fails. A semantic reviewer judges a branch even when all behavior tests pass.
5. Freeze scores before joining the controller record. Compare paired conditions by fixture within each model. Publish raw counts, missing cells, behavior failures, wall time and usage. With one sample per cell this pilot can identify examples and tradeoffs. A model-specific prevalence claim needs independent repeats. No production instruction changes follow from an incomplete pilot.
