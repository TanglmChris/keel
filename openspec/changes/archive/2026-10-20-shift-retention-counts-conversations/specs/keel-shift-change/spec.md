## MODIFIED Requirements

### Requirement: A CLI session changes its own shift and the next one is named for its start

In a Claude Code CLI session, `keel shift ready --wake` MUST record the session id and process in the note, queue the hand-off in the chat store, arm no clear waiter, leave a detached hand-over waiter that carries the hand-over out every few seconds until the entry is no longer pending or two hours pass, and say that the session should end its turn. `keel tick` MUST carry out any queued hand-off as well, and the two MUST NOT start two sessions for one entry. A hand-over MUST leave the entry while `claude agents` shows the old session's status as anything but idle — busy, or waiting for input such as a session blocked on a question — and MUST NOT read its job state, which labels the last message rather than whether the turn has ended; once its status is idle, or it is stopped or gone it MUST retire the old session by stopping it with `claude stop`, keeping its conversation, and MUST NOT resume it, because a session running with Remote Control takes its claude.ai title back over a rename, and only then start a new session with `claude --bg -n "<role> · <MM-DD HH:MM>" --permission-mode <mode>`, named for its local start time, and a prompt to run `keel shift resume`, in the role's worktree, recording `delivered` with the new session id and name or `failed` with the reason, once per entry. After a delivered hand-over it MUST keep the newest `shift: keep_old_sessions:` (default 3) stopped background sessions whose working directory is one of the role's bound worktrees, other than the new session, counting only a session with a conversation — a transcript in the host's files or in Keel's store — and remove each older one with `claude rm` only once Keel's store holds a copy of its transcript, recording the removed ids on the entry; a session whose transcript cannot be copied MUST stay, and a session with no transcript anywhere, never given a prompt, MUST NOT be counted and MUST stay. `keel shift status` MUST list each hand-off with its state and the command that reopens the old session, and the patrol MUST report a failed hand-off, or one pending over 15 minutes, as a risk.

#### Scenario: The waker hands a CLI shift over once the old session is idle
- **WHEN** `verify`'s CLI session `5b14fbae-b6aa-40b6-a72a-b3f89d2c6eea` (job id `5b14fbae`) runs `keel shift ready --wake`, and `claude agents --json --all` shows it busy, then waiting for input with state `blocked`, then idle with state `working`, with no `keel tick` run
- **THEN** the note records the session id and a waiter was started with no `CLAUDE*` variable in its environment; nothing is stopped or started while it is busy or waiting; once it is idle, though its state still reads `working`, the calls are, in order, `stop 5b14fbae` and `--bg -n "verify · <MM-DD HH:MM>" --permission-mode auto` with a `keel shift resume` prompt in verify's worktree, and the old session is never resumed; status shows it delivered with the new session, its name, and `claude attach 5b14fbae`

#### Scenario: Only the newest old sessions stay listed
- **WHEN** `keel/config.yaml` declares `shift: keep_old_sessions: 2`, and after a hand-over `claude agents` lists six stopped background sessions in verify's worktree — one newer than all but the session just handed over with no transcript anywhere, and the oldest with only Keel's copy of its transcript — a stopped session in another worktree, and the new session
- **THEN** the two newest old sessions with a transcript stay; each older one is removed with `claude rm` after Keel's store holds its copy, the one with only Keel's copy included; the one with no transcript is not counted and stays, as do the other worktree's session and the new session; and `keel shift status` names the removed sessions

#### Scenario: The tick and the waiter start one session
- **WHEN** a hand-over lock younger than two minutes exists for `verify` and `keel tick` runs, and then the lock is removed and `keel tick` runs twice
- **THEN** the first tick starts nothing; the second starts one session and the third none

#### Scenario: A failed hand-off is a risk
- **WHEN** the new session cannot start
- **THEN** status shows the hand-off failed with the reason, and `keel patrol` reports it as a risk
