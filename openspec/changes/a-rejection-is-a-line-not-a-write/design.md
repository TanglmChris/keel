## Context

`completionChecks()` (`src/core/gates.js:733`) already validates the shape of author-written Evidence entries that are not gate-computed: `Blocker` (concreteness gates a hard stop) and the four Review entries (concreteness plus a shared vocabulary). `Reauthorizations` joins this set as a fifth author-written entry, but with different semantics from both of its neighbors — unlike `Blocker`, its presence must never block completion; unlike Review, it carries no accepted vocabulary at all, only a concreteness requirement.

`reviewValue()` (`src/core/gates.js:368`) already reads a labelled Evidence entry from its label line to the next sibling entry at the same or shallower indentation. It operates on `field(task, "Evidence")` and a label string; nothing about it is specific to the four Review labels it currently serves. 5.28.0's design recorded this directly: "if a fifth label is added later it inherits the block read, which is the intended behavior for any labelled value" (A3, `openspec/changes/archive/2026-08-04-a-review-field-is-what-the-author-wrote/design.md`).

## Goals / Non-Goals

**Goals:**

- A task author can record, in their own words, what a gate rejected and what they changed, without the gate writing anything on the failing outcome that produced the rejection.
- `task-complete` validates only that a written `Reauthorizations` entry is concrete — the same bar `missing-field` already applies to `Covers`, `Verify`, and `Evidence` — and never that a rejection factually occurred.
- A `Reauthorizations` entry that wraps across lines is read whole, not truncated at its first line.
- Existing tasks — every one of which predates this field — keep passing with no `Reauthorizations` entry at all.

**Non-Goals:**

- Gate-side recording of a rejection (R3). Not taken; `keel-core-gates:231` stays unconditional. F1–F3.
- Making `Reauthorizations` a hard stop like `Blocker`. Its presence is a log entry, not a blocker; a task with real rejections recorded can still complete. F4.
- Requiring the field on every task, or requiring its entry count to match how many times a gate actually rejected the task. Nothing records a rejection count today (F1), so there is nothing to check completeness against, and requiring the field would fail every archived task that predates it.
- Any structural format inside a `Reauthorizations` entry beyond concreteness — no requirement to name a gate, a problem code, or a fixed template. Free text, the same trust boundary `Findings` already carries.
- Touching `field()`, `fieldValues()`, `parseTasks()`, or `reviewValue()`'s own logic. The fifth label is a new caller, not a new reader.

## Decisions

- **F1** — `keel-core-gates:231` is unconditional: "The only permitted project writes are the disposable `keel-write-guard/v1` manifest written by a passing `task-start` … and the single-line replacement of the … `Contract:` Evidence anchor performed by a passing `task-start` … `task-complete`, `change-close`, and every failing or `needs-review` outcome MUST NOT write project state." *Basis: `openspec/specs/keel-core-gates/spec.md:231`, quoted directly on #70.*
- **F2** — replaying a gate-side record-the-rejection write (丙 in its most direct form) across this repository's 44 archived changes fires 458 times; 87% of non-first tasks in a multi-task change have at least one path in a sibling task's `Touch` that was already dirty at their own `task-start`, because tasks in this repository do not commit between each other. At least one of the 458 is already proven false — recorded in that change's own Review at the time. *Basis: issue #70, comment 2026-08-04 ([issuecomment-5175636843](https://github.com/TanglmChris/keel/issues/70#issuecomment-5175636843)).*
- **F3** — the owner chose R2 over R3 on 2026-08-05, transcribed on the issue: "the task author records a `Reauthorizations:` line in Evidence themselves; the gate adds no new write. R3 … was not chosen — no need to reverse a published rule when R2 gets the same visibility without it." *Basis: [issuecomment-5190238655](https://github.com/TanglmChris/keel/issues/70#issuecomment-5190238655).*
- **F4** — `Blocker`'s existing check (`gates.js:782`) pushes a `blocker` problem whenever the field is concrete — presence alone fails the gate. `Reauthorizations` needs the opposite: a task that recorded real rejections and then fixed them must still be able to complete, or the field would punish the exact honesty R2 is meant to collect. *Basis: reading `completionChecks()`.*
- **D1** — `Reauthorizations` is validated with the same concreteness rule `missing-field` already applies (`task-contract.js:416`): absent, `none`, or `pending` need no entry; any other text must carry no unfilled `<slot>`/`TODO`/`TBD`/`placeholder` token. `unfilledToken()` already computes exactly this distinction and already discriminates "nothing here" from "a placeholder is still here" for every other field that uses it — reusing it needs no new vocabulary. *Basis: `task-contract.js:45-59`, D1 keeps this reuse rather than a bespoke check.*
- **D2** — the entry is read with `reviewValue(task, "Reauthorizations")`, unmodified. The function's own extent logic — label line to next sibling at the same or shallower indentation — is exactly what a multi-line rejection record needs, and A3 of the change that built it named this reuse as the intended behavior for a fifth label. No change to `reviewValue()`, `REVIEW_SIBLING`, or any of its four existing callers. *Basis: Context, `keel-core-gates` design A3 (2026-08-04-a-review-field-is-what-the-author-wrote).*
- **D3** — the check is additive-only: a completely absent `Reauthorizations` entry, indistinguishable by `reviewValue()` from an entry present but empty, produces no problem either way. `unfilledToken()` returns `null` for both "nothing was written" and "none/pending was written," and only returns a token when real, non-placeholder text was started and left with a slot in it — so absence and `none` are accepted identically, and only an actually-abandoned placeholder is refused. This is what makes every one of the repository's existing tasks — none of which declare this field — keep passing task-complete unchanged. *Basis: `task-contract.js:45-59`; Goals/Non-Goals "existing tasks... keep passing."*
- **D4** — verification drives `keel gate task-complete` on real repositories, not a unit test of the extractor: absence, bare `none`, a wrapped multi-line entry, and an entry left with an unfilled `<slot>` token are each asserted through the CLI's JSON problem list, plus a regression proving presence of a concrete entry does not by itself fail completion (the anti-`Blocker` case). *Basis: D1, D2, F4; the same posture 5.28.0's D6 took for `reviewValue()`'s other callers.*
- **D5** — the templates (`openspec/schemas/keel-spec-driven/templates/tasks.md` and its packaged copy) add `- Reauthorizations: none` after `- Blocker: none` in every Evidence example, so a newly authored task discovers the field the same way it discovers `Blocker`. This does not change `task-start`: the field is not part of the compiled capsule (`compileTaskContract`), only of `completionChecks()`, so its presence in the template has no effect on any `task-start` verdict. *Basis: Impact in proposal.md; `tasks-template-red-green-example` only exercises `task-start`.*

## Hidden Knowledge / Assumptions

- **A1** — no existing archived or in-progress `tasks.md` declares a `Reauthorizations` entry, since the field does not exist before this change. D3 is what makes that safe rather than merely convenient. *Basis: D3. Owner: this change — if wrong, some other reader already matches the literal string `Reauthorizations:` for an unrelated purpose, which `grep -rn "Reauthorizations" --include=*.js --include=*.md .` (excluding this change's own directory) would show before implementation.*
- **A2** — `reviewValue()`'s sibling-bound extent, built and hardened for the four Review entries, generalizes correctly to a label with no nested indentation requirements of its own. `Reauthorizations` entries are flat prose or a flat list, the same shape `Findings` already takes; nothing about `Reauthorizations` needs a second level of nesting the way `Review:` itself has one. *Basis: D2. Owner: this change.*
