- F1 — Verified fact: `scopeProblems` (`src/core/gates.js:355-366`) already exempts two path classes from outside-Touch attribution: the literal `keel/guard.json`, and anything under `openspec/changes/<change>/` for the change being completed. The comment names the reason — "the working state the gate is completing against". `keel-core-gates / Dirty-worktree attribution is conservative` states the same rule normatively, with two dedicated scenarios. Basis: the function body and the live spec.
- F2 — Verified fact: the guard has no equivalent. `pathAllowed(candidate, manifest.touch)` (`plugins/keel/scripts/pretooluse-guard.js:78-85, 144`) is the only allowance, and `manifest.touch` is exactly the declared Touch list. Basis: the hook body.
- F3 — Verified fact: `authorityPaths` (`src/core/guard.js:51-60`) seeds the authority set with `openspec/changes/<change>/tasks.md` unconditionally, and every `Covers` entry that resolves to free text also carries `source: openspec/changes/<change>/tasks.md#<id>`, so the file is in the set for every task. `hashAuthority` records its byte hash, and both the hook (`:118-135`) and `guardStatus` (`src/core/guard.js:242-252`) deny on any byte change. Ticking a checkbox or appending Evidence changes those bytes. Basis: all four call sites, and issue #8's reproduction.
- F4 — Verified fact: the compiled capsule contains no checkbox state and no Evidence values. Its fields are task identity, owner, mode, resolved authority, read, touch, acceptance, verification, boundaries, coupling, helper authority, and prohibitions. Confirmed by execution on 2026-07-27: a task's recorded fingerprint recomputed unchanged after its checkbox was ticked and its entire Evidence block was written, four times across two changes. Basis: the capsule constructor (`src/core/task-contract.js:780-830`) and the gate runs in `openspec/changes/archive/2026-07-27-honest-surfaces-and-owners/tasks.md`.
- F5 — Verified fact: `guardStatus` compares the recompiled contract fingerprint against the manifest's independently of the authority hashes (`src/core/guard.js:230-241`, `fingerprint-drift`), and `task-complete` recompiles and compares the anchor recorded in Evidence. Both would catch an edit to Touch, Verify, Covers, or a boundary inside `tasks.md`. Basis: both call sites.
- F6 — Verified fact: `taskStartContractProblems` (`src/core/task-contract.js:234-269`) accepts `Touch: none` only for `Mode: diagnose-only`; every other mode requires a concrete path, and `SUPPORTED_MODES` holds exactly `implementation`, `diagnose-only`, `plan-first`. The capsule's `prohibitions` list carries `must not commit` for every mode, and adds `must not write product files` only for `diagnose-only`. Basis: the function body and the capsule constructor.
- F7 — Verified fact: both manifest readers require `touch` to be a non-empty string list (`src/core/guard.js:105-111`, `pretooluse-guard.js:54-56`). A `Touch: none` task compiles to `touch: ["none"]`, which satisfies that shape and matches no candidate path, so a no-write task is already representable in the manifest without a shape change. Basis: both validators and the capsule constructor.

## Decisions

- D1 — The guard gains one record-write layer, defined identically to the completion gate's: paths under `openspec/changes/<manifest.change>/`. It is **derived from the manifest's existing `change` field, not stored**, so the manifest schema does not change. Consequence, deliberately chosen: a session running an older plugin hook against a newer CLI keeps today's behavior — it denies record writes — instead of failing closed on an unrecognized shape, which is what a `keel-write-guard/v2` bump would have caused for anyone whose plugin and CLI versions had drifted. Rejected: adding a stored `record` array, which carries the same skew risk for no gain, since the rule has exactly one input the manifest already holds. Basis: F1, F2.

- D2 — Authority-drift checking skips the same prefix, in the hook and in `guard status`. Byte hashing is retained for authority outside the change directory, which is where a task genuinely must not be editing.

  **This narrows write-time detection, deliberately.** Byte hashing did two jobs at once: it reported record writes as drift (the defect), and it also let the hook notice a *real* contract edit inside `tasks.md` — a moved Touch, Verify, or title — at the moment of the next write. The hook cannot compile a capsule, so it cannot separate the two, and the first job has to go. The trade: contract drift inside the change directory is now caught by `keel guard status` and by `keel gate task-complete`, both of which compile and compare the fingerprint (F5), rather than at the next write. An agent that edits its own Touch and forgets to reauthorize is stopped before completion instead of before the write.

  Rejected: teaching the hook to hash a normalized projection of `tasks.md` with the checkbox and Evidence stripped. It would preserve write-time detection, but only by duplicating a piece of the task parser inside a hook whose stated contract is that it never spawns the CLI and never adjudicates contracts — and a projection that drifts from the real parser fails in both directions, denying valid writes or missing real drift. The narrower hook with an exact compile-time check is the more honest split. Basis: F3, F4, F5.

- D3 — `Mode: repo-action` is a fourth supported mode for a task whose effect is an authorized repository-level action and which writes no worktree file. It requires `Touch: none`, exactly like `diagnose-only`; it carries `must not write product files`, exactly like `diagnose-only`; and it is the one mode whose prohibitions omit `must not commit`, because performing that action is the task. Rejected: allowing `Mode: implementation` with `Touch: none` (issue #8's other option), because `implementation` means "modify only Touch files" in the resident protocol and a mode that means the opposite should not share its name — and because a distinct mode value changes the fingerprint, so the authorization is visible in the capsule rather than inferred from an empty field. Basis: F6, F7.

- D4 — Whether the repository action a `repo-action` task performs was actually authorized stays a Review judgment, not a deterministic check. The gate could only guess from `Verify` prose, and `keel-core-gates` already assigns exactly this class of judgment to the current agent and `keel-review-checklist`. What the gate does enforce is the write posture: no worktree writes, and the mode recorded in the fingerprint. Rejected: pattern-matching `Verify` checks for git observations, which is a text heuristic that would reject legitimate phrasings and admit illegitimate ones.

## Risks

- A1 — Risk: the record layer allows a guarded task to write *any* file under its change directory, including another task's entry in the same `tasks.md`. Mitigation: this is already true of the completion gate (F1), so the layers agree rather than diverging; and a task that alters another task's contract is caught when that task's own recorded fingerprint is recompiled at its `task-start` resume or `task-complete`. File-granularity is the only granularity the hook has.
- A2 — Risk: skipping byte-drift on the change directory means editing `design.md` or a delta spec mid-task no longer denies writes. Mitigation: if the edited text is referenced by this task's `Covers`, it is part of the capsule's resolved authority, so the fingerprint moves and F5's checks stop the task. If it is not referenced, it was never this task's authority.
- A3 — Assumption: no existing task changes its compiled fingerprint. Basis: D1 and D2 touch only the guard's runtime decisions and add no capsule field; D3 adds a mode value that no existing task declares. Resolve by: the fingerprint-stability scenarios in the full suite.
- A4 — Revisit trigger, deliberately out of scope: `keel/archive/**` remains a declared path in both the guard and the gate. It kept appearing undeclared only because `finding-owner` refused an issue URL and forced a local proxy note, which was issue #12 and is fixed in 5.2.4. If archive writes start recurring as an unavoidable, unforeseeable need after that fix, this decision is the thing to revisit — this entry is its owner until then.
