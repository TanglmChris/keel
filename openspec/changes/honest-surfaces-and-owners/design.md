## Decisions

- D1 — A durable follow-up owner may be an absolute `http` or `https` URL, in both places a durable owner is required. The two independent implementations (F2) share one helper for the accepted-form list, so the tracker form cannot be added to one and forgotten in the other; each check keeps whatever it accepted before on top of that shared list, so the change is additive in both. The gate cannot confirm an external reference resolves — core gates run without network by requirement — but it already accepts two forms it never confirms (F1), so a shape check for an external tracker is consistent with what the check has always been, not a weakening of it. The spec's own definition of a durable owner was never form-constrained; the enumeration was. Rejected: a configured tracker allowlist in `keel/config.yaml`, which adds project configuration surface without changing anything the gate can actually prove. Rejected: keeping `keel/HANDOFF.md` excluded only by name — it stays excluded, because it is explicitly an override pointer, not an owner. Basis: F1, F2.

- D2 — The guard manifest is declared ignorable by a `keel/.gitignore` containing `guard.json`, scaffolded once by install and never overwritten. `keel/` already mixes committed project content (`config.yaml`, `CHANGELOG.md`, `archive/`) with this one piece of local session state, so the narrowest correct declaration lives beside it. Rejected: moving the manifest under `.git/`, which is conceptually the right home for per-clone state but breaks in a checkout that is not a git repository and changes a path named in the spec, in guard messages, and in the validation suite. Rejected: editing the repository-root `.gitignore`, which is project content Keel does not own and cannot merge safely. Basis: F3.

- D3 — The guard command's own output states the enforcement boundary, in the same sentence family the capability requirement already uses. `started` and `active` describe the manifest; the added statement says enforcement requires a runtime hook that Keel cannot observe from the repository, so the status is never read as a probe result. Rejected: probing the host's resident plugin state to detect the mismatch in F5 — that fact lives on the target side and may not be exposed at all, and Keel's existing capability discipline is to report `manual` rather than infer activation, not to guess harder. Basis: F4, F5, F6.

- D4 — The dogfood hazard is reported as a `--doctor` line gated on `isKeelSourceRepo`, reusing the shipped predicate rather than adding a second test. It states the concrete working invocation, including the explicit repository argument the local entry point requires, because the failure mode is a *silently stale* result rather than an error. Rejected: making the CLI detect that it is running against its own source and warn on every gate invocation, which would fire on every command in this repository including the many that do not touch gate code. Basis: F7 and issue #13 item 3.

## Risks

- A1 — Risk: accepting any absolute URL admits a link that is dead, private, or wrong, and the gate cannot tell. Mitigation: this is the pre-existing property of two of the three accepted forms (F1); the semantic judgment of whether an owner is real stays with `keel-review-checklist`, which reads the Review, and the gate's job here is only to reject a finding with no owner at all.
- A2 — Risk: touching the `Expectation Coverage` rule as well as the `Findings` rule is a wider blast radius than issue #12 reported. Mitigation: the change is strictly additive in both places — every form each check accepted before is still accepted — so no existing tasks.md can start failing. Resolve by: running the full suite, which contains expectation-gate scenarios.
- A4 — Known divergence, deliberately preserved: the two checks disagree on how strictly they read the `openspec/changes/…` form. `Findings` requires an existing `proposal|design|tasks` artifact; `Expectation Coverage` accepts the bare prefix without touching the filesystem, so a `Durable owner:` naming an artifact that does not exist passes `change-close` today. Tightening that is a narrowing unrelated to issue #12 and is out of scope here; this entry is its owner until a change takes it up.
- A3 — Assumption: a project that already has a `keel/.gitignore` wants it left alone, even if it does not mention `guard.json`. Basis: the scaffold-once strategy already used for `keel/config.yaml`. Consequence if wrong: such a project keeps the untracked file, which is exactly today's behavior, so the failure mode is no worse than the status quo.
