# Keel Changelog

## 5.3.1 - the full gate runs in CI; a finished task no longer fails the next one

Closes issues #10 and #13. With #8 and #15 item 1, every issue opened against 5.2.x is now resolved except the resident-block byte budget.

- **A finished task's uncommitted work is no longer the next task's scope failure** (closes issue #13, its last item): `task-complete --base HEAD` diffed the worktree and attributed every changed path outside the selected task's Touch, so when the previous task of the same change had finished but was not yet committed, its files landed on whoever ran next. A path is now withheld from the selected task when a **checked** task of the same change declares it in Touch — derived from `tasks.md`, which the gate had already parsed, so no new state and no fingerprint change. Only a checked sibling counts: an unchecked task's Touch is a plan, not a record. The exclusion is **reported, not silent** — a base comparison cannot establish which task wrote a path, so a warning names the path and the owning task. The per-task commit habit stays the better practice; forgetting it no longer produces a diagnostic naming a file the author never touched. (keel-core-gates)
- **Keel runs its own full gate in CI** (closes issue #10): the 70-odd validator scenarios' only regression net was a pre-push hook on one Windows machine, which is also what `keel-verification-layering` already said should not be the case — it places the full gate "at CI or `keel gate change-close`". Two things blocked it, both smaller than the comment in `publish.yml` implied: **two** scenarios hard-required local `codex`/`claude` CLIs, and **six** assertions hardcoded Windows path separators. `.github/workflows/test.yml` now runs `npm test` on `ubuntu-latest` for every push and pull request; `publish.yml` is untouched and keeps only its tag/version guard. (keel-validation-runner)
- **An absent external runtime skips instead of failing.** A scenario exits `3` when a runtime it probes is not installed — `0` pass, `1` fail, `2` unknown scenario, so conflating an unavailable runtime with either would hide both. `--all` counts skips separately, names each with its reason, and **excludes them from the verified count**, so the number in evidence is the number actually run. The reason is narrow by design: an inconvenient assertion, a hard fixture, or a platform difference is a failure, never a skip. (keel-validation-runner)
- **Assertions no longer encode the host path separator**: a `posix_paths` helper folds captured output and assertions state the forward-slash form — not branching on the platform, and not accepting both spellings, which would pass on a platform printing neither correctly. (keel-validation-runner)
- **Resident-block topics are matched as topics, not as prose** (closes issue #15 item 1): the ten required entries were a flat substring list, so the consumer bootstrap's wording was pinned character-for-character by a check whose purpose is only that the block still covers its topics. An entry may now be a **literal** — for a command, marker, or identifier, where a rename must fail — or a **pattern**, for prose whose wording may move; the diagnostic says which kind was missing. Only the entry that had demonstrably blocked work is converted. (keel-validation-runner)
- The consumer bootstrap now says Touch is the write boundary **for product files**, so a consumer no longer infers that Touch bounds every write. Naming the record-layer exemption outright still does not fit the block's 1024-byte budget — measured at 3 bytes over — which is what remains of issue #15.
- Version alignment: the npm package, both native plugin manifests, protocol docs, and this changelog share Keel 5.3.1; the OpenSpec dependency pin stays `^1.4.1`.

## 5.3.0 - Touch layering: records are not product, and a repository action is a legal task

Closes issue #8. Minor rather than patch: the write guard's decision changes, and there is a new task mode.

- **A task's own change directory is a record-write layer** (issue #8 example 1, and the five reauthorization cycles in its comment): `keel-core-gates` already required that `keel/guard.json` and paths under the selected change's own `openspec/changes/<change>/` directory not be attributed as outside-Touch failures — they are the authoring artifacts the completion gate is completing against — and `task-complete` implemented exactly that. The write guard did not: it denied writes there, and it hashed that directory's `tasks.md` as authority, so **ticking a checkbox or appending Evidence locked the task out of its own bookkeeping**. Declaring `tasks.md` in Touch, the more careful act, produced the worse experience. The guard now derives the same record prefix from the manifest field it already carries — writes under it are allowed undeclared, and recorded authority entries under it are skipped for drift. **No manifest schema change**, so an older plugin hook against a newer CLI keeps its previous behavior instead of failing closed. (keel-touch-write-guard)
- **Post-completion denial is now stated, not inferred**: byte hashing was also what incidentally stopped a checked task from writing. A checked task now gets no further product writes by an explicit checkbox check, while its own records stay writable so it can finish the Evidence its completion gate requires. (keel-touch-write-guard)
- **Write-time drift detection is narrowed, deliberately.** A hook that cannot compile a capsule cannot tell a contract edit from a record write in the same file. Contract drift inside the change directory — a moved Touch, Verify, Covers, title, or boundary — is now caught by `keel guard status` and `keel gate task-complete`, which compile and compare the fingerprint, rather than at the next write. Authority *outside* the change directory still denies at write time. A new spec scenario states where each is caught. (keel-touch-write-guard)
- **`Mode: repo-action`** (issue #8 example 2): a task whose whole effect is an authorized repository-level action — a commit, a tag — writes no worktree file, so it had no concrete Touch; it is not `diagnose-only`, because it has real side effects needing evidence; and `Touch: none` was accepted for no other mode. The reporter was forced to name a path the task did not write, which then tripped the drift defect above. `repo-action` requires `Touch: none`, carries `must not write product files`, and is the one mode whose prohibitions omit `must not commit`. Push, sync, archive, and marking tasks complete stay prohibited. Whether the action performed was the authorized one remains a Review judgment; the capsule fixes the write posture, and the mode is recorded in the fingerprint. Rejected: `Mode: implementation` with `Touch: none`, since `implementation` means "modify only Touch files" and a mode meaning the opposite should not share its name. (keel-task-capsule)
- Authoring surface: the shipped `keel-spec-driven` tasks template and the resident protocol name the new mode and the record layer. The consumer bootstrap could not carry the record-layer qualifier — it is 1013 bytes against a 1024-byte budget and its wording is a literal required topic — so that gap is tracked as issue #15.
- Version alignment: the npm package, both native plugin manifests, protocol docs, and this changelog share Keel 5.3.0; the OpenSpec dependency pin stays `^1.4.1`.

## 5.2.4 - Keel's own surfaces stop manufacturing work and stop overstating what they know

- An issue tracker can own a follow-up (closes issue #12): `keel-expectation-slice-evidence-gates` requires "a durable follow-up owner" without constraining its form, but the gate enumerated three — a `Discard reason:` prefix, a `keel/archive/…` path, or an existing `openspec/changes/…` artifact — so a project whose declared owner is an issue tracker had to write a local note per finding whose only job was to be a shape the gate recognized. An absolute `http`/`https` reference is now accepted, in both the Review `Findings` check and the `## Expectation Coverage` `Durable owner:` check, and both rejection messages list it. The accepted-form list moved into one shared constant so a form added to one check can no longer be missing from the other. Every form each check accepted before is still accepted, and `keel/HANDOFF.md` is still refused. (keel-core-gates)
- A gate run no longer dirties `git status` (closes issue #11): `task-start` writes `keel/guard.json` and nothing declared it ignorable, so every gate run left an untracked file — and since `task-complete` attributes working-tree paths against Touch, that was a permanent exception the author re-adjudicated at every completion. `keel --install` now scaffolds `keel/.gitignore` declaring it, reusing the scaffold-once strategy so a project's own file is never rewritten. (keel-touch-write-guard)
- A written guard manifest is not observed enforcement (closes issue #14): `Guard: started` means the manifest was written, and authors read it as "writes are being checked now". The two came apart when a session kept plugin state that predated a marketplace switch — the manifest was valid and the PreToolUse hook never ran. Every guard result now carries a second standing statement: the status describes the manifest, enforcement runs as a runtime hook in the host that Keel cannot observe from the repository, and a written manifest is not evidence that any write was checked. This is the same caution `--doctor` already applies when it refuses to infer activation from a target's name. (keel-touch-write-guard)
- Keel's own developers are told to run Keel's own CLI (closes issue #13 item 3): a bare `keel gate …` resolves to the installed package, so when the repository under change *is* Keel, gate commands verify the released CLI rather than the working tree — and the failure mode is a silently stale result, not an error. `keel --doctor` now reports one advisory line, gated on `isKeelSourceRepo` so consuming projects never see it, naming the invocation to use instead including the explicit repository argument the local entry point requires. Issue #13 item 2 stays open. (keel-target-surface-diagnostics)
- Version alignment: the npm package, both native plugin manifests, protocol docs, and this changelog share Keel 5.2.4; the OpenSpec dependency pin stays `^1.4.1`.

## 5.2.3 - diagnostics name their cause; reauthorizing a task no longer needs a hand edit

- No silent compact-to-v3 downgrade (closes issue #7): `requiredFieldProblems` used to pick between the compact v4 and legacy v3 required-field sets with `isConcrete(Verify)`, so a valid v4 task whose `Verify` prose contained angle brackets silently compiled as v3 and reported seven fields the author never intended to use. A non-concrete `Verify` now produces its own `non-concrete-verify` diagnostic naming the offending token and stating that the expanded v3 fields are not required. (keel-task-capsule)
- Documented patterns are writable in task fields: the unfilled-token test now strips inline code spans before looking for a slot — and does so *after* the empty test, so a field whose whole value is one span is not read as empty — covering all four token forms, not only angle brackets. A token left bare outside backticks is still reported. Issue #7's original reproduction goes from 10 problems to 0. (keel-task-capsule)
- Covers and authority diagnostics name their cause (closes issue #7): `unresolved-covers` now states when a requirement name in the target capability contains the ` / ` hierarchy separator, and an over-segmented reference whose first segment names an existing capability fails loudly instead of degrading to an unlinked `legacy-task-reference` with empty Acceptance — which was the worse half of the reported defect, since the *correct* spelling passed silently. `unresolved-authority` now names the exact field and line prefix it wants (`Autonomy boundary:` / `Pre-authorized fallback:`) instead of pointing at `design.md`. (keel-task-capsule)
- Dev-only checks are scoped to Keel's own repository (closes issues #6 and #9): a new `isKeelSourceRepo` predicate — `package.json` name `@christang/keel` **and** `plugins/keel/` present — with a Python mirror in the installer. `keel --doctor` omits the `native plugin source` line in consuming repositories, where it was permanently `missing` with remediation telling an author who had just installed the plugin to install the plugin; and `keel --install` skips the `AGENTS.md` bootstrap write inside Keel's own repository, printing an explicit skip line, instead of overwriting the protocol file and turning the repository red. (keel-target-surface-diagnostics)
- Recording a contract fingerprint is idempotent (closes issue #13 item 1): `keel gate task-start --record` used to refuse whenever the selected task's anchor was anything but the literal `- Contract: pending`, so the recovery path Keel's own drift diagnostics prescribe — "reauthorize through `keel gate task-start`" — required hand-editing the fingerprint line back to `pending` first, a manual step that ran five times in one dogfood session and risks silently revoking another task's authorization. `--record` now replaces the anchor whatever it holds and refuses only when the task has no `- Contract:` line at all. The result reports which of three outcomes occurred — `recorded`, `rerecorded`, `unchanged` — and carries the replaced value; an `unchanged` outcome writes nothing, so gate write-boundedness is tightened rather than loosened, and a re-record landing a different fingerprint warns that evidence produced under the previous contract is stale. (keel-core-gates)
- Version alignment: the npm package, both native plugin manifests, protocol docs, and this changelog share Keel 5.2.3; the OpenSpec dependency pin stays `^1.4.1`.

## 5.2.2 - verification layering: fast inner-loop pre-push vs full gate

- Verification layering (closes issue #5): a new `keel-verification-layering` capability and a "Verification layering" section in both READMEs document splitting verification into a **fast inner-loop check** (seconds, run at a local pre-push and during iteration) and the **full gate** (the complete or slow suite — golden byte-determinism tests, cross-platform runs — run at CI or `keel gate change-close`), so a slow suite never blocks `git push`. Generic pre-push hooks that run the full suite are the trap this convention avoids. (keel-verification-layering)
- Fast-check declaration and opt-in pre-push: projects declare their fast inner-loop command as `fast_check:` in a new `keel/config.yaml` that `keel --install` scaffolds once (a commented template it never overwrites). `keel --install --with-git-hooks` — an explicit, opt-in flag — reads `fast_check`, writes a `#!/bin/sh` `.githooks/pre-push` that runs it, and sets `core.hooksPath` to `.githooks` (per-clone, repo-local, reversible); it refuses when no `fast_check` is declared, a plain `keel --install` never touches git config, and `keel --uninstall`/`--clear` unset `core.hooksPath` only when Keel set it to `.githooks`. `keel --doctor` gains a read-only "Fast pre-push surface" section reporting the `fast_check`, the pre-push hook, and `core.hooksPath`.
- Task-capsule Verify layer tag: a task capsule `Verify` check may carry an optional `(fast)` or `(full)` tag after its `M<n>` label to mark which checks the fast inner loop runs; an untagged check is `full`. The tag is declarative — it never changes check text, Evidence label mapping, or what `change-close` requires — and the compiled capsule emits the layer only for `fast` checks so untagged checks keep a byte-identical shape and fingerprint. (keel-task-capsule)
- Version alignment: the npm package, both native plugin manifests, protocol docs, and this changelog share Keel 5.2.2; the OpenSpec dependency pin stays `^1.4.1`.

## 5.2.0 - pluggable domain lenses; gate authoring-surface and install/runtime honesty

- Domain guidance is now pluggable and user-authored. Keel core keeps only the mechanism — detect a domain signal, load the one matching lens, feed it to alignment/execution/review — while the lens *content* lives in the repository at `keel/lenses/*.md`. Each lens is self-describing: an `Applies when:` header states its trigger signals and an `Execution and review checks` section carries the depth. The `keel-align-expectations`, `keel-tdd-or-test-first`, `keel-debug-failure`, and `keel-review-checklist` skills consult only the matching lens and load nothing when none matches; core no longer bundles any domain knowledge.
- The three former built-in references ship as opt-in templates under `assets/lenses/` (`web`, `hardware`, `hardware-dsl`) and are never installed automatically. New CLI: `keel lenses list` shows shipped templates and installed lenses, and `keel lenses add <name>` scaffolds a template into `keel/lenses/`, refusing to clobber an existing lens without `--force`.
- Renamed the domain vocabulary from "reference/profile" to "lens" across `AGENTS.md`, the keel-spec-driven schema and tasks template (source and repo copies), and the READMEs; the `authoring-continuity` and `domain-lens-scaffold` validators assert the new wording and CLI behavior.
- `keel --doctor` now reports a "Domain lens surface" section — the shipped lens templates as present or incomplete, any lenses installed in `keel/lenses/`, and a migration warning for a leftover v3 `keel-profile-*` skill (reported, left untouched, and never treated as active capability state).
- Gate authoring-surface alignment (closes issue #1 cases B/C/D): `keel gate task-complete` now accepts `Status: done`, and the accepted Review Status vocabulary (`pass, passed, complete, completed, ok, done`) is single-sourced across `gates.js` and `context.js` and documented in the `keel-task-capsule/v1` template and tasks instruction; the `semantic-review` error names the failing field and lists the accepted tokens. The keel-spec-driven tasks template now ships the `## Expectation Coverage` section that `change-close` requires (with a `- None.` default and an `E<n>: … Covered by:` example), and the `finding-owner` gate, template, and instruction enumerate the accepted Findings forms (`none`, a `Discard reason:`/`Discard rationale:` prefix, a `keel/archive/…` path, or an existing `openspec/changes/…` artifact; not HANDOFF); both errors carry a format sample.
- Install and runtime honesty (closes issue #1 case A, #2, #3): keel-* behavioral skills are now honestly reported as plugin-delivered — the dead `dist/`-sourced install path is removed, `keel --help` no longer claims the CLI installs `.claude/skills/keel-*`, and `keel --doctor` reports keel-* as a plugin surface with remediation. A new `keel openspec …` passthrough resolves OpenSpec through Keel, and the apply/archive overlays direct OpenSpec calls through it; `keel --doctor` downgrades `openspec` from `ok` to a warning when only a non-PATH nested shim resolves, naming the failure and the working invocation. The archive overlay now directs `openspec archive --skip-specs` after `/opsx:sync` has already promoted the spec delta (archive is not idempotent) and reminds the author to run `keel guard clear` (the read-only gate never clears the guard).
- Record-compatible template anchor: the keel-spec-driven tasks template emits the literal `- Contract: pending` anchor that `keel gate task-start --record` rewrites in place, so recording a fresh scaffold needs no manual trim.
- Version alignment: the npm package, both native plugin manifests, protocol docs, and this changelog share Keel 5.2.0; the OpenSpec dependency pin stays `^1.4.1`.
