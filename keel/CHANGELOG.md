# Keel Changelog

## 5.15.0 - doctor answers for the repository it names

`keel --doctor` opens with `keel doctor for <repo>` and then answered about a different one. The OpenSpec version it reported as declared was read from `PACKAGE_ROOT/package-lock.json` — the directory Keel itself is installed in — not from the repository on the line above.

- **The check written to expose version drift was dead wherever version drift can happen.** The cross-check added in 5.11.0 (#36) exists to explain a green pipeline and a red worktree that were the same command run against two different programs. Rooting it at Keel's install location made it correct in exactly one arrangement: `node bin/keel.js` from Keel's own source checkout, where the two paths coincide. Measured 2026-08-02 at 5.14.0, a scratch repository pinning `9.9.9` was told `lockfile 1.6.0` — Keel's own pin — and a global install, which ships no lockfile, was told `lockfile unreadable` forever. The declaration is now read from the diagnosed repository, with **no fallback** to `PACKAGE_ROOT`: falling back would reinstate the misattribution and leave the reader unable to tell which case they were in. (keel-target-surface-diagnostics, closes #57)
- **Two versions on one line now have two owners.** `lockfile 1.6.0` named a file the reader was never shown. The line reads `(1.6.0, repo pins 1.6.0)`, and the answering build stays attributed by the path already printed beside it. A reader who sees two numbers can tell which one is theirs without knowing how Keel resolves anything.
- **Declaring nothing and failing to read are different facts.** A repository with no lockfile, and one whose lockfile names no OpenSpec, both *declare* nothing — the ordinary case for any project that does not depend on OpenSpec directly — and are reported as `repo declares no OpenSpec version` with no warning. Only a lockfile that exists and cannot be parsed is a read failure. Collapsing the three would either warn at everyone or hide a real failure.
- **Which `openspec` runs is deliberately unchanged.** #57 proposed rerooting resolution as well. That is declined and recorded as a decision rather than an omission: it would make Keel select a build on the user's behalf, which both `bin/keel.js` and this capability's spec refuse, and would silently change the program every existing consumer runs at upgrade — the same class of surprise this change exists to make visible. `keel openspec --version` reports the same build from Keel's checkout and from a repository declaring something else, and that is asserted, not assumed.
- **The coverage that hid it is the part worth reading.** Every scenario spawns `node <keel-checkout>/bin/keel.js`, so `PACKAGE_ROOT` was Keel's checkout no matter what the working directory was — `source-repo-cli-resolution` already drove doctor from a temp consumer directory and still could not see this. The new scenario separates the two roots by giving the diagnosed repository its own declaration, which needs no second installation and no network. A defect reachable only from outside the source checkout needs a check driven from outside it, or the suite reports facts about an arrangement no user is in.
- **Version alignment**: the npm package, both native plugin manifests, protocol docs, the twelve OpenSpec surface overlays, and this changelog share Keel 5.15.0; the OpenSpec dependency pin stays `^1.4.1`.
- No new dependency. Validator at **124 registered scenarios**, one added: `doctor-reads-the-diagnosed-repository`. Two notes recorded against existing issues rather than folded in: the `Covers` diagnostic reports an unresolvable reference without saying that the second segment is the requirement and the third the scenario (#49, same shape by a different route), and `keel gate task-start --record` no longer causes guard drift as reported in #53.

## 5.14.0 - the sync surface says nothing

`AGENTS.md` gates two actions identically: "`/opsx:sync` and `/opsx:archive` completion is gated by `keel gate change-close --action sync|archive` plus `keel-review-checklist`". Archive's command surface carried a Keel overlay saying so. Sync's carried none.

- **The surface that performs a gated action never named its gate.** `OPENSPEC_OVERLAY_ACTIONS` listed propose, apply, and archive, so `.claude/commands/opsx/sync.md`, `.claude/skills/openspec-sync-specs/SKILL.md`, and the Codex projection received nothing — measured, none of them contained `change-close`, `keel gate`, or `keel openspec`. An agent invoking `/opsx:sync` read generic upstream instructions and was told nothing about the gate that decides whether the sync may complete, nothing about the semantic review, and nothing about invoking OpenSpec off PATH. The protocol stated the requirement in a file the agent may not have been reading at that moment; the surface it *was* reading contradicted it by silence. The sync overlay now says what the archive overlay says for its own action, plus the half archive already documented from the other side — **sync is what promotes the spec delta**, so an archive that follows one uses `--skip-specs`. (keel-openspec-surface-overlay)
- **The doctor label was a hardcoded pair.** `keel --doctor` printed `Keel apply/archive overlay`, which was correct while those were the managed actions and became wrong the moment a third joined them — silently, and while still reporting a healthy count. It is now derived from the managed action list, so an action added to the set cannot be left out of the diagnostic. Overlay markers go from nine to **twelve**. (keel-target-surface-diagnostics)
- **Two things deliberately not done, recorded so they do not read as oversights.** `/opsx:explore` receives no overlay: it reads and reports, reaches no gate, and changes no state, so an overlay there would be governance where there is none. And `sync` is **not** added to the `authorize:` vocabulary — naming the gate that governs an action and deciding whether a repository may authorize it once are separate decisions, and only the first was needed here.
- **Where this leaves #34.** The issue's four layers were largely already delivered and the ledger had gone stale against the releases: L1 (repository-level standing authorization) shipped in **5.5.0**, L2 (decision precedents, with promotion to auto-applicable kept an owner act) shipped in **5.6.0**, and L0's other half — the per-occurrence confirmations a standing authorization removes — shipped in 5.5.0 alongside it, in the apply and archive overlays. This is the piece of L0 that was genuinely missing. Keel still schedules nothing; `/loop`, cron, and CI triggers belong to the host runtime.
- **Version alignment**: the npm package, both native plugin manifests, protocol docs, the twelve OpenSpec surface overlays, and this changelog share Keel 5.14.0; the OpenSpec dependency pin stays `^1.4.1`.
- No new dependency. Validator at **123 registered scenarios**, one added: `sync-surface-overlay`. Two defects found while building it are filed rather than folded in: `keel --uninstall` leaves the overlay block on every OpenSpec surface (#50), and authored task contracts have named a non-existent scenario, file, or behavior four times across three changes (#51).

## 5.13.0 - surfaces that agree with each other

Keel has several surfaces that answer questions about the environment it runs in. Three of them were wrong, and each looked exactly like working — an environment check that is wrong is invisible, because the thing it would have told you is the thing you do not know.

- **`keel --doctor` called an interpreter ok that the suite refuses.** It printed `python3: ok - python3` while `run_python.js` on the same machine printed "no Python 3.10 or newer was found — tried python3 (3.9.6)". Two Keel surfaces, one question, opposite verdicts, and the one a person runs *deliberately to check their environment* was the wrong one. The cause was two implementations: `bin/keel.js` carried its own candidate list that asked only whether a command runs. It now imports the rule from `scripts/run_python.js` instead of restating it, and prints the version it found — `ok` with no number behind it is a claim the reader cannot check, and here it was the wrong claim for as long as the line existed. (keel-target-surface-diagnostics)
- **The interpreter search now tries versioned names.** `python3.13` down to `python3.10`, after the unversioned ones so a machine where `python3` already qualifies is unaffected, and `KEEL_PYTHON` still short-circuits everything. On macOS `python3` is the system 3.9 while Homebrew installs `python3.11` beside it, so the refusal was telling a reader who had already installed a newer Python to install one. **This repository no longer needs `KEEL_PYTHON` set by hand.** The names are generated from the declared minimum, so raising it drops the ones below without a second edit. (closes the L1 layer of #38)
- **`keel context` now names the Keel that produced its answer**, and the resident protocol asks for it beside the protocol version the repository declares. This is the load-bearing change and the reasoning matters more than the line. Measured here: installed plugin **5.7.1**, CLI **5.7.0**, repository protocol **5.12.0**, and no session said anything — because the SessionStart version comparison shipped in *5.9.0*, so the installed plugin does not contain it. **The check that reports a stale runtime is part of the stale runtime**, and its silence is indistinguishable from three versions agreeing, which is exactly what 5.9.0 designed silence to mean. No amount of work inside that mechanism fixes it: an absent mechanism cannot announce itself. What is always current is the repository — the working tree is what every runtime reads — so the comparison is asked for in `AGENTS.md`, explicitly whether or not the hook said anything. (keel-stateless-continuity, closes the L3 layer of #38)
- **`keel gate task-start` warns when two tasks in a change are shaped like one behavior** — an identical Touch set under a red-green strategy — and names the other task. Issue #41 records the case: a split that passed this gate and the Slice Start Gate and was not executable, because the first half was wrong on its own and, once it was right, the second had no honest red left. A **warning, not a `needs-review`**: a genuine vertical split can share files, and there is no way to acknowledge a verdict, so promoting the signal would leave a legitimate split unstartable. `keel-review-checklist` asks the same question at completion, which is the first point at which it is answerable. (keel-core-gates, closes #41)
- **Version alignment**: the npm package, both native plugin manifests, protocol docs, the nine OpenSpec surface overlays, and this changelog share Keel 5.13.0; the OpenSpec dependency pin stays `^1.4.1`.
- No new dependency. Validator at **122 registered scenarios**, three added: `interpreter-surfaces-agree`, `context-names-its-keel`, `task-shape-warning`.

## 5.12.0 - a message that cannot be true

Three surfaces stated something the reader could not act on, and in each the true statement had no form available. A check can be perfectly right about *whether* to fail and still describe the wrong failure — and a reader acting on that sentence goes to a place with no problem in it, which costs more than saying nothing.

- **A finding fixed in its own task had to be recorded as discarded.** This capability's spec says "**WHEN** Review identifies an *unresolved* finding" and `keel-review-checklist` says "each *unresolved* finding with a durable owner"; the implementation applied the requirement to every non-`none` Findings value. So a finding found and repaired inside one task had no accepted form, and in 5.11.0 the text "Closed here; no follow-up is owed" was refused — the only way through the gate was `Discard reason:` for something that had been fixed. The archive recorded a repair as a dismissal. **`Resolved here:` is now the third disposition**, and it must name what proves the fix: an `M<n>` check the task declares, or a repo-relative path that exists. A bare marker is refused, or the new state would be a way out of the other two. So is a tracker reference — a link to work someone else will do is the durable-owner state, not evidence this task did it — and that case is tested *before* the path form, so a URL is not refused by reporting that some substring of it is not a file. `## Invalidates` has carried the same third slot since it shipped, where `Updated by:` names tasks of this change. (keel-core-gates)
- **The criterion is now written down, not left to whichever marker passes.** `AGENTS.md` and both copies of `keel-review-checklist` state all three: fixed here with a check that proves it → `Resolved here:`; still open and owned by someone → `Durable owner:`; considered and deliberately not done → `Discard reason:`. Only the last two are follow-ups. The gap that produced this was never a missing marker alone — an author at the gate picks whichever marker gets through.
- **A stale write-guard manifest denied by giving advice that could not be followed, and granted authority it no longer had.** `taskIsChecked` reads the guarded change's `tasks.md`; once the change is archived that read throws, the miss is read as "not checked", and control reaches the Touch comparison. A write *outside* the archived task's Touch was denied by a message naming a task that cannot be reauthorized; a write *inside* it **passed silently**, so an archived task went on granting write authority. The second half is the worse one and was found by aiming the check inside Touch. The hook now separates a change directory that is gone — a fact `keel guard status` already reports as `drifted` — from a task id missing from a live `tasks.md`, which is a parse miss it must not guess about. The first denies and names `keel guard clear`; the second is unchanged. It still denies: failing closed is what stops `openspec archive` from quietly disabling the guard. (keel-touch-write-guard)
- **The one-message-many-failures assertion shape is now counted.** Issue #43 records it caught by `keel-review-checklist` in three consecutive changes, every time in `scripts/validate_plugin.py`: `if <the run did not work> or <the output lacks a specific thing>:` under one `report(...)` describing only the second operand. Measured: 1069 report-then-return assertion sites, 287 with an `or`, and **75** of the counted shape — so the lint the issue proposed is unshippable as a pass/fail rule, and the three that were caught are the three someone happened to look at. A recorded count fails when the number rises and lists what it measured, and **fails when it falls without the constant being lowered**, because a number that only checks for rises stops being true the first time a site is fixed. **The number bounds a shape and is not a count of defects**; whether a given sentence misleads needs a model and stays in the checklist. The constant was first written as 77, predicted rather than measured, and the check refused it on its first run. (keel-validation-runner, closes #43)
- **Known limits, recorded rather than papered over.** `Findings` is one line of free prose the gate cannot split, so one valid disposition satisfies a block that also holds an unresolved finding — the same limitation the owner forms have had since they shipped. And writing the marker's *name* inside a Findings block counts as using it, so a finding that discusses the disposition must name it in words instead of quoting it. Both are in the change's design.md with the reasoning; fixing either means one-finding-per-line Findings, which is a protocol change with its own cost.
- **Version alignment**: the npm package, both native plugin manifests, protocol docs, the nine OpenSpec surface overlays, and this changelog share Keel 5.12.0; the OpenSpec dependency pin stays `^1.4.1`.
- No new dependency. Validator at **119 registered scenarios**, three added: `findings-resolved-here`, `guard-stale-manifest`, `assertion-shape-count`. All three contributed zero counted assertion sites, which is why the recorded number is the same 75 the file carried before this change.

## 5.11.0 - the name is not the thing

Five checks compared names instead of things, and each failed silently while looking exactly like a check that works. The write guard is the one that matters, because it is the only mechanism that enforces anything at write time; everything else in Keel's write discipline is convention the guard is supposed to make real.

- **The write guard could be bypassed by a symlinked path.** Containment was `path.relative(repo, path.resolve(repo, target))`, and `path.resolve` never follows a symbolic link while the `cwd` the operating system reports usually already has. Measured against a repository reached through a link, manifest active, Touch allowing `src/allowed.js`: `<real>/src/denied.js` was **denied** and `<symlink>/src/denied.js` was **allowed**. The same file. The hook returned before reading the manifest at all. On macOS `/tmp` is such a link by default, and any repository reached through one — a symlinked checkout, a home-directory link — was affected on every platform. Both sides are now resolved, from the nearest existing ancestor because a guarded write is usually a file about to be created. **A write that passed yesterday through a symlinked path is denied today**; that is the fix, and it can land mid-session. (keel-touch-write-guard)
- **`src/core/helper.js` had the mirror image**, calling a path inside the worktree external, so the helper wrote its baseline into the repository it had just promised not to touch. That is why `native-helper-read-only` had been red on macOS and green on Linux CI. It passes now without being edited: the defect it was reporting was real.
- **A Chinese filename in Touch could not complete.** Git octal-escapes any path holding a non-ASCII byte and quotes it; `gitPaths` then ran `line.slice(3).trim().replace(/\\/g, "/")`, which left the quote attached and turned `\346` into `/346`. Paths are now read with `--porcelain=v1 -z` and `--name-only -z`, which emit raw bytes for non-ASCII, spaces, quotes and backslashes alike — measured, because `core.quotepath=false` removes the octal and still quotes the rest, and `status` and `diff` do not agree on which cases they quote. A flag rather than a repository setting, so the answer does not depend on how a repository happens to be configured. (keel-core-gates, closes #40)
- **Three separator rewrites were removed, not one.** `gitPaths` corrupted every escape it read; `pathAllowed` rewrote the Touch entry; `scopeEvidence` rewrote the candidate. The last two cancelled each other for a filename holding a literal backslash, which is why nothing had ever surfaced — while a Touch entry naming `src/back/slash.js` silently admitted a changed `src/back\slash.js` the task never declared. Git emits forward slashes on every platform, so all three normalized a separator that never arrives.
- **The suite ran on whatever interpreter and OpenSpec answered.** `run_python.js` accepted any interpreter whose `--version` exited zero, so macOS system Python 3.9 ran a suite needing 3.10 and failed ten scenarios with messages naming ten unrelated features; it now requires 3.10 and names every candidate with the version it reported. `keel` resolved `openspec` from PATH in silence when `node_modules` was absent, so this repository validated against 1.4.1 while its lockfile resolves 1.6.0. `keel doctor` now names the resolved command and both versions, and the suite fails naming both when they differ. Keel reports which build answered and selects none. (keel-target-surface-diagnostics, closes #36)
- **The template fixture was malforming the template.** `fill_template_slots` replaced every HTML comment with slot text, including the own-line author instruction the spec template gained in `ed1388d` — the change whose own task asserted that a requirement written from this template validates. The instruction became a bare paragraph above `The system SHALL …`, and `openspec validate` reported the requirement as lacking a modal verb. One rule for both templates now, and a new assertion that fails at the fixture rather than at the template.
- **Version alignment**: the npm package, both native plugin manifests, protocol docs, the nine OpenSpec surface overlays, and this changelog share Keel 5.11.0; the OpenSpec dependency pin stays `^1.4.1`.
- No new dependency. Validator at **116 registered scenarios**, three added: `guard-containment-is-resolved`, `git-paths-carry-no-escaping`, `runtime-versions-are-checked`. `npm test` is green with no exceptions for the first time since the move to macOS.

## 5.10.0 - the anchor is compared, not counted

The contract anchor exists to answer one question: did the task's authority change while it was being implemented? `keel context` compared it. `keel guard status` compared it. `keel gate task-complete` — named in the same protocol sentence, and the gate that decides whether a task is finished — checked only that sixty-four hex characters were present, then discarded the value.

- **A well-formed but non-matching anchor now fails where it passed.** Measured before the fix: a task whose Touch was rewritten from `src/feature.js` to `src/DRIFTED.js` after recording passed `task-complete`, and the gate's own JSON printed the recompiled `2ca3e03d…` beside the recorded `241984…` in the same payload. It held both numbers and did not compare them. An anchor of sixty-four zeros passed with an empty `problems` array. Both now fail with `contract-drift`. **The recovery is `keel gate task-start --record`**, which rewrites the anchor in place; the refusal names it, names both fingerprints, and says that execution evidence produced under the previous contract is stale — the same sentence `--record` already emitted as a warning when it replaced a different value. (keel-core-gates)
- **`change-close` compares too, and refuses a checked task that recorded no anchor.** Issue #37 named `task-complete`; stopping there would have left the entire window between the last checkbox and the archive open at the one gate whose job is closing it, and `change-close` already compiled every task's capsule, so the comparison was free. The missing-anchor half is the stricter part and the part most likely to be met on upgrade: without it the comparison is bypassed by deleting a line. Its diagnostic is written for the close rather than reused from completion, whose remedy ends "then complete it" and would send the reader of an already-checked task somewhere with no problem in it.
- **Archived changes are unaffected.** Change discovery excludes the archive tree, so no gate can select an archived change and no archived anchor is ever recompiled. That boundary was already stated in `keel-core-gates` — an archived task's capsule names source paths under a directory that archiving renamed, so it recompiles to a different value by design — and this change depends on it rather than moving it.
- **The `keel-task-capsule/v1` prefix stays optional.** A fingerprint is a digest over the canonical capsule serialization, so a value that matches could only have come from the schema that produced it; requiring the prefix would add a second failure mode for hand-written anchors while proving nothing the comparison does not. It earns its place inside the drift message, where naming which schema compiled the current value is what separates contract drift from a capsule-format change. This answers the adjacent question issue #37 raised rather than deferring it.
- **Two shipped requirements stopped being false.** `keel-touch-write-guard` said a contract edit is caught because `task-complete` "refuses the recorded anchor, because both compile the capsule and compare it"; `keel-core-gates` said a recorded anchor "is compared against the recompiled fingerprint". Neither was true. This is the defect class 5.7.1 named — a check whose form is valid and whose content is never examined — sitting inside the mechanism the rest of the protocol's drift detection rests on.
- **The scenario that claimed to prove the comparison was itself the proof it never ran.** `completion-requires-a-recorded-anchor` recorded the fingerprint of one change and wrote it into a different change's `tasks.md`; those values differ, because a compiled capsule names its own source paths. It passed anyway. It now records against the change it completes and asserts that the foreign fingerprint is refused. Three more shipping fixtures were closing changes whose checked tasks had no anchor, or editing Touch without reauthorizing — each was corrected to what an author does, not accommodated.
- **Version alignment**: the npm package, both native plugin manifests, protocol docs, the nine OpenSpec surface overlays, and this changelog share Keel 5.10.0; the OpenSpec dependency pin stays `^1.4.1`.
- No new dependency, and no new runtime cost: both gates already compiled the value they were failing to compare. Validator at **113 registered scenarios**, one added: `contract-anchor-is-compared`.

## 5.9.0 - the runtime says which version it is

Every answer Keel gives rests on its checks being local, deterministic, and reproducible. It has never said which build produced them. The SessionStart projection now compares the plugin executing the hook, the CLI it invokes, and the protocol version the repository stamped into its managed block, and reports a disagreement on both channels.

- **It reports, and does not manage.** The obvious next sentence after "your plugin is stale" is "so let me update it", and the host already owns that command — which is exactly why this is where 5.8.0's scope rule was most tempting to break. The remedy named is `claude plugin update`, and only for the target whose manifest was actually read; an unprobed target gets a description rather than an invented command line. Naming is not running, and that is checked rather than asserted: a preload patches `child_process` inside the hook's own process, and the log holds exactly the two `keel` invocations the hook already made. Those two are also the recorder's positive control — a recorder that had stopped working would leave an empty log and fail the same count. (keel-native-runtime-projection, keel-surface-evolution-policy)
- **Silence when aligned.** A matching set adds nothing. This diverges from issue #38's own wording, which proposed a line naming all three versions every session; the divergence is deliberate, and the cost is accepted — confirming which build is running is now a question you ask, and `keel --version` answers it. A line printed every session stops being read weeks before the session it mattered in.
- **Missing is not mismatched.** A repository with no managed block is a normal state, not a fault. An undiscoverable version never produces a line on its own, and fewer than two readable versions is nothing to compare rather than agreement. When one appears beside a real disagreement it is named as `undiscovered, not compared`, so a partial comparison cannot be read as a complete one.
- **The comparison is exact string equality, not semantic ordering.** The question is whether the runtime is the protocol, and any difference answers it. Ordering would invite a judgement about which direction is acceptable — a newer plugin than protocol, an older CLI than plugin — and every such judgement is a rule that has to be right.
- **The report names the restart requirement**, because a session's hooks are fixed at session start. Without that sentence the reader updates the plugin, sees the same warning, and concludes the check is broken. That is not hypothetical: it is what happened on 2026-08-01, when `claude plugin update` succeeded and the old hook kept denying a write the new record layer permits until the session was restarted.
- **No new mechanism.** The hook already ran `keel --version` and parsed it only far enough to check the major number, then discarded the rest; it already emitted both channels. The added cost is one `plugin.json` read and one regex, which matters because this runs on every session including post-compaction reinjection, under `KEEL_HOOK_TIMEOUT_MS`. Nothing reaches the network — Keel compares what is installed against what the repository declares, and never asks what the newest release is.
- **It caught real drift on its first live run**, on the machine it was written on: plugin 5.8.0, CLI 5.7.0, protocol 5.8.0. The globally installed CLI was a release behind and nothing had said so.
- **Two tasks were merged mid-change because the split could not be executed.** Implementing "report a disagreement" without "missing is not mismatched" left `protocol null` in the projection of every repository with no managed block, breaking a shipping scenario; and once it was implemented correctly, the second task had no honest red left to record. The guard hard-stopped the contract edit and `task-start` reauthorized at a new fingerprint, which is the protocol working — but nothing in authoring flagged that two tasks sharing one Touch set were one behavior, and that is #41.
- **Version alignment**: the npm package, both native plugin manifests, protocol docs, the nine OpenSpec surface overlays, and this changelog share Keel 5.9.0; the OpenSpec dependency pin stays `^1.4.1`.
- No new dependency. Validator at **112 registered scenarios**, one added: `runtime-version-drift`, covering the comparison, the silence, the partial report, and the spawn log. 110 pass here; the two that do not are the local-environment failures owned by #36. (Earlier entries counted passes rather than registrations, which is why this number jumps by three.)

## 5.8.0 - declare who runs the task

A repository can say that a task may be implemented by a subagent, and at which capability tier. The interesting part is what did not have to be built.

- **The containment was verified, not written.** A probe on 2026-08-01 spawned a subagent under a live guard manifest: its write outside `Touch` was denied with the byte-identical message the current agent receives, and its write inside `Touch` succeeded. That second half is the positive control — without it the probe would have shown only that subagents cannot write at all. The manifest scopes a repository and a task, never the identity of the process writing, so delegation needed a declaration rather than a mechanism. The probe is now a permanent scenario, because nothing in the hook mentions delegation and a future reader has no local signal that it matters. (keel-authorized-delegation, keel-touch-write-guard)
- **A capability the target runtime already provides is not Keel's to build.** The surface-evolution policy carried the procedures serving this rule — do not cede a maintained surface without a coverage report, do not integrate a host surface without recorded design authority — and never the rule itself. A procedure without its rule is followed where it was written and nowhere else, which is exactly why this change proposed a write-capable brief module before anyone asked whether the host already carried one. It is not built; the `subagent-start` projection Keel already publishes carries the write boundary and the tier instead. The requirement separates a *conflicting* surface from a duplicating one: duplication wastes effort, while a surface contradicting the runtime leaves the agent no correct action. (keel-surface-evolution-policy)
- **The tier is declared, never inferred.** `delegation:` in `keel/config.yaml` over a closed vocabulary — `routine`, `standard`, `deep` — inherited by a task that authored no `Delegation:`, with the capsule naming the file as the source. A tier names the capability the work requires rather than a guess at its size, because a tier named for size authorizes precisely the judgement 5.7.0 refused for triage. Keel names no model: one is target-specific and expires at the next release, in a file whose point is to still be correct after both.
- **`authorize:` is deliberately not extended.** Its four names each change durable repository or outside-world state; delegation only routes execution. A fifth name would redefine a closed set whose value is being narrow enough to read at a glance — and the aimed red shows the cost concretely, since with `delegate` inside it `authorize: [commit, delegate]` grants both.
- **A delegate's result is a claim, and the current agent re-runs every check.** This is structural rather than cautious: the before/after byte-identity verification that lets a read-only helper's return be trusted cannot apply to something authorized to write, so re-running is what restores the property it provided. It is also what makes a wrong tier cost a retry instead of a bad merge.
- **Delegation is refused with no active guard manifest.** An absent manifest passes every write through silently and looks identical on screen to one the guard checked, so the condition is answered before a delegate starts rather than inferred from what it did afterwards.
- **The single-task goal path admits a delegate, and its invariant is restated rather than removed** — the current agent is the sole holder of *write authority*. The invariant's purpose was never that one process performs the writes; it was that one party is answerable for them. The delegation fields sit inside the 4,000-character activation budget, so an overflow refuses rather than trimming.
- **Keel cannot observe which model ran and does not pretend to**, in the same shape 5.7.0 states that it cannot verify a human applied a triage label. Established from the Claude Code runtime binary rather than its documentation: `SubagentStart` and `SubagentStop` exist, and neither payload carries a model identifier. The one indirect route is refused rather than unavailable — reading a native transcript would contradict `keel-stateless-continuity`.

## 5.7.1 - a valid reference is not a full one

Closes **#33** and the second instance recorded on it. Two failures in this repository share one shape: a check whose **form** is valid while its **content** is empty or wrong.

- **A durable owner declared as a URL must already carry its content at the moment it is cited.** A valid link to an empty issue owns nothing. Caught empirically in 5.4.0, where expectation E5 cited issue #32 as the place a rejected proposal's reasoning was recorded while `gh issue view 32` returned zero comments — the claim was false when both deterministic gates returned `pass`, and it was noticed only because someone happened to look.
- **A failure message must name the actual cause.** The trigger to watch for is one condition guarding two distinct failures: `if result is None or result["status"] != expected` reports the first failure's message when the second one happened, sending a reader somewhere with no problem in it. Reproduced in 5.7.0's own new triage scenario — in a repository that fixed this class in 5.2.3, by the agent that had just read the rule. A fix that corrects instances without leaving a recurrence guard has a half-life, and this is the guard.
- **Both stay semantic-review checks, and the spec now says why they must not become gate checks.** A gate that fetched a reference would stop being local and offline, failing differently on a plane than in CI; judging whether a sentence misleads needs a model. `keel-expectation-slice-evidence-gates` already stated that a gate "cannot confirm that a URL resolves" and then assigned the resulting check to nobody — this names the owner rather than adding a mechanism.
- Neither check judges quality. Both concern whether content is present and whether a stated cause is the real one, never whether reasoning is sound or wording is elegant.
- **This change was admitted to an unattended run** by the `auto` label on issue #33, evaluated by `keel triage`. Admission started the work and decided nothing in it: the change went through authoring, both gates, and semantic review exactly as any other, and it ends at a pull request rather than a merge.
- No behavior change to any gate, command, or config surface. Validator at **101 scenarios**.

## 5.7.0 - declare what may run unattended

Third layer of **#34**. 5.5.0 declared which *actions* may proceed; 5.6.0 recorded *why decisions went the way they did*. Neither said which **work** may start, so an unattended run had nothing to consult at the moment it mattered most — an issue arrives and something must decide whether it becomes a change at all.

- **A repository declares which issues may start work unattended**, as a label allowlist under `triage:` in `keel/config.yaml`. `keel triage --labels <labels>` evaluates it and returns admit or refuse with a reason. Absent declaration admits nothing. (keel-unattended-triage)
- **That decision could not have been reached any other way, and the reason is worth stating.** "Should this issue be done" sits in the materiality categories that require asking, and 5.6.0's precedent rules forbid a precedent from moving a decision out of that list — deliberately, because a system that can learn its way out of asking drifts toward asking nothing at a rate nobody notices. So no accumulation of triage history can make this automatic. The only route is the one standing authorization already established: the owner declares it, and a declaration *is* the decision rather than a claim about what the owner would decide. The precedent spec now says so explicitly, since a store of past triage decisions is the most tempting thing a reader would try to apply.
- **A label is the unit on purpose.** A person applies one to a specific issue, so the policy admits a class the owner curates one issue at a time. The alternatives were considered and refused: author allowlists authorize a person rather than a piece of work; title or body keywords authorize whatever anyone chooses to type; and size or complexity estimates authorize the agent's guess about difficulty, which is exactly the judgement that should not be automated. Keel cannot verify a human applied the label and does not pretend to — a repository whose automation can label issues has a broader policy than it appears.
- **Keel never fetches the issue.** The agent reads it with `gh` and passes the labels in. A check that reaches the network trades the local, offline, deterministic evaluation that makes every other Keel answer worth trusting, and it also makes the check untestable without a network. Proven under a preload that makes every network primitive throw, with the same inputs asserted to give the same answer twice.
- **Admission answers "may this begin" and nothing after it.** Every gate, evidence requirement, Review, and the write guard behave exactly as they do for work nobody triaged — asserted by comparing a declaring repository against an identical silent one, with a positive control that was itself verified to fire.
- **A run may open a pull request and may not merge one.** No configuration key grants a merge. Merging is where an unreviewed decision becomes the project's history, and a pull request is what makes an unattended run reviewable after the fact.
- **Stopping at a material decision is the designed boundary, not a failure.** The protocol says so, and says not to widen the triage policy to stop it happening — without that sentence, "it keeps stopping" turns into exactly the pressure this design exists to resist.
- **Keel schedules nothing.** `/loop`, cron, and CI triggers belong to the host runtime; claiming otherwise would be asserting a capability Keel does not have. This is a spec requirement rather than a disclaimer in prose.
- This repository declares no triage policy of its own. Doing so would start unattended work on its own issues, which is its owner's decision rather than a default worth shipping — so unlike 5.5.0 and 5.6.0, this interface ships fixture-tested rather than in use, and that gap is recorded on #34.
- No behavior change without a declaration, and nothing to do on upgrade. No new dependency.
- Validator at **100 scenarios**, with three added for the declaration, its inertness, and the boundary.

## 5.6.0 - the reasoning is the part that transfers

Second layer of **#34**. 5.5.0 gave a repository somewhere to record *that* an action is authorized. This gives it somewhere to record *why a decision went the way it did* — the part that would generalise to a decision not yet seen, and the part that a context reset destroys completely.

- **A repository can point Keel at a directory of precedents** by declaring `precedents:` in `keel/config.yaml`. Keel bundles none and creates none, exactly as it bundles no domain lens. The path is declarable rather than fixed — unlike `keel/lenses/`, which is necessarily in-repo because a lens describes that repository's domain — so one store outside your repositories can serve all of them. (keel-decision-precedent)
- **The mechanism is the one Keel already had.** Domain lenses were already user-authored markdown in a declared directory, self-describing, loaded only on match, with nothing shipped. Precedents are a sibling of that surface rather than a new invention; they differ in two ways that made sharing the file space wrong — they accumulate over time, and each carries a promotion state a lens has no concept of.
- **A precedent must carry its rationale, and one that carries only a conclusion is reported incomplete.** "Chose A" applies only to the situation literally recorded; "chose A because B fails offline" can be applied to a case nobody has seen — and, just as importantly, recognised as *not* applying when the new case is online. The check is structural: Keel reports the field's presence and never claims to have judged the reasoning.
- **Three rules, all of them chosen against a specific failure.** A precedent is cited exactly where it replaced a question the user would otherwise have been asked, so a citation always marks a decision made in their place rather than running commentary. Promotion from `recorded` to `authorized` happens only when the user accepts a proposal — never by a usage count, because a threshold crosses with nobody watching. And a precedent answers a *recurrence* within a materiality category; it can never move a decision out of the categories that require asking, or the system drifts toward asking nothing at a rate too slow to notice.
- **A precedent informs a decision and never substitutes for a proof.** Gates, evidence, Review, and the write guard are untouched. Asserted the same way 5.5.0 asserted it for standing authorization: compare a store-declaring repository against an identical silent one, with a positive control that first proves the two actually differ — a store that silently failed to load would make every such comparison trivially equal.
- **SessionStart carries a pointer, never a body.** Counts and freshness only. The store grows without bound while the precedents relevant to any one session are a small subset, and the hook pays its cost on every session including post-compaction reinjection. The projection is checked against a sentinel string planted in the precedent bodies, so a leak fails loudly rather than being caught by a length limit.
- **A declared store that is not there behaves exactly as no declaration** — no error, no changed exit code. This repository declares a private store, so that path is what every other clone and every CI run lands in, and it is tested by actually removing the store rather than by reasoning that the code handles it.
- Three documents enumerated what `keel/config.yaml` holds or which surfaces are user-authored. All now include the precedent store; the config header's "two independent declarations" was written one release ago and is now three.
- No behavior change without a declaration, and nothing to do on upgrade. No new dependency.
- Validator at **97 scenarios**, with four added for the declaration, its inertness, the projection pointer, and the three rules.

## 5.5.0 - authorize once, in a file

First layer of **#34**, which asked why execution keeps stopping for confirmations the owner already decided.

- **A repository can now declare standing authorization once**, in `keel/config.yaml`, over a closed vocabulary: `commit`, `push`, `release`, `archive`. Before this there was nowhere to put such a decision — the task capsule had the vocabulary (`Autonomy boundary:` / `Pre-authorized fallback:`) but no repository-level default to inherit, so a permission granted in conversation died at the next `/clear` and was asked for again. (keel-standing-authorization)
- **A task inherits the declaration only where it authored nothing.** A task that declares its own `Autonomy boundary:` keeps it untouched; a repository-wide default that could overwrite a task's stated boundary would make the capsule unreadable on its own. The compiled capsule names `keel/config.yaml` as the source of any entry it supplied, so an inherited authorization is never mistaken for one the task decided. (keel-task-capsule)
- **It authorizes the action and never the proof.** Every gate, evidence requirement, semantic Review, and the write guard run exactly as before: `keel gate task-complete` returns the same status, the same problem set, and the same failure text whether or not anything is declared. This is asserted, not asserted-to — the test compares an authorizing repository against an identical silent one and first proves the two actually differ, because a declaration that failed to reach the capsule would make every comparison trivially equal.
- **It is not a trigger.** `keel context` returns the same selection and next action either way. Nothing schedules itself and no next task is chosen for you; the declaration removes a confirmation, not the step that reaches the action.
- **An unrecognized action name is reported with the accepted set and authorizes nothing** — including the valid entries beside it. Silently dropping a typo would leave the author believing they had granted something they had not.
- **The apply and archive overlays now route confirmations to the declaration** instead of asking again, and say in the same breath that an undeclared action still requires today's confirmation and that authorization never substitutes for a gate. A repository that declares nothing sees no change on any surface.
- Four documents stated the hard-stop default and the unauthorized-action list unconditionally — the compact-task template and the schema, in both their source and installed copies, plus the resident protocol. All now state the condition. `keel/config.yaml`'s own header no longer introduces the file as if `fast_check` were its only key.
- No behavior change without a declaration: an absent, blockless, or empty `authorize:` block leaves every action hard-stop, which is exactly 5.4.0's behavior. Nothing to do on upgrade.
- No new dependency. The reader is line-oriented like `fast_check`'s, in a new `src/core/config.js` shared by the CLI and capsule compilation; the package still carries one runtime dependency and zero devDependencies.

## 5.4.0 - the projection reaches the human

Closes **#32**, whose analysis of the available channels was correct when written and wrong for Claude Code 2.1.220.

- **The SessionStart projection now reaches the person, not only the agent.** It was delivered entirely through `additionalContext`, which the host injects into the model and never renders, so the only path to the user was an instruction asking the agent to restate it — which requires the agent to comply and requires the user to send a first message. Someone who opened a session and waited was told nothing, which is exactly how the issue was reported. (keel-native-runtime-projection)
- **The channel already existed and Keel was not using it.** The host's common hook-output schema declares `systemMessage` beside `continue`, `suppressOutput`, and `decision`, and consumes it in the same handler as `additionalContext` with no gating by event. That proposal is **not** built; its author withdrew it in favour of this.

A fallback that stays silent to the human is indistinguishable from a hook that never ran, which is the failure this change exists to close.
- **Both channels ship, and neither is redundant.** The host's line says what the state is; the instruction to restate it is what surfaces the state the agent is actually working from. Only the second can expose the two disagreeing — as one did during development, when the projection selected a task that `tasks.md` already showed complete.
- **An opt-in panel**, off by default: `KEEL_SESSION_PANEL=1` frames the message in a titled box with a Keel mark, sized to its content so a long change name widens the frame instead of being truncated. The default single line is unchanged and carries the same information, which is enforced rather than intended — the tests strip the frame and the mark away and require the status and next command to survive.
- Three documents asserted that the projection reaches only the agent. All three now state both channels and why the agent still restates the projection; the requirement they justified survives for a different reason.
- No behavior change for a host that does not recognise `systemMessage`: the field is optional in the host's own schema, and the `additionalContext` payload is byte-identical to 5.3.9's. Nothing to do on upgrade.

## 5.3.8 - the gate reads what it promises

Closes **#29** and **#30**. Both are cases where a structure was read differently from how it is documented, and the gap stayed invisible until it misfired.

- **A task body now ends at the next task or the next `##` heading** (closes #29). `parseTasks` gave a task every line up to the next task or end of file, and a heading did not stop it, so `## Invalidates` and `## Expectation Coverage` were appended to whichever field was open last — the `Evidence`, in every shipped template. A task group heading leaked into the preceding task's last field the same way. (keel-task-capsule)
- **That also dissolves the contradiction, rather than papering over it.** `invalidation-phrase` requires the searchable wording in double quotes; the concreteness test rejects an angle-bracket slot outside inline code. Once the section is no longer read as Evidence, the same text satisfies both — the two checks were never in conflict, the parser only made them appear so. A control fixture asserts the phrase check was not simply weakened. This mattered most under #16, which requires an invalidation to quote exactly the kind of prose that carries such tokens.

- **`task-complete` refuses a task that recorded no start fingerprint** (closes #30). `anchoredFingerprint` returns null for a non-digest anchor and completion then skipped the comparison entirely, so a task with `Contract: pending` passed with zero problems. (keel-core-gates)
- The missing anchor joins a named task's problem list rather than short-circuiting it, so it cannot hide everything else the task has wrong — the masking shape 5.3.7 removed twice. Selection ambiguity still short-circuits, because there the gate does not know which task the caller meant.
- The change broke 11 existing validator scenarios, every one a fixture that completed a task without ever starting it. That is the behavior being introduced, not collateral damage; each now runs the real loop.

The step was already the documented loop in `AGENTS.md` and the bootstrap block; it is now enforced rather than assumed.

## 5.3.7 - the diagnostic and the template both name what to do

### Diagnostics name the cause (closes #28 items 4, 5, 6, 9)

All four are gate diagnostics that knew what was wrong and reported something else. Three of the changes **widen** what is accepted; the fourth adds one refusal, described below.

- **Citing a resolved question no longer re-opens it** (closes #28 item 9). The question scan ran over the whole `Covers` field, so a task whose entry read `F13 (Q1 resolved: …)` was told to declare a pre-authorized fallback for a question it does not carry. (Fixed in the next release, which ends a task body at the next `##` heading; the two checks were never in conflict.)
### Following the template no longer guarantees a refusal (closes #28 items 2, 3, 7)

- **A requirement written from the spec template validates on first run** (closes #28 item 7). The template's requirement body was the comment `<!-- requirement text -->` with no modal verb, and `openspec validate` requires `SHALL` or `MUST`, so the reporter's 16 requirements produced 16 errors. The body now carries the literal line `The system SHALL` before its behavior slot.

The scenarios fill each template's author-facing slots and hand the result to the tool that consumes it — the real `openspec validate`, and `task-start` over all three template groups. ## 5.3.5 - the suite stops writing to the repository it validates

Closes issue #26. No product behavior changes; `keel --install` against the source repository is still supported. What changes is that the *test* stops calling it there.

- **A validation run now leaves the working tree byte-identical** (closes #26). `source-repo-bootstrap-skip` ran a real `keel --install --target claude` against the repository root to prove that install skips `AGENTS.md` in Keel's own repo. It asserted the skip and nothing else, so the install's overlay refresh silently rewrote the `.claude/` markers and `CLAUDE.md` every time. The scenario now builds a fixture carrying the two signals `is_keel_source_repo` actually reads — a `package.json` named `@christang/keel` and a `plugins/keel/` directory — and additionally fails naming any file the install rewrote without announcing it, which is the assertion whose absence was the real defect. (keel-validation-runner)
- **The worse half, and the reason this is not just tidiness.** The marker-alignment check added in 5.3.4 was green on the `.claude/` side *because the suite wrote those markers*, not because anything guaranteed them. One run demonstrates both fixes at once: rolling a `.claude/` marker back to `5.3.3` and running `npm test` now leaves it at `5.3.3` **and fails** with `shipped version marker disagrees with the package version 5.3.4`. Before, the same rollback ended the run repaired and green. A check whose input its own run produces cannot fail, however green it reports.
- A baseline check refuses any scenario passing the repository root to a mutating Keel command, naming file, line, and invocation. It keys on the subcommand rather than on the root, so the many read-only invocations — `--help`, `--version`, `--doctor`, `gate …` — stay legal. The sweep confirmed the relocated call was the only offender.
- This is the third form in the family issue #18 opened. First: a check that compares nothing, because its root does not exist. Second: a check comparing a directory against itself (`dist_root = source_root`). Third: a check kept green by a side effect of the same run. The shared question that catches all three — **can this assertion's input be changed by the process running it?**
- Filed #27 from the same investigation: `keel --check` prints an empty dry-run plan while `keel --install` reports `refreshed=1` and rewrites a file, because the overlay refresh runs outside the action plan. A dry-run that under-reports is why this side effect stayed invisible to anyone reading the plan.
- Validator stays at **80 scenarios**.

## 5.3.4 - refusals that name what they accept, and checks that actually run

Closes issues #15, #18, #20, #21, #22, and #23. Both gate changes **widen** what is accepted, so every currently passing tasks.md keeps passing; two narrowings are called out below.

### Statements that stopped being true (closes #15, #22, #23)

- **The consumer bootstrap now names the record-write exemption** (closes #15). It said Touch is the write boundary "for product files" and left the reader to infer what the qualifier excluded; the inference actually made is that `tasks.md` belongs in Touch, the trap #8 reported. It now says "Touch bounds product writes; the change's own dir is exempt." Room was made by listing one guard opt-out instead of two — `keel guard clear` is unchanged as a command, it just no longer costs resident bytes — so the block **shrank** to 1012 against an unchanged 1024-byte budget. (keel-openspec-surface-overlay)
- **Live specs stopped requiring versions that already shipped** (closes #22). A sweep found **seven** version-pinned statements across two capabilities — `3.0.0`, `4.0.0`, a forbidden `2.7.0` — all false at 5.3.4, one of them asking for version markers on the retired `dist/` tree. The requirement naming a version is replaced by the invariant it was reaching for: every shipped marker agrees with the package version. Zero version literals remain in live specs.
- **That invariant is now enforced rather than asserted** (closes #23). Baseline validation walks every shipped `.md`/`.json`, extracts each `keel:… version=` marker, and fails naming the file when one disagrees. The marker list is discovered, not declared, so it cannot become the next thing to fall behind, and `bump_version.js` sweeps the same set — all twelve markers move in one step instead of `.codex/` waiting for someone to remember.
- **Correction to the 5.3.3-era account of that drift.** It was recorded as "the release bump carries `.claude/` along and leaves `.codex/` behind". That was wrong: `bump_version.js` never touched either. The validator scenario `source-repo-bootstrap-skip` runs a real `keel --install --target claude` against the repository root, and that install silently refreshed the Claude overlays. So it was "a test installs one target and nothing installs the other" — and a test mutating the working tree is its own defect, filed as **#26**.
- **The contract-anchor guarantee states its bound** (closes #24 as documented). An anchor is reverifiable while its change is live; once archived it is a historical record. The boundary turned out to be **enforced** rather than merely undocumented — the gates reject a change name under `archive/`, so no CLI path recompiles an archived task. **Second narrowing:** `bump_version.js` compared an LF changelog header against a CRLF working copy and aborted after every marker had been written, leaving the repository half-bumped; fixed.

### A regression check can stand on its own (closes #21)

- **A red-green strategy no longer demands a red that cannot exist.** It required `.red` and `.green` for every `M<n>`, but a regression check asserts that something already green is still green and has no honest red. The author's only options were to fabricate one or to fold the guard into the behavior check — this repository took the fold twice while shipping 5.3.2 and 5.3.3, and recorded both times that it cost expressiveness. The gate's shape was deciding the task's decomposition. (keel-task-capsule)
- An `M<n>` may now carry a comma-separated tag set after its label: `fast`, `full`, and the new `regression`. The set form exists because a regression check is exactly the kind you want in the fast pre-push loop, so `M3 (fast, regression): …` had to be sayable.
- Two properties keep the tag from becoming an escape hatch. A red-green strategy must retain **at least one untagged check**, refused at task-start as `regression-only-strategy`. And the tag lands in the compiled capsule, so the exemption is a visible term of the contract rather than a silent skip. A tagged check is exempt from red-green, **not** from evidence: its bare `M<n>` entry is still required.
- Untagged checks emit no tag key at all, following the 5.2.2 layer-tag precedent, so **no recorded contract fingerprint moves**. Proven on real tasks rather than fixtures: this change's own 1.1 and 3.1 recompile to the values captured before any of the code existed, and emitting the key unconditionally moves both.

### A durable owner can be a file the repository keeps (closes #20)

- **`Durable owner:` accepted three prefixes and the refusal said only "lacks a durable owner".** An author pointing at their own ledger — `openspec/FOLLOWUP.md` in the report — was told the entry had no owner while it plainly named one, and could only find the boundary by trial. (keel-expectation-slice-evidence-gates)
- The whitelist verified nothing: a gate runs without network, so it cannot resolve a URL, and it never confirmed a `keel/archive/…` path either. A repo-relative path is the one form it *can* check, which made it the least defensible thing to refuse. Now a URL is accepted on shape and **any repo-relative path is accepted on existence**, across all three places the form is shared — Review `Findings`, `## Expectation Coverage`, and `## Invalidates`.
- **Narrowing, deliberate:** a path with no file behind it is now refused by name (`invalidation-owner-missing` / `expectation-owner-missing`). Previously a `keel/archive/…` path passed without existing. A note nobody wrote owns nothing.
- `keel/HANDOFF.md` is still refused although it exists — existence is necessary, not sufficient, for something the protocol defines as a pointer. In `Findings`, which is free prose, a path counts only when it follows `Durable owner:`, because mentioning the file a finding concerns does not give that finding an owner. That rule bit its own author within the hour: the first draft of task 2.1's Findings named an archive note in passing and `task-complete` refused it.
- Every refusal now lists the accepted forms from one shared string, so the three messages cannot drift apart.
- Authoring surface: the tasks template, the `tasks` artifact instruction, and the resident protocol all carry both rules. The new scenario reads the instruction the way an author receives it — install into a temp repo, scaffold a change, ask the CLI — rather than from the schema file it is composed from, so a change that never reaches the author fails. Also fixed there, #21's second report: the template read as though `.red`/`.green` **replace** the bare `M<n>` entry, when the gate has always wanted all three.

### A check that fails by doing nothing (closes #18)

- **Six assertions covering the packaged OpenSpec schema had never executed** (closes #18). `packaged_openspec_schema_install_paths()` resolved a root under `dist/` — a tree the validator itself asserts has been removed — and answered `[]`. All six call sites were `for … in <empty>`, so whether `keel --install` writes the schema into a consumer repository, and whether `--uninstall` and `--clear` remove it, had no executing verification at all, while `keel-openspec-surface-overlay` requires that behavior. The helper now resolves `assets/openspec/schemas/keel-spec-driven`, the root `install_to_repo.openspec_schema_actions` reads, and **raises** on a missing root. The installer already raised on exactly that condition; the same fact being fatal there and silent here was the defect, not the wrong path string. (keel-validation-runner)
- The restored coverage is real and was measured, not assumed: with the old helper, deleting a packaged schema template from an installed fixture left `thin-native-install` passing clean. `cli` and `uninstall` turned out to have adjacent nets that catch the same fault with a vaguer message, so for those two this sharpens the diagnostic rather than adding a catch — recorded as measured rather than claimed as more.
- **All four restored scenarios passed on first real execution**, so nothing was hiding behind the vacuity. Had one failed it would have been a product defect, which is why the change was authored to stop and reauthorize rather than fix inline.
- New: `validate_paths` reads the validator's own source and fails on any line building a `Path` into a retired distribution tree, naming file, line, and expression. It keys on the construction form, so the retirement list itself and the README and `package.json` literals that must name `dist/` stay legal. Seven live instances failed it before the sweep.
- Removed: `run_keel_hook` (zero callers, pointing at a hook the custom distribution took with it); `compact-task-authoring`'s projection loop, whose comparison `invalidation-authoring-surface` now performs against the copies that exist; and `validate_openspec_schema`'s source-versus-dist diff, which assigned `dist_root = source_root` and so compared a directory against itself. Both survivors were mutation-tested to confirm the deletions cost no coverage. The package-hygiene loops were repointed rather than removed, and now scan the roots `package.json` actually ships.
- The shape worth naming: this is issue #16's rule turned on tests. #16 required an invalidation entry to quote a *searchable symptom phrase* because the text that goes stale is the text you were not thinking about. The same asymmetry governs assertions — the ones that go vacuous are the ones nobody rereads, and a check whose failure mode is silence never asks to be reread.
- Filed #22 from the same sweep: `keel-expectation-slice-evidence-gates` still carries a live requirement pinning the version to `3.0.0` and asking for `dist/` asset markers.
- Filed #24 from task 1.1: recompiling an archived task no longer reproduces its recorded fingerprint, all 47 of them. It blocks nothing — archived tasks are never resumed — but it is why the fingerprint evidence above uses before-and-after values rather than the archive as a corpus.
- Validator at **80 scenarios**.

## 5.3.3 - a change declares what it makes stale

Closes issue #16. **Migration: every change in flight gains a required `## Invalidates` section in tasks.md**, and `keel gate task-start` refuses without it. The migration is one line — `- None.` — and the template supplies it for new changes.

- **The Task Authoring Gate now asks what a change invalidates** (closes #16). Follow-up Ownership governs work a change left undone; nothing governed the opposite shape — statements left standing by work the change *completed*. A fix is correct and still makes every sentence describing the old behavior wrong, and no gate, spec, or checklist asked. On the day that produced this issue, ten changes shipped and the closing audit found stale statements created by that same day's fixes. `task-start` now requires a `## Invalidates` section: one `- I<n>: "the wording that is now wrong" — where it lives.` entry per stale statement, closed by `Updated by:` naming tasks of this change, a `Durable owner:`, or a `Discard reason:`, or `- None.` when nothing is invalidated. (keel-expectation-slice-evidence-gates)
- **An entry must quote a searchable phrase, not merely list paths.** This is the load-bearing constraint rather than a formatting preference. The text that goes stale is the text the author was not already holding in mind — every miss in the recorded case was a file that merely mentioned the behavior, while every catch was a file already open — so a list of remembered locations reproduces the failure it is meant to prevent. A location-only entry is refused as `invalidation-phrase`.
- **Asked at authoring time, not at the close.** The whole value is that affected paths enter Touch before implementation; asking at `change-close` finds the same facts *after* the reauthorization it was meant to prevent, which is what happened four times in the recorded case. Closure is checked for form, not completion — at authoring time the named updater has not run, so completion is structural: that task carries the paths in its Touch and passes its own gate. Nothing re-verifies at the close, which is the accepted cost of a single checkpoint.
- The section is a sibling heading, so it stays outside every task body and **moves no capsule fingerprint**. The compact parser slices a task body to the next task or EOF, so a trailing block that is not a `##` heading would be absorbed into the last task's final field.
- Authoring surface: the shipped tasks template carries the section with a `- None.` default and its example inside the guidance comment, the `tasks` artifact instruction describes the entry and closure forms, and the resident protocol names it under Completion gates. Two resident sentences were **corrected** rather than supplemented — `task-start` was described as returning the capsule and fingerprint, and Follow-up Ownership read as the complete account of what a change owes at its close.
- Found by the new rule, on its own author: a symptom search for the stale wording surfaced the `tasks` artifact instruction in both schema copies, a surface the change's own proposal had not listed. That is the argument for searching by symptom rather than recalling by filename, demonstrated by the change that introduced it.
- New: the `invalidation-authoring-surface` scenario asserts the repo-local and packaged schema copies are byte-identical. `compact-task-authoring` intended that check but compares against a canonical root absent from this layout, so its `rglob` iterates nothing and has been silently vacuous; the dead loop itself is issue #18. Validator at **75 scenarios**.
- Adding the gate broke 17 existing fixtures, each repaired with the same single line a consumer will add — the migration cost measured rather than estimated.
- npm note: **5.3.2 was tagged but never published**, because its whole change was in the plugin script and `bin`/`src` were byte-identical to 5.3.1. This release does change the CLI.
- Version alignment: the npm package, both native plugin manifests, protocol docs, and this changelog share Keel 5.3.3; the OpenSpec dependency pin stays `^1.4.1`.

## 5.3.2 - the session projection stops talking only to the agent

- **SessionStart projection now instructs the agent to disclose what it found.** The projection is emitted as `additionalContext`, which the host injects into the agent and never renders for the human, so a session would open, the hook would fire, and the user would still have to ask where the work stood. Nothing was broken — the projection was accurate and invisible, which is worse, because a projection nobody sees is a projection nobody checks against OpenSpec and Git. Every branch now carries one line asking the agent to state status, selection, and next action in its first reply: the ready branch, the shared non-ready branch, and all three fallbacks. The degraded branches are the point — a missing CLI or a timeout is exactly the case where the agent's silence reads to the user as established continuity. The instruction confers no authority: the projection still selects nothing, records nothing, and starts nothing. (keel-native-runtime-projection)
- **The resident protocol carries the same rule**, so it holds when no plugin projection runs. A host loads its plugins once per session and can hold a stale set for reasons no repository check can observe — which is not hypothetical, it is why the write guard sat inert through an entire session of this project's own development. The `native-plugin-session-start` scenario reads the shipped `AGENTS.md` rather than a fixture, and pins the two rules that section already carried alongside the new one, because adding a rule to a resident block is precisely where a quiet substitution happens.
- Coverage gained an idle fixture: the scenario previously jumped from a ready repository straight to an ambiguous one, so the most common real state — an OpenSpec repository with no active change — went unexercised.
- The consumer bootstrap does **not** carry this rule. Its managed block has roughly seven bytes of headroom against the sub-1024-byte assertion, and in a consumer repository `keel --install` rewrites `AGENTS.md` from that block — so for consumers the bootstrap is the only durable carrier, and it is the one place the sentence will not fit. That is the same wedge as issue #15 and remains open with it.

## 5.3.1 - the full gate runs in CI; a finished task no longer fails the next one

Closes issues #10 and #13. With #8 and #15 item 1, every issue opened against 5.2.x is now resolved except the resident-block byte budget.

- **A finished task's uncommitted work is no longer the next task's scope failure** (closes issue #13, its last item): `task-complete --base HEAD` diffed the worktree and attributed every changed path outside the selected task's Touch, so when the previous task of the same change had finished but was not yet committed, its files landed on whoever ran next. A path is now withheld from the selected task when a **checked** task of the same change declares it in Touch — derived from `tasks.md`, which the gate had already parsed, so no new state and no fingerprint change. Only a checked sibling counts: an unchecked task's Touch is a plan, not a record. The exclusion is **reported, not silent** — a base comparison cannot establish which task wrote a path, so a warning names the path and the owning task. The per-task commit habit stays the better practice; forgetting it no longer produces a diagnostic naming a file the author never touched. (keel-core-gates)
- **Keel runs its own full gate in CI** (closes issue #10): the 70-odd validator scenarios' only regression net was a pre-push hook on one Windows machine, which is also what `keel-verification-layering` already said should not be the case — it places the full gate "at CI or `keel gate change-close`". Two things blocked it, both smaller than the comment in `publish.yml` implied: **two** scenarios hard-required local `codex`/`claude` CLIs, and **six** assertions hardcoded Windows path separators. `.github/workflows/test.yml` now runs `npm test` on `ubuntu-latest` for every push and pull request; `publish.yml` is untouched and keeps only its tag/version guard. (keel-validation-runner)
- **An absent external runtime skips instead of failing.** A scenario exits `3` when a runtime it probes is not installed — `0` pass, `1` fail, `2` unknown scenario, so conflating an unavailable runtime with either would hide both. `--all` counts skips separately, names each with its reason, and **excludes them from the verified count**, so the number in evidence is the number actually run. The reason is narrow by design: an inconvenient assertion, a hard fixture, or a platform difference is a failure, never a skip. (keel-validation-runner)
- **Assertions no longer encode the host path separator**: a `posix_paths` helper folds captured output and assertions state the forward-slash form — not branching on the platform, and not accepting both spellings, which would pass on a platform printing neither correctly. (keel-validation-runner)
- **Resident-block topics are matched as topics, not as prose** (closes issue #15 item 1): the ten required entries were a flat substring list, so the consumer bootstrap's wording was pinned character-for-character by a check whose purpose is only that the block still covers its topics. An entry may now be a **literal** — for a command, marker, or identifier, where a rename must fail — or a **pattern**, for prose whose wording may move; the diagnostic says which kind was missing. Only the entry that had demonstrably blocked work is converted. (keel-validation-runner)
- The consumer bootstrap now says Touch is the write boundary **for product files**, so a consumer no longer infers that Touch bounds every write. Naming the record-layer exemption outright still does not fit the block's 1024-byte budget — measured at 3 bytes over — which is what remains of issue #15.
- Version alignment: the npm package, both native plugin manifests, protocol docs, and this changelog share Keel 5.3.1; the OpenSpec dependency pin stays `^1.4.1`.

## 5.3.0 - Touch layering: records are not product, and a repository action is a legal task

Closes issue #8. Minor rather than patch: the write guard's decision changes, and there is a new task mode.

- **A task's own change directory is a record-write layer** (issue #8 example 1, and the five reauthorization cycles in its comment): `keel-core-gates` already required that `keel/guard.json` and paths under the selected change's own `openspec/changes/<change>/` directory not be attributed as outside-Touch failures — they are the authoring artifacts the completion gate is completing against — and `task-complete` implemented exactly that. The write guard did not: it denied writes there, and it hashed that directory's `tasks.md` as authority, so **ticking a checkbox or appending Evidence locked the task out of its own bookkeeping**. Declaring `tasks.md` in Touch, the more careful act, produced the worse experience. The guard now derives the same record prefix from the manifest field it already carries — writes under it are allowed undeclared, and recorded authority entries under it are skipped for drift. **No manifest schema change**, so an older plugin hook against a newer CLI keeps its previous behavior instead of failing closed. (keel-touch-write-guard)
- **Post-completion denial is now stated, not inferred**: byte hashing was also what incidentally stopped a checked task from writing. A checked task now gets no further product writes by an explicit checkbox check, while its own records stay writable so it can finish the Evidence its completion gate requires. (keel-touch-write-guard)
- **Write-time drift detection is narrowed, deliberately.** A hook that cannot compile a capsule cannot tell a contract edit from a record write in the same file. Contract drift inside the change directory — a moved Touch, Verify, Covers, title, or boundary — is now caught by `keel guard status` and `keel gate task-complete`, which compile and compare the fingerprint, rather than at the next write. Authority *outside* the change directory still denies at write time. A new spec scenario states where each is caught. (keel-touch-write-guard)
- **`Mode: repo-action`** (issue #8 example 2): a task whose whole effect is an authorized repository-level action — a commit, a tag — writes no worktree file, so it had no concrete Touch; it is not `diagnose-only`, because it has real side effects needing evidence; and `Touch: none` was accepted for no other mode. The reporter was forced to name a path the task did not write, which then tripped the drift defect above. `repo-action` requires `Touch: none`, carries `must not write product files`, and is the one mode whose prohibitions omit `must not commit`. Push, sync, archive, and marking tasks complete stay prohibited. Whether the action performed was the authorized one remains a Review judgment; the capsule fixes the write posture, and the mode is recorded in the fingerprint. Rejected: `Mode: implementation` with `Touch: none`, since `implementation` means "modify only Touch files" and a mode meaning the opposite should not share its name. (keel-task-capsule)
- Authoring surface: the shipped `keel-spec-driven` tasks template and the resident protocol name the new mode and the record layer. The consumer bootstrap could not carry the record-layer qualifier — it is 1013 bytes against a 1024-byte budget and its wording is a literal required topic — so that gap is tracked as issue #15.
- Version alignment: the npm package, both native plugin manifests, protocol docs, and this changelog share Keel 5.3.0; the OpenSpec dependency pin stays `^1.4.1`.

## 5.2.4 - Keel's own surfaces stop manufacturing work and stop overstating what they know

- An issue tracker can own a follow-up (closes issue #12): `keel-expectation-slice-evidence-gates` requires "a durable follow-up owner" without constraining its form, but the gate enumerated three — a `Discard reason:` prefix, a `keel/archive/…` path, or an existing `openspec/changes/…` artifact — so a project whose declared owner is an issue tracker had to write a local note per finding whose only job was to be a shape the gate recognized. (keel-core-gates)

## 5.2.2 - verification layering: fast inner-loop pre-push vs full gate

- Verification layering (closes issue #5): a new `keel-verification-layering` capability and a "Verification layering" section in both READMEs document splitting verification into a **fast inner-loop check** (seconds, run at a local pre-push and during iteration) and the **full gate** (the complete or slow suite — golden byte-determinism tests, cross-platform runs — run at CI or `keel gate change-close`), so a slow suite never blocks `git push`. Generic pre-push hooks that run the full suite are the trap this convention avoids. (keel-verification-layering)
- Fast-check declaration and opt-in pre-push: projects declare their fast inner-loop command as `fast_check:` in a new `keel/config.yaml` that `keel --install` scaffolds once (a commented template it never overwrites). `keel --install --with-git-hooks` — an explicit, opt-in flag — reads `fast_check`, writes a `#!/bin/sh` `.githooks/pre-push` that runs it, and sets `core.hooksPath` to `.githooks` (per-clone, repo-local, reversible); it refuses when no `fast_check` is declared, a plain `keel --install` never touches git config, and `keel --uninstall`/`--clear` unset `core.hooksPath` only when Keel set it to `.githooks`. `keel --doctor` gains a read-only "Fast pre-push surface" section reporting the `fast_check`, the pre-push hook, and `core.hooksPath`.
- Task-capsule Verify layer tag: a task capsule `Verify` check may carry an optional `(fast)` or `(full)` tag after its `M<n>` label to mark which checks the fast inner loop runs; an untagged check is `full`. The tag is declarative — it never changes check text, Evidence label mapping, or what `change-close` requires — and the compiled capsule emits the layer only for `fast` checks so untagged checks keep a byte-identical shape and fingerprint. (keel-task-capsule)
