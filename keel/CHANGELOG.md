# Keel Changelog

## 5.45.0 - a refusal names the cause

- **A file at the repository root is nameable as a `Durable owner:` and as `Resolved here:` evidence** (closes issue #107). `declaredPath()` located a path by finding a run of non-whitespace *containing a path separator*, and a root file has none — so `Durable owner: AGENTS.md` was refused with `it names neither a check nor a path`, for a path whose file exists. Nine files sit at this repository's root today, `AGENTS.md`, `CLAUDE.md`, `README.md`, `LICENSE`, and `package.json` among them, and every one is a legitimate owner; the way past it was `./AGENTS.md`, a concession to the extractor rather than a path anyone meant. Reproduced while completing 5.43.0's own release task. The separator form is tried first and is unchanged, so nothing that resolved before resolves differently, and the trailing-punctuation trim runs before the new shape is judged so a root file ending a sentence is still a root file. **The boundary is the half worth reading**: a value with neither a separator nor a filename shape stays `unrecognized`, because `Durable owner: pending` reported as a file that does not exist would send the author to create one; and the extension must begin with a letter, which is what keeps a version string like `5.44.0` from reading as a file named `44`. Existence still decides, and where a reader names a missing path — `## Invalidates` and `## Expectation Coverage` — it names a separator-free name the same way. `Findings` reports one owner refusal for every unusable owner, as it always has. (keel-core-gates)
- **An `## Invalidates` quoted phrase may wrap across the entry's lines** (closes issue #108). The check was `/"[^"\n]{3,}"/`, so a quotation running past the end of a line was reported as `names where to look but not what to look for` — when it had named exactly that, and the only repair was to reflow the text. Five entries across three changes hit this in one session. The corpus looked clean for a misleading reason: **42 of this repository's 194 archived entries span more than one line and not one carries a wrapped quotation**, because the gate refused every one that did — the shape is absent as a workaround, not as a fact about how authors write. `Findings` in the same file was already read as wrapping. The entry's bounds are the section parser's, so a quotation cannot reach past its own entry; the new scenario asserts that from the other side, with a wrapped I1 above an unquoted I2 and the refusal naming I2 alone. An entry carrying no quotation anywhere is still refused. (keel-expectation-slice-evidence-gates)
- Both changes are loosening, each in the one place it was refusing correct work, and both are bounded by an assertion on what still fails. Two new scenarios drive the real CLI; `durable-owner-vocabulary`, `an-owner-outlives-the-change`, and `task-start-invalidation` all pass unchanged, so no verdict that was right became wrong.
- `assertion-shape-count` refused this change's own first draft of a scenario for guarding two distinct failures behind one condition, at 81 sites against a recorded bound of 80. The condition was split rather than the bound raised, which is what that check exists to prevent.
- Version alignment: the npm package, both native plugin manifests, protocol docs, and this changelog share Keel 5.45.0; the OpenSpec dependency pin stays `^1.4.1`.

## 5.44.0 - the spec names the managed set

- **`keel-openspec-surface-overlay`'s specification says which actions it covers, and a check keeps it saying so** (closes issue #86). `bin/keel.js` has managed four actions — `propose`, `apply`, `archive`, `sync` — for some time, but `propose` and `sync` arrived as *new requirements appended to the same file* rather than as edits to the statement that says what the set is. So the file disagreed with itself: the summary at the top named two actions and the requirements below it covered four. Measured across `openspec/specs/` against 5.43.0: 9 statements name a proper subset, all in that one file — the `## Purpose`, the opening requirement's name and body, its three per-target scenarios, and the two install/refresh scenarios that say `apply/archive/sync` about behavior covering `propose` as well. Issue #86 reports the first of the nine. All nine now name the managed set, and the per-target scenarios enumerate the actual surfaces per target, including OpenCode receiving no authoring overlay. (keel-openspec-surface-overlay)
- **Why the Purpose line survived issue #79's sweep, stated rather than left as a puzzle.** OpenSpec's delta format has operations for Requirements only — `ADDED`, `MODIFIED`, `REMOVED`, `RENAMED` — confirmed against openspec 1.6.0's own change parser. A capability's `## Purpose` is written once when the spec is created and edited directly afterwards; OpenSpec's generated placeholder says as much ("Update Purpose after archive"). No change was ever going to route that line through a review, which makes it the location most likely to drift and least likely to be noticed. The requirement now records that, and the Purpose is the first thing the new check reads.
- **The check is two named locations, not a scan, and that is the point.** Three published statements name a proper subset of the managed set and are correct: `apply/archive/sync` in `keel-target-surface-diagnostics` is `overlayActionLabel()`'s output, which excludes the authoring action deliberately because that line counts state-changing command surfaces; `sync/archive decisions` names what the current agent owns rather than what Keel overlays; and `authoring/apply/archive/sync` names all four with `propose` spelled as authoring. A check that read the file for action words would refuse all three. The new `the-spec-names-the-managed-set` scenario instead parses `OPENSPEC_OVERLAY_ACTIONS` out of `bin/keel.js` — no literal of its own, the same rule the runtime summaries already follow — asserts the two locations, and asserts those three spellings stay accepted. It fails on five constructed drifted copies, and reports an absent requirement heading as an absent location rather than as a missing action name.
- This extends the existing "Every overlay summary names the managed action set" requirement, which made the runtime summaries derived and drift-checked in 5.30.0 and left the specification's own statement of the set out of that rule.
- No production code changed. `bin/keel.js` is read, not written: the managed set was already derived there, and this release makes the prose agree with it rather than moving the authority.
- Version alignment: the npm package, both native plugin manifests, protocol docs, and this changelog share Keel 5.44.0; the OpenSpec dependency pin stays `^1.4.1`.

## 5.43.0 - an owner outlives the change

- **A `Durable owner:` or `Resolved here:` naming a path inside the change's own directory is refused** (closes issue #100). The existence check is the one real guarantee these forms carry, and for this class of path it expires by construction: archiving moves `openspec/changes/<name>/` under `openspec/changes/archive/`, so the pointer is true when the gate reads it and false one workflow step later. Measured across this repository's 35 archived changes: 10 declarations name a path inside a live change directory — 8 `Durable owner:` and 2 `Resolved here:` — **all 10 are dead, and all 10 point at the change that wrote them**. The field report measured the same shape independently in a consuming repository: 36 such pointers, 35 dead, the survivor being the one change still in flight. A pointer that must break is worse than none, because the Review reads as closed while the trail ends halfway. The refusal names the cause — the directory moves when the change is archived — rather than reporting a spelling problem the author does not have, and it reaches all four readers that resolve one: Review `Findings`, `Resolved here:` evidence, `## Invalidates`, and `## Expectation Coverage`. This is the second entry on the line `keel/HANDOFF.md` already sat on: existence is necessary, not sufficient. (keel-expectation-slice-evidence-gates)
- **A path inside a *different* live change directory is unchanged and still accepted.** The resident protocol names a new OpenSpec change as a legitimate owner of deferred work, and zero measured pointers have that shape — refusing it would have traded a real defect for an invented one. The rule is stated on the directory the workflow is about to move, not on change directories in general.
- **Every refusal that lists the accepted owner forms now says what each one is worth**: a repo-relative path is checked for existence at the moment it is cited and is not re-checked afterwards, and a tracker reference is accepted on its shape because a gate runs offline and never fetches one. Issue #100's second half is that the tracker branch is never validated; that stays true and stays deliberate, because a gate that reached the network would lose the local, offline, deterministic property its verdict rests on. What changes is that the author is no longer left to infer a check ran that did not. `keel-review-checklist` still carries the semantic half — a cited URL must already carry the content it claims to hold — where a model can judge it.
- **Not changed: archived pointers already written.** They are a record of what was written, and editing them to stay true would falsify the record. The gates refuse an archived change rather than recompiling one, so no existing declaration in this repository is retroactively refused. Reporting them through `keel --doctor` is issue #100's direction 2 and a separate change.
- Two pre-existing scenarios demonstrated an accepted owner with a path inside the fixture's own change and were repaired rather than deleted, each keeping the assertion it existed for: `durable-owner-vocabulary`'s change-artifact form now names another live change, and `review-entry-extent`'s wrapped-Findings owner names the repository ledger. One new scenario, `an-owner-outlives-the-change`, drives `task-start`, `task-complete`, and `change-close` through the real CLI and asserts the refusal text rather than only the verdict.
- Version alignment: the npm package, both native plugin manifests, protocol docs, and this changelog share Keel 5.43.0; the OpenSpec dependency pin stays `^1.4.1`.

## 5.42.0 - quoted text is not a claim

- **`keel --check` no longer reads a `tasks.md` line's quoted spans** (closes issue #65 items 2 and 4, owner-decided 2026-09-05). Evidence prose quotes what it is evidence of — the command that ran, the output it printed, the branch base an `M<n>.red` ran against, the name of the requirement under change — and every one of those carries exactly the words the recorded-state rules refuse. Measured across this repository's 35 archived `tasks.md` (8,169 lines, against 5.41.0): the rules fire on 91 lines, and 21 of those matches sit entirely inside an inline code span or a quotation span, among them a Scope check recording that it ran `` `git status --short` `` and an `M1.red` naming the branch base `` `68e4fd2` `` it failed against. 70 lines stay refused. `withoutInlineCode()` in `src/core/task-contract.js` settled this shape for the field reader when it shipped; this reader never had it. The removed spans are inline code, a fenced block, and `"…"`/`“…”`/`「…」`/`《…》` — not the ASCII single quote, which is an apostrophe far more often than a quotation mark and would silence the remainder of any line carrying a contraction. Text outside the spans is still read, asserted from both sides: a line quoting an identifier and recording `uncommitted` outside the quotes is still refused and still names its line. Fenced blocks are included on the same argument although the corpus holds zero instances of one, because accepting a one-backtick span and refusing a three-backtick fence would put the code at odds with the rule it states. (keel-stateless-continuity)
- **The `已提交` family refuses a line only when a Git word shares it** (closes issue #103, owner-decided 2026-09-05). `TASKS_COMMIT_STATUS_PATTERNS[2]` matched `已提交`/`未提交`/`待提交`/`尚未提交` as bare words, requiring no Git identifier and no Git context, and 提交 is an ordinary transitive verb — 提交资料, 提交审核, 提交申请. The reported line records that a user submitted merchant paperwork to a third-party review queue and was refused as recorded commit state, while the same fact written in English (`has submitted the paperwork`) passed untouched: the check's verdict depended on which language the author wrote in. The family now needs a word naming Git or a Git object on the same line (`git`, `commit`, `master`, `main`, `HEAD`, `branch`, `PR`, `merge`, 分支, 仓库, 代码库, 代码, 合入, 工作区, 暂存). The 合入 family keeps matching bare — it names the Git act and has no ordinary-prose reading — and the Chinese words keep supplying context to a hash-shaped token unchanged, which is what their missing word boundary was always for. This supersedes 5.29.0's "The Chinese context words carry no boundary, and must not": the boundary reasoning stays true for the hash-context rule and stops carrying the wording rule. The cost is stated rather than left to be found: a recorded commit state phrased with no Git noun — `该任务尚未提交，等待评审` — now passes, and that false negative is owned by issue #103. (keel-stateless-continuity)
- **Not changed: the failure level.** Issue #65 item 3 asked for these refusals to degrade to warnings. Declined by the owner on 2026-09-05: making every true positive quieter is the worse trade once the false positives are gone, so a real match still makes `keel --check` report `keel state: failed`.
- Three pre-existing scenarios asserted the removed behavior and were repaired rather than deleted, each keeping the assertion it existed for: `a-context-word-is-a-word`'s three bare Chinese fixtures now carry a hash-shaped token and no other context word, which is what the missing boundary actually buys; `decimal-runs-are-not-hash-shaped`'s wording-only fixture names 分支; and `a-covers-citation-is-not-a-record`'s field-boundary fixture uses 已合入. Two new scenarios, `a-quoted-span-is-not-a-claim` and `a-submission-is-not-a-commit`, drive `keel --check` through the real CLI against an installed fixture repository.
- Issue #49 was confirmed already fixed in the current tree and closed with evidence rather than reopened: its three reports were covered by 5.34.0, 5.38.0, and 5.40.0.
- Version alignment: the npm package, both native plugin manifests, protocol docs, and this changelog share Keel 5.42.0; the OpenSpec dependency pin stays `^1.4.1`.

## 5.41.0 - authorize continuation between tasks

The protocol's "one task, then stop" boundary folded two different stops into one: stops at real decisions — a blocker, fingerprint drift, an out-of-scope need, a material alignment escalation, an unresolved `Q<n>` — each with its own independent trigger, and the stop at a task boundary inside a change whose `tasks.md` the owner already approved, which re-asked for an approval already given and had no durable place to record the answer (the conversational grant is exactly the channel issue #34 catalogued as not surviving a context reset). Declared in `authorize:`, `continuation` covers exactly the boundary between a durably complete task and the next unchecked task of the same change, in the approved `tasks.md` order, and nothing else: each next task still starts through `keel gate task-start` with its own recorded fingerprint, every gate, evidence requirement, semantic Review, and the write guard run unchanged, no repository action rides along (`commit`, `push`, `release`, `archive` each still require their own name), and nothing schedules — proven inert against a silent twin repository on gate results and continuity selection. The goal skill's stop rule, `README.md`, `keel/config.yaml`'s comment, and `AGENTS.md`'s Execution boundary now name the word and its bounds. On an older Keel the entry is unrecognized and the whole declaration authorizes nothing until corrected — fail-closed, never a silent grant. This repository's own `authorize:` list is unchanged; declaring the word here is a separate owner decision. Settles the C-class row issue #94 found missing from issue #34's closing settlement: C-class task-boundary stops are now closable by declaration, while every other stop class keeps its trigger. (keel-standing-authorization, keel-single-task-goal-execution)

## 5.39.0 - a regression the change owns

- **A `(regression)`-tagged `M<n>` check's bare Evidence may now read `deferred to C<n>`, pointing at a check declared once for the whole change instead of run once per task** (closes issue #95). Reproduced against 5.38.0: `completionChecks()` validated a `(regression)`-tagged check's bare Evidence with nothing but `isConcrete()`, so any change-wide check an author wanted to amortize across several tasks had no place to live — repeat it on every task, attach it only to the last one and leave the earlier ones with no safety net, or drop it. `tasks.md` gains two optional, change-level sections: `## Change Verify` (`Strategy:` plus one `C<n>: <check>` line per check) and `## Change Evidence` (one `C<n>: <result>` line per declared check). A non-`(regression)` check may not defer. No change to `src/core/task-contract.js`'s compiled capsule or fingerprint — the deferral lives entirely in Evidence. (keel-core-gates)

## 5.36.0 - a value is not a name

`#93` measured that `keel/config.yaml`'s `authorize:` vocabulary (`commit`, `push`, `release`, `archive`) does not include `sync`, while `keel gate change-close --action sync|archive` accepts `sync` as a value beside `archive`. A reader who copies from `--help` reasonably copies both into `authorize:`, and the declaration then fails closed exactly as designed — except the failure was reported only by `keel --doctor`, an explicitly-invoked diagnostic; `keel context`, the command a session runs first per `AGENTS.md`, said nothing about it. The issue's own repro shows the same broken declaration sitting uncaught for eight days.

`#93` named three candidate directions and took no position among them. Widening `authorize:` to accept `sync` was not this release's decision to make: this repository's own `sync-surface-overlay` scenario (`#54`, M4) already asserts that `keel/config.yaml` never adds `sync` to its own `authorize:` list, reasoning that naming the gate that governs an action and deciding whether a repository may authorize it once are separate. `authorize:`'s accepted vocabulary is unchanged by this release.

- **The `authorize:` unrecognized-action message, printed by `keel --doctor`, now names the confusion specifically when `sync` is among the unrecognized entries** — it states that `sync` is a `change-close --action` value, not an `authorize:` name, and points at `archive` as the name to declare instead. An unrelated typo (for example `deploy`) is unaffected; the message gains no sentence it does not already carry.
- **`keel context` now reports a broken `authorize:` declaration as a `Warning:` line**, carrying the same message `--doctor` already prints. Previously `keel context`'s `warnings` said nothing about this declaration at all, so learning it was dead required a separate, explicitly-invoked `--doctor` call. `status` and `nextAction` are unaffected by the warning.
- `src/core/config.js`'s `readStandingAuthorization` now computes this message once (a new `message` field, null when the declaration is clean) and both `bin/keel.js` and `src/core/context.js` read it, so the two surfaces cannot re-diverge the way they already had for this exact declaration.

## 5.35.0 - a hash decides what changed

`#72` measured that `keel gate task-complete`'s default (no `--base`) dirty-path attribution subtracted a path from attribution the moment it was dirty when the task started, regardless of what happened to it afterwards. Two tasks of one change, each declaring one file in its own Touch, walked in this repository's normal order — no commit between tasks — and the second task's undeclared write to the first task's already-dirty output passed `task-complete` and `change-close --action archive` with zero problems and zero warnings. The issue measured this as the common case, not the edge case: 81% of this repository's 44 archived changes carry two or more tasks, and 70% of tasks are not their change's first, so most tasks begin with a tree a prior task's legitimate output already left dirty — and every one of those paths was, until this release, a no-further-checks zone for every task that followed.

Three directions were measured on the issue (2026-08-03). 乙 (commit after every task) was excluded because it collides with `repo-action` being the only mode allowed to commit — a protocol change, not a gate fix. 丙 (exempt only the union of prior tasks' own declared Touch) was the owner's first decision (2026-08-04), but an unattended run's own measurement (2026-08-04) showed replaying it against this repository's 44 archived changes fires 458 times across 87% of non-first tasks without ever catching the reproduced defect, with at least one of those 458 already proven a false positive by its own task's Review. The owner then picked **甲** over 丙 (2026-08-05, dasauto#18): record a content signature per dirty path at task start, and attribute a path only when its content no longer matches that signature at completion.

- **`keel gate task-start` records each dirty path's content signature (a sha256, or an explicit absent marker) alongside its name in `keel/guard.json`**, taken at the same moment and by the same worktree read the completion gate already used for the bare path list.
- **`keel gate task-complete`'s default comparison now exempts a dirty-at-start path only while its content still matches the signature recorded then.** A path whose content changed since task start is attributed as outside Touch even though it was already dirty when the task began — the defect `#72` reproduces. A path left untouched since task start stays exempt exactly as before; this is not a reopening of the false-positive class 5.16.0 removed.
- `--base`-driven comparison, the completed-sibling exclusion, the guard-manifest and change-directory exemptions, and every other `outside-touch` behavior are unchanged — this release touches only the no-`--base`, has-a-record branch of `scopeEvidence`. `change-close` performs no dirty-path comparison of its own (unchanged, and out of this release's scope: adding one would be a separate, un-owner-authorized decision), and the write guard (PreToolUse hook) still denies purely by Touch membership and never reads the recorded set — its blindness to shell-issued writes remains a separate, already-shipped concern (5.15.0/5.16.0).
- `openspec/specs/keel-core-gates/spec.md`'s "Dirty-worktree attribution is conservative" requirement and `openspec/specs/keel-touch-write-guard/spec.md`'s "The manifest records what was dirty when the task started" requirement are updated to state the conditional exemption and the content-signature record; the former's "Keel stores no baseline" scenario is narrowed to name the one scoped hash set this release adds, since it previously claimed no hash set is ever persisted.
- Version alignment: the npm package, both native plugin manifests, protocol docs, and this changelog share Keel 5.35.0; the OpenSpec dependency pin stays `^1.4.1`.

## 5.34.0 - the instruction leads the menu

## 5.33.0 - a rejection is a line, not a write

`#70` measured that "a gate never false-stops" has no ongoing check: the archive under `openspec/changes/archive/` is filtered by the very gates it would need to audit, so it only ever holds what passed. A false stop today leaves no trace — the author is refused, assumes the refusal is correct, edits the contract into the shape the gate accepts, and the archived artifact is the edited version, indistinguishable from one that was never rejected. An unattended run has no one to notice this happening.

Three directions were measured on the issue: comparing rejected-and-resubmitted contract text mechanically, making "I think the gate is wrong" a cheap recordable act, and keeping the rejected shape at archive time. The third's most direct form — the gate itself writing the rejected shape at the moment of refusal — was measured against `keel-core-gates:231`, which is unconditional: every failing or `needs-review` outcome must not write project state. Replaying that write across this repository's own 44 archived changes fired 458 times, because tasks in this repository don't commit between each other, so a path outside a task's own `Touch` already being dirty at its `task-start` is the normal shape of most non-first tasks, not the rare shape that direction needed it to be.

The owner picked recording the rejection in the task's own Evidence (R2) over a gate-side write (R3) on 2026-08-05: the task author records what a gate rejected themselves; the gate adds no write of its own and validates only the entry's shape. This keeps `keel-core-gates:231` intact — recording a rejection is the same trust boundary Review, Findings, and every other author-written Evidence entry already carry, not a new mechanism.

- **A task's `Evidence` gains an optional `Reauthorizations` entry, sibling to `Blocker`.** `Reauthorizations: none` is the default; when a gate rejects a task and the author revises and resubmits, the author records what was rejected and what changed as free text under the label. `task-complete` validates only the entry's shape — absent, `none`, or `pending` need no entry; any other content must carry no unfilled `<slot>`/`TODO`/`TBD`/`placeholder` token — and never judges whether a rejection factually occurred or requires the entry's presence or count to match anything else.
- **Presence does not block completion, unlike `Blocker`.** A concrete `Reauthorizations` entry is a log, not a stop condition: a task that recorded real rejections and resolved them still completes. Proven able to fail rather than assumed — a concrete `Blocker` on the same fixture does fail completion, so the comparison is not vacuous.
- **The entry reuses `reviewValue()`'s existing sibling-bound extent** (5.28.0, "a review field is what the author wrote"), so a `Reauthorizations` block spanning several lines is read whole, including an unfilled token left on a continuation line rather than the label line itself.
- Both `tasks.md` templates gain `- Reauthorizations: none` after `- Blocker: none`, with no effect on `task-start` — the field is not part of the compiled capsule, only of completion's shape check.
- Version alignment: the npm package, both native plugin manifests, protocol docs, and this changelog share Keel 5.33.0; the OpenSpec dependency pin stays `^1.4.1`.
- No change to `field()`, `fieldValues()`, `parseTasks()`, `reviewValue()` itself, or any of the four existing Review entries. No change to what `task-start`, `Blocker`, or any existing Evidence field accepts, and no new project write on any gate outcome. ## 5.29.0 - a word inside a word is not the word

`keel --check` scans every active `tasks.md` for state git already owns. Two of its rules read free prose, and both were matching text that was never a claim. `remaining` supplied the context word `main`; `heading` supplied `head`. And a `Covers` entry — a citation whose three segments must resolve to names that exist in a spec — was read as a sentence, so citing `keel-core-gates / Dirty-worktree attribution is conservative` was refused as recording a dirty worktree. Both halves reported as #65, whose material choices the owner decided on 2026-08-04.

- **A context word is now a word.** The ASCII alternatives carry `\b` and their inflected forms: `commits?|committed|committing|master|main|HEAD|hash(es)?`. Across all 53 `tasks.md` in this repository's history, contextual refusals fall from **12 to 8, with none newly refused** — and the four that go are `remaining` twice and `heading` twice, every hex token on them a `sha256:` contract anchor or a recompiled capsule fingerprint, read line by line rather than counted. (keel-stateless-continuity, #65)
- **The stricter boundary was available and was not taken.** `\b(commit|master|main|HEAD|hash)\b` drops the same four false positives, and also drops `committed` and `hashes` — 4 real refusals in the corpus, mostly `Scope check:` prose quoting `git status`. The owner's answer to "is that worth paying" was no, so the inflections are spelled out. This is the trade-off, not an oversight in the pattern.
- **The Chinese context words carry no boundary, and must not.** `\b` is defined between a word and a non-word character, and every character of `提交` is a word character, so `\b提交\b` matches neither `已提交` nor `未提交` — exactly what the wording rule exists for. Adding one there would have disabled the rule silently rather than wrongly, which is the failure no existing fixture would have caught, so it now has its own.
- **A `Covers` citation is not a record of what it cites.** The field is exempt from both prose rules. This half is **wider than #65 reported**: 11 lines across 4 changes in this repository's history are refused this way, 8 of them citing requirements published in `openspec/specs/` today, and the rules have been in the file since the initial commit — so those lines were live `state-error`s for as long as their changes were active. The issue reports one change's three lines, because the workaround (rename the requirement) was cheaper than the report. 5.19.0's own requirement is named "commit **identifier**" for precisely that reason; that constraint is now gone.
- **The exempt region is the field, not the label line.** All 165 `Covers:` labels in the corpus are the block form with citations on the lines below, so a label-only exemption would have changed nothing. The bound is `parseTasks()`'s own — a two-space `- Name:` line, holding every line until the next one — copied from `src/core/task-contract.js` so the exempt set is exactly the lines the contract compiler reads as citations, and a line cannot be a citation for one tool and prose for the other.
- **What the exemption costs, stated rather than left to be found.** A genuine commit hash pasted inside a `Covers` entry is no longer refused by this check. It is bounded by `unresolved-covers`, which already refuses any entry that does not resolve to a spec name or a design reference, so the hash would have to be part of a name published in a spec. `Evidence` and `Verify`, where a hash actually gets pasted, are untouched — asserted from the other side, by a fixture whose wording is exempt inside the field and still refused one line later.
- **Two of #65's four items are still the owner's and are not reopened.** Exempting backticked text and downgrading a violation to a warning were declined in 5.19.0's D3, for reasons this change adds no fact to. One measured instance is recorded against the first: authoring this change's own `tasks.md` required rewording it three times to get past the rules being repaired, and the new case is `## Invalidates`, where the protocol asks you to quote the wording that goes stale and the check refuses the quote.

## 5.28.0 - a review field is what the author wrote

One release after a change-level section stopped being cut short of what its author wrote, the same defect turns up one level in. A task's Review lives inside `Evidence` as four labelled entries — `Status`, `Acceptance check`, `Scope check`, `Findings` — and `reviewValue()` matched each with a line-anchored regex whose `(.*)` stops at the newline. The continuation lines were already in hand: `parseTasks()` gathers the whole field body and `field()` joins it. This one reader threw the rest away. So a `Findings` recording its `Durable owner:` on the fourth line was refused with the owner present, the path existing, and the form correct — and joining the identical text onto one line, without changing a word, made it pass. Reported as #49's first supplement, where the author records landing in it twice in one session.

- **A Review entry is now the text the author wrote under its label.** It runs from the label line to the next entry at the same or shallower indentation. A finding may wrap across as many lines as it needs and still be read whole. (keel-core-gates, #49)
- **The reported half: a durable owner below the first line is now seen.** The diagnostic made this worse than a plain refusal. It closes with "Name a path after `Durable owner:` so it reads as the owner rather than a file the finding mentions" — a sentence about *notation*, true when a path was written in passing and false here, since the author had named it exactly where the message asks. Faced with a message about wording, an author checks the wording. The cause was that lines two through four were never read.
- **The silent half, which #49 does not report and which is the worse one.** A `Findings` reading `none` on its first line and recording two unowned findings below it produced no problem at all — the check tested `/^none\.?$/i` against the word `none` and never saw the rest. A finding with no owner passed the gate whose subject matter is finding ownership. That is why the widened read covers all four entries rather than only the one the issue names.
- **Widening the read stops at the sibling entry.** Without that bound `Findings` — always the last of the four — would run to the end of `Evidence` and read `- Blocker:` as its own text, trading a fail-closed defect for a fail-open one. A deeper-indented `- ` line is a continuation, which is what keeps a `Findings` written as a sub-list one entry.
- **`Status` is the one place the wider read newly refuses rather than newly accepts.** A wrapped `Status: pass` is now judged on its whole text and reported as outside the accepted vocabulary. That is the right answer for a vocabulary field — text under `Status` is text about the status, and discarding it silently is the defect being removed — but it is the direction nobody asked for, so it is named here rather than left to be discovered. Exempting `Findings` alone would have put a per-field special case where one reader belongs, and left three entries judging text they had not read.
- **Nothing about what is accepted moved.** Every disposition marker, owner form, `Status` token, concreteness rule, diagnostic code, and message string is what it was; the only verdicts that change are those turning on text the gate previously discarded. Measured against the whole history: of **640 Review entries** across every change under `openspec/changes`, **zero** wrap, so no archived verdict moves.
- **`Verify`'s own line-wise splitting was deliberately left alone.** A continuation line under `- M1: …` is still refused as `invalid-command-label` — #49's second supplement, reproduced at 5.27.0 and untouched here. `Verify`, `Covers`, and `Touch` read entry *lists*, where one line per entry is the meaning rather than an accident, and `Touch` is compiled by the write guard. That is a separate reader and a separate change.
- **The sibling bound is asserted by mutation rather than assumed**, since it passes before and after. The first mutation — dropping the break entirely — turned the *wrong* cell red: `Status` then swallowed the other three entries and the Review failed before the Findings check was reached. Narrowing it to invert the comparison struck the intended cell. A mutation that goes red is not automatically the mutation you meant.
- Version alignment: the npm package, both native plugin manifests, protocol docs, the twelve OpenSpec surface overlays, and this changelog share Keel 5.28.0; the OpenSpec dependency pin stays `^1.4.1`.
- No new dependency, no gate, timing, or ordering change, and no schema change. Validator at **136 registered scenarios**, one added: `review-entry-extent`.

The cost is kept; what changed is that the surface reporting it now names the way out. That trade was the owner's call on the issue, not this change's to make.

Two mutations were aimed at it: inverting the directory test turned the archived cell red, and forcing every state down the stale branch left that cell green while turning the parse-miss cell red on the exact comparison it exists for — `Expected ['authority-drift'], got ['stale-manifest']`.

That was true of the status *word* and was taken as true of the whole surface; nobody read the sentence underneath it. A measurement of one field stood in for a measurement of the message, and the repair stopped one function short.

## 5.26.0 - a section is what the author wrote

`## Invalidates` and `## Expectation Coverage` were each read by finding the heading and taking everything up to the next `## ` heading. That is the right bound for a document made of headings, and a tasks.md is not one: its dominant structure is a list, and what follows a change-level section is almost always a task. So whenever either section was not the file's last one, it ran over the whole task list and judged what the tasks had declared. Every archived change happens to put both sections in the tail — 49 of 49 — which is why this never surfaced from the archive. The position that avoided it was written down nowhere: not in `AGENTS.md`, not in either template, not in the schema, not in any diagnostic. It was a habit. Reported as #71, found while authoring a fresh change rather than by reading the archive, which can only hold what passed.

- **A change-level section now ends at the next `##` heading or at the next task, whichever comes first.** Its extent is the section the author wrote, wherever in the file it sits. Both readers compute it through one `sectionBody()` rather than through two character-identical copies, and the task half is the task list already parsed for that file — not a second checkbox pattern that would have to keep agreeing with `parseTasks()`. (keel-task-capsule, closes #71)
- **The loud half: an entry that was closed was reported as unclosed.** With `## Expectation Coverage` above the task list, `change-close` refused with `E1 lacks behavior coverage, durable owner, or discard rationale.` for an `E1` closed by `Covered by: 1.1` three lines above. The entries it judged were the `- E1:` lines each task declares under its own `Covers`. Moving the identical section to the tail made the same command pass with no edit to its content — so the diagnostic sent the reader to an entry that had nothing wrong with it, and an unattended run to a repair that was not needed.
- **The quiet half, which #71 does not report and which is the worse one.** The section's `- None.` early return tested the whole swallowed body. A `repo-action` task declares `Touch` as a bare `- none`, so with `## Invalidates` above the task list an `I1` that closed nothing at all returned `pass` from `keel gate task-start` — the entire declaration read as "this change invalidates nothing". The gate whose subject is what a change makes stale was failing open on it. That cell is why both readers were fixed rather than only the one the issue names.
- **Position is now irrelevant rather than required.** #71 offered both endings. Requiring the tail would have refused a layout nothing has ever documented as wrong, would have needed a new diagnostic to say so honestly, and buys nothing — what the checks judge is the section's content. What closes an entry is untouched, every diagnostic code and message is untouched, and the entry patterns are untouched.
- **The heading half was deliberately left alone, and that is the owner's decision.** An earlier attempt unified it with `parseTasks()`'s `/^\s*##\s/` on the reasoning that the two patterns match the same headings. They do not: a tail-position section whose body contains an indented `## …` line truncated there, and an unclosed `- I2:` after that line stopped being reported at all — a new instance of the exact failure class this release removes. The published requirement asks that consumers of *a task's extent* share one boundary, which the task half satisfies literally; a section's own heading bound is not a task's extent.
- **The tail position is asserted rather than argued.** It is the shape all 49 archived changes use and it passes before and after, which is also the shape that passes when the mechanism producing both sides is broken. So the boundary was mutated to end at the first task unconditionally: `section-boundary` went red naming the tail fixture, and the same mutation failed six scenarios across the suite.

## 5.19.0 - a decimal run is not a hash

`keel state: failed` on a line holding no commit identifier. The evidence prose contained a fake phone number, `13800138000`, and the check answered `remove contextual commit hash from tasks.md; git log is the source of truth`.

- **Eleven decimal digits are eleven characters of `[0-9a-f]`.** The criterion paired a context word with any run of 7–40 characters from that class, so a phone number, a timestamp, an order number, a port, and every numeric fixture were commit identifiers to it. - **The cost was never the refusal — it was what the refusal asked for.** Nothing was wrong with the line, so the only way past it was to write the evidence differently; the reporter changed the number to `138****0000`. Evidence reworded to satisfy a pattern is weaker than the evidence that was true, and a check that fails on correct work is one people learn to route around. At that point it is not protecting anything.
- **What the narrowing costs, measured rather than assumed.** An abbreviated identifier that happens to carry no letter is now missed — `(10/16)^7` ≈ **3.7%** of seven-character abbreviations, 0.6% at twelve, nothing at forty. Two things bound it: across every tasks.md in this repository's OpenSpec history, active and archived, **5,210 lines, no verdict changes**; and the commit-*wording* patterns are untouched, so `已合入 master`, `未提交`, and `merged into main` still fail on the words regardless of the digits.
- **The same cause as #60, repaired in the opposite direction.** 5.18.0 widened a class that was too narrow; this narrows one that was too wide. Its `D5` said so in advance, and both entries now stand for one rule: the implementation must match the criterion, in whichever direction that lies. "Loosen the pattern" was never the lesson, and neither is "tighten it."
- **Three repairs the issue proposes are deliberately not here**, because they change *which lines the rule refuses* rather than how it recognizes what it already refuses — how much surrounding context is required, whether backticked text is exempt, and whether a violation stops `--check` at all. Each is the owner's call. Filed with the measurement as **#65**, together with a fourth found while writing this change: the wording rule refuses a tasks.md that *cites* it, because a `Covers` entry has to quote its requirement name verbatim. The requirement here is named "commit identifier" for exactly that reason — the same cost the issue reports, paid in the spec's vocabulary.

## 5.12.0 - a message that cannot be true

Three surfaces stated something the reader could not act on, and in each the true statement had no form available. A check can be perfectly right about *whether* to fail and still describe the wrong failure — and a reader acting on that sentence goes to a place with no problem in it, which costs more than saying nothing.

- **A finding fixed in its own task had to be recorded as discarded.** This capability's spec says "**WHEN** Review identifies an *unresolved* finding" and `keel-review-checklist` says "each *unresolved* finding with a durable owner"; the implementation applied the requirement to every non-`none` Findings value. So a finding found and repaired inside one task had no accepted form, and in 5.11.0 the text "Closed here; no follow-up is owed" was refused — the only way through the gate was `Discard reason:` for something that had been fixed. The archive recorded a repair as a dismissal. **`Resolved here:` is now the third disposition**, and it must name what proves the fix: an `M<n>` check the task declares, or a repo-relative path that exists. A bare marker is refused, or the new state would be a way out of the other two. So is a tracker reference — a link to work someone else will do is the durable-owner state, not evidence this task did it — and that case is tested *before* the path form, so a URL is not refused by reporting that some substring of it is not a file. `## Invalidates` has carried the same third slot since it shipped, where `Updated by:` names tasks of this change. (keel-core-gates)
- **The criterion is now written down, not left to whichever marker passes.** `AGENTS.md` and both copies of `keel-review-checklist` state all three: fixed here with a check that proves it → `Resolved here:`; still open and owned by someone → `Durable owner:`; considered and deliberately not done → `Discard reason:`. Only the last two are follow-ups. The gap that produced this was never a missing marker alone — an author at the gate picks whichever marker gets through.
- **A stale write-guard manifest denied by giving advice that could not be followed, and granted authority it no longer had.** `taskIsChecked` reads the guarded change's `tasks.md`; once the change is archived that read throws, the miss is read as "not checked", and control reaches the Touch comparison. A write *outside* the archived task's Touch was denied by a message naming a task that cannot be reauthorized; a write *inside* it **passed silently**, so an archived task went on granting write authority. The second half is the worse one and was found by aiming the check inside Touch. The hook now separates a change directory that is gone — a fact `keel guard status` already reports as `drifted` — from a task id missing from a live `tasks.md`, which is a parse miss it must not guess about. The first denies and names `keel guard clear`; the second is unchanged. It still denies: failing closed is what stops `openspec archive` from quietly disabling the guard. (keel-touch-write-guard)
- **The one-message-many-failures assertion shape is now counted.** Issue #43 records it caught by `keel-review-checklist` in three consecutive changes, every time in `scripts/validate_plugin.py`: `if <the run did not work> or <the output lacks a specific thing>:` under one `report(...)` describing only the second operand. Measured: 1069 report-then-return assertion sites, 287 with an `or`, and **75** of the counted shape — so the lint the issue proposed is unshippable as a pass/fail rule, and the three that were caught are the three someone happened to look at. A recorded count fails when the number rises and lists what it measured, and **fails when it falls without the constant being lowered**, because a number that only checks for rises stops being true the first time a site is fixed. **The number bounds a shape and is not a count of defects**; whether a given sentence misleads needs a model and stays in the checklist. The constant was first written as 77, predicted rather than measured, and the check refused it on its first run. (keel-validation-runner, closes #43)
- **Known limits, recorded rather than papered over.** `Findings` is one line of free prose the gate cannot split, so one valid disposition satisfies a block that also holds an unresolved finding — the same limitation the owner forms have had since they shipped. And writing the marker's *name* inside a Findings block counts as using it, so a finding that discusses the disposition must name it in words instead of quoting it. Both are in the change's design.md with the reasoning; fixing either means one-finding-per-line Findings, which is a protocol change with its own cost.

## 5.11.0 - the name is not the thing

Five checks compared names instead of things, and each failed silently while looking exactly like a check that works. The write guard is the one that matters, because it is the only mechanism that enforces anything at write time; everything else in Keel's write discipline is convention the guard is supposed to make real.

- **The write guard could be bypassed by a symlinked path.** Containment was `path.relative(repo, path.resolve(repo, target))`, and `path.resolve` never follows a symbolic link while the `cwd` the operating system reports usually already has. Measured against a repository reached through a link, manifest active, Touch allowing `src/allowed.js`: `<real>/src/denied.js` was **denied** and `<symlink>/src/denied.js` was **allowed**. The same file. The hook returned before reading the manifest at all. On macOS `/tmp` is such a link by default, and any repository reached through one — a symlinked checkout, a home-directory link — was affected on every platform. Both sides are now resolved, from the nearest existing ancestor because a guarded write is usually a file about to be created. **A write that passed yesterday through a symlinked path is denied today**; that is the fix, and it can land mid-session. (keel-touch-write-guard)
- **`src/core/helper.js` had the mirror image**, calling a path inside the worktree external, so the helper wrote its baseline into the repository it had just promised not to touch. That is why `native-helper-read-only` had been red on macOS and green on Linux CI. It passes now without being edited: the defect it was reporting was real.
- **A Chinese filename in Touch could not complete.** Git octal-escapes any path holding a non-ASCII byte and quotes it; `gitPaths` then ran `line.slice(3).trim().replace(/\\/g, "/")`, which left the quote attached and turned `\346` into `/346`. Paths are now read with `--porcelain=v1 -z` and `--name-only -z`, which emit raw bytes for non-ASCII, spaces, quotes and backslashes alike — measured, because `core.quotepath=false` removes the octal and still quotes the rest, and `status` and `diff` do not agree on which cases they quote. A flag rather than a repository setting, so the answer does not depend on how a repository happens to be configured. (keel-core-gates, closes #40)
- **Three separator rewrites were removed, not one.** `gitPaths` corrupted every escape it read; `pathAllowed` rewrote the Touch entry; `scopeEvidence` rewrote the candidate. The last two cancelled each other for a filename holding a literal backslash, which is why nothing had ever surfaced — while a Touch entry naming `src/back/slash.js` silently admitted a changed `src/back\slash.js` the task never declared. Git emits forward slashes on every platform, so all three normalized a separator that never arrives.
- **The suite ran on whatever interpreter and OpenSpec answered.** `run_python.js` accepted any interpreter whose `--version` exited zero, so macOS system Python 3.9 ran a suite needing 3.10 and failed ten scenarios with messages naming ten unrelated features; it now requires 3.10 and names every candidate with the version it reported. `keel` resolved `openspec` from PATH in silence when `node_modules` was absent, so this repository validated against 1.4.1 while its lockfile resolves 1.6.0. `keel doctor` now names the resolved command and both versions, and the suite fails naming both when they differ. Keel reports which build answered and selects none. (keel-target-surface-diagnostics, closes #36)
- **The template fixture was malforming the template.** `fill_template_slots` replaced every HTML comment with slot text, including the own-line author instruction the spec template gained in `ed1388d` — the change whose own task asserted that a requirement written from this template validates. The instruction became a bare paragraph above `The system SHALL …`, and `openspec validate` reported the requirement as lacking a modal verb. One rule for both templates now, and a new assertion that fails at the fixture rather than at the template.

## 5.10.0 - the anchor is compared, not counted

The contract anchor exists to answer one question: did the task's authority change while it was being implemented? `keel context` compared it. `keel guard status` compared it. `keel gate task-complete` — named in the same protocol sentence, and the gate that decides whether a task is finished — checked only that sixty-four hex characters were present, then discarded the value.

- **Archived changes are unaffected.** Change discovery excludes the archive tree, so no gate can select an archived change and no archived anchor is ever recompiled. That boundary was already stated in `keel-core-gates` — an archived task's capsule names source paths under a directory that archiving renamed, so it recompiles to a different value by design — and this change depends on it rather than moving it.

## 5.9.0 - the runtime says which version it is

Every answer Keel gives rests on its checks being local, deterministic, and reproducible. It has never said which build produced them. The SessionStart projection now compares the plugin executing the hook, the CLI it invokes, and the protocol version the repository stamped into its managed block, and reports a disagreement on both channels.

- **It reports, and does not manage.** The obvious next sentence after "your plugin is stale" is "so let me update it", and the host already owns that command — which is exactly why this is where 5.8.0's scope rule was most tempting to break. The remedy named is `claude plugin update`, and only for the target whose manifest was actually read; an unprobed target gets a description rather than an invented command line. Naming is not running, and that is checked rather than asserted: a preload patches `child_process` inside the hook's own process, and the log holds exactly the two `keel` invocations the hook already made. Those two are also the recorder's positive control — a recorder that had stopped working would leave an empty log and fail the same count. (keel-native-runtime-projection, keel-surface-evolution-policy)
- **Silence when aligned.** A matching set adds nothing. This diverges from issue #38's own wording, which proposed a line naming all three versions every session; the divergence is deliberate, and the cost is accepted — confirming which build is running is now a question you ask, and `keel --version` answers it. A line printed every session stops being read weeks before the session it mattered in.
- **Missing is not mismatched.** A repository with no managed block is a normal state, not a fault. An undiscoverable version never produces a line on its own, and fewer than two readable versions is nothing to compare rather than agreement. When one appears beside a real disagreement it is named as `undiscovered, not compared`, so a partial comparison cannot be read as a complete one.

Ordering would invite a judgement about which direction is acceptable — a newer plugin than protocol, an older CLI than plugin — and every such judgement is a rule that has to be right.

Without that sentence the reader updates the plugin, sees the same warning, and concludes the check is broken. The added cost is one `plugin.json` read and one regex, which matters because this runs on every session including post-compaction reinjection, under `KEEL_HOOK_TIMEOUT_MS`. ## 5.8.0 - declare who runs the task

A repository can say that a task may be implemented by a subagent, and at which capability tier. The interesting part is what did not have to be built.

- **The containment was verified, not written.** A probe on 2026-08-01 spawned a subagent under a live guard manifest: its write outside `Touch` was denied with the byte-identical message the current agent receives, and its write inside `Touch` succeeded. That second half is the positive control — without it the probe would have shown only that subagents cannot write at all. A procedure without its rule is followed where it was written and nowhere else, which is exactly why this change proposed a write-capable brief module before anyone asked whether the host already carried one. It is not built; the `subagent-start` projection Keel already publishes carries the write boundary and the tier instead. The requirement separates a *conflicting* surface from a duplicating one: duplication wastes effort, while a surface contradicting the runtime leaves the agent no correct action. (keel-surface-evolution-policy)
- **The tier is declared, never inferred.** `delegation:` in `keel/config.yaml` over a closed vocabulary — `routine`, `standard`, `deep` — inherited by a task that authored no `Delegation:`, with the capsule naming the file as the source. A tier names the capability the work requires rather than a guess at its size, because a tier named for size authorizes precisely the judgement 5.7.0 refused for triage. Keel names no model: one is target-specific and expires at the next release, in a file whose point is to still be correct after both.
- **`authorize:` is deliberately not extended.** Its four names each change durable repository or outside-world state; delegation only routes execution. A fifth name would redefine a closed set whose value is being narrow enough to read at a glance — and the aimed red shows the cost concretely, since with `delegate` inside it `authorize: [commit, delegate]` grants both.
- **A delegate's result is a claim, and the current agent re-runs every check.** This is structural rather than cautious: the before/after byte-identity verification that lets a read-only helper's return be trusted cannot apply to something authorized to write, so re-running is what restores the property it provided. It is also what makes a wrong tier cost a retry instead of a bad merge.
- **Delegation is refused with no active guard manifest.** An absent manifest passes every write through silently and looks identical on screen to one the guard checked, so the condition is answered before a delegate starts rather than inferred from what it did afterwards.
- **The single-task goal path admits a delegate, and its invariant is restated rather than removed** — the current agent is the sole holder of *write authority*. The invariant's purpose was never that one process performs the writes; it was that one party is answerable for them. The delegation fields sit inside the 4,000-character activation budget, so an overflow refuses rather than trimming.

Established from the Claude Code runtime binary rather than its documentation: `SubagentStart` and `SubagentStop` exist, and neither payload carries a model identifier. The one indirect route is refused rather than unavailable — reading a native transcript would contradict `keel-stateless-continuity`.

The capsule field is emitted only when a tier resolves — an unconditional one moved every compiled fingerprint, including every live change in every consumer repository, and `task-body-ends-at-heading` caught it.

## 5.7.1 - a valid reference is not a full one

Closes **#33** and the second instance recorded on it. Two failures in this repository share one shape: a check whose **form** is valid while its **content** is empty or wrong.

- **A durable owner declared as a URL must already carry its content at the moment it is cited.** A valid link to an empty issue owns nothing. Caught empirically in 5.4.0, where expectation E5 cited issue #32 as the place a rejected proposal's reasoning was recorded while `gh issue view 32` returned zero comments — the claim was false when both deterministic gates returned `pass`, and it was noticed only because someone happened to look.
- **A failure message must name the actual cause.** The trigger to watch for is one condition guarding two distinct failures: `if result is None or result["status"] != expected` reports the first failure's message when the second one happened, sending a reader somewhere with no problem in it. Reproduced in 5.7.0's own new triage scenario — in a repository that fixed this class in 5.2.3, by the agent that had just read the rule. A fix that corrects instances without leaving a recurrence guard has a half-life, and this is the guard.
- **Both stay semantic-review checks, and the spec now says why they must not become gate checks.** A gate that fetched a reference would stop being local and offline, failing differently on a plane than in CI; judging whether a sentence misleads needs a model. `keel-expectation-slice-evidence-gates` already stated that a gate "cannot confirm that a URL resolves" and then assigned the resulting check to nobody — this names the owner rather than adding a mechanism.
- Neither check judges quality. Both concern whether content is present and whether a stated cause is the real one, never whether reasoning is sound or wording is elegant.
- **This change was admitted to an unattended run** by the `auto` label on issue #33, evaluated by `keel triage`. Admission started the work and decided nothing in it: the change went through authoring, both gates, and semantic review exactly as any other, and it ends at a pull request rather than a merge.
- No behavior change to any gate, command, or config surface. Validator at **101 scenarios**.

## 5.7.0 - declare what may run unattended

Third layer of **#34**. 5.5.0 declared which *actions* may proceed; 5.6.0 recorded *why decisions went the way they did*. Neither said which **work** may start, so an unattended run had nothing to consult at the moment it mattered most — an issue arrives and something must decide whether it becomes a change at all.

- **A repository declares which issues may start work unattended**, as a label allowlist under `triage:` in `keel/config.yaml`. `keel triage --labels <labels>` evaluates it and returns admit or refuse with a reason. Absent declaration admits nothing. (keel-unattended-triage)
- **That decision could not have been reached any other way, and the reason is worth stating.** "Should this issue be done" sits in the materiality categories that require asking, and 5.6.0's precedent rules forbid a precedent from moving a decision out of that list — deliberately, because a system that can learn its way out of asking drifts toward asking nothing at a rate nobody notices. So no accumulation of triage history can make this automatic. The only route is the one standing authorization already established: the owner declares it, and a declaration *is* the decision rather than a claim about what the owner would decide. The precedent spec now says so explicitly, since a store of past triage decisions is the most tempting thing a reader would try to apply.
- **A label is the unit on purpose.** A person applies one to a specific issue, so the policy admits a class the owner curates one issue at a time. The alternatives were considered and refused: author allowlists authorize a person rather than a piece of work; title or body keywords authorize whatever anyone chooses to type; and size or complexity estimates authorize the agent's guess about difficulty, which is exactly the judgement that should not be automated. Keel cannot verify a human applied the label and does not pretend to — a repository whose automation can label issues has a broader policy than it appears.
- **Keel never fetches the issue.** The agent reads it with `gh` and passes the labels in. A check that reaches the network trades the local, offline, deterministic evaluation that makes every other Keel answer worth trusting, and it also makes the check untestable without a network. Proven under a preload that makes every network primitive throw, with the same inputs asserted to give the same answer twice.
- **Admission answers "may this begin" and nothing after it.** Every gate, evidence requirement, Review, and the write guard behave exactly as they do for work nobody triaged — asserted by comparing a declaring repository against an identical silent one, with a positive control that was itself verified to fire.
- **A run may open a pull request and may not merge one.** No configuration key grants a merge. Merging is where an unreviewed decision becomes the project's history, and a pull request is what makes an unattended run reviewable after the fact.
- **Stopping at a material decision is the designed boundary, not a failure.** The protocol says so, and says not to widen the triage policy to stop it happening — without that sentence, "it keeps stopping" turns into exactly the pressure this design exists to resist.
- **Keel schedules nothing.** `/loop`, cron, and CI triggers belong to the host runtime; claiming otherwise would be asserting a capability Keel does not have. This is a spec requirement rather than a disclaimer in prose.
- This repository declares no triage policy of its own. Doing so would start unattended work on its own issues, which is its owner's decision rather than a default worth shipping — so unlike 5.5.0 and 5.6.0, this interface ships fixture-tested rather than in use, and that gap is recorded on #34.
- No behavior change without a declaration, and nothing to do on upgrade. No new dependency.
- Validator at **100 scenarios**, with three added for the declaration, its inertness, and the boundary.

## 5.6.0 - the reasoning is the part that transfers

Second layer of **#34**. 5.5.0 gave a repository somewhere to record *that* an action is authorized. This gives it somewhere to record *why a decision went the way it did* — the part that would generalise to a decision not yet seen, and the part that a context reset destroys completely.

- **A repository can point Keel at a directory of precedents** by declaring `precedents:` in `keel/config.yaml`. Keel bundles none and creates none, exactly as it bundles no domain lens. The path is declarable rather than fixed — unlike `keel/lenses/`, which is necessarily in-repo because a lens describes that repository's domain — so one store outside your repositories can serve all of them. (keel-decision-precedent)
- **The mechanism is the one Keel already had.** Domain lenses were already user-authored markdown in a declared directory, self-describing, loaded only on match, with nothing shipped. Precedents are a sibling of that surface rather than a new invention; they differ in two ways that made sharing the file space wrong — they accumulate over time, and each carries a promotion state a lens has no concept of.
- **A precedent must carry its rationale, and one that carries only a conclusion is reported incomplete.** "Chose A" applies only to the situation literally recorded; "chose A because B fails offline" can be applied to a case nobody has seen — and, just as importantly, recognised as *not* applying when the new case is online. The check is structural: Keel reports the field's presence and never claims to have judged the reasoning.
- **Three rules, all of them chosen against a specific failure.** A precedent is cited exactly where it replaced a question the user would otherwise have been asked, so a citation always marks a decision made in their place rather than running commentary. Promotion from `recorded` to `authorized` happens only when the user accepts a proposal — never by a usage count, because a threshold crosses with nobody watching. And a precedent answers a *recurrence* within a materiality category; it can never move a decision out of the categories that require asking, or the system drifts toward asking nothing at a rate too slow to notice.
- **A precedent informs a decision and never substitutes for a proof.** Gates, evidence, Review, and the write guard are untouched. Asserted the same way 5.5.0 asserted it for standing authorization: compare a store-declaring repository against an identical silent one, with a positive control that first proves the two actually differ — a store that silently failed to load would make every such comparison trivially equal.
- **SessionStart carries a pointer, never a body.** Counts and freshness only. The store grows without bound while the precedents relevant to any one session are a small subset, and the hook pays its cost on every session including post-compaction reinjection. The projection is checked against a sentinel string planted in the precedent bodies, so a leak fails loudly rather than being caught by a length limit.
- **A declared store that is not there behaves exactly as no declaration** — no error, no changed exit code. This repository declares a private store, so that path is what every other clone and every CI run lands in, and it is tested by actually removing the store rather than by reasoning that the code handles it.
- Three documents enumerated what `keel/config.yaml` holds or which surfaces are user-authored. All now include the precedent store; the config header's "two independent declarations" was written one release ago and is now three.
- No behavior change without a declaration, and nothing to do on upgrade. No new dependency.
- Validator at **97 scenarios**, with four added for the declaration, its inertness, the projection pointer, and the three rules.

## 5.5.0 - authorize once, in a file

First layer of **#34**, which asked why execution keeps stopping for confirmations the owner already decided.

- **A repository can now declare standing authorization once**, in `keel/config.yaml`, over a closed vocabulary: `commit`, `push`, `release`, `archive`. Before this there was nowhere to put such a decision — the task capsule had the vocabulary (`Autonomy boundary:` / `Pre-authorized fallback:`) but no repository-level default to inherit, so a permission granted in conversation died at the next `/clear` and was asked for again. (keel-standing-authorization)
- **A task inherits the declaration only where it authored nothing.** A task that declares its own `Autonomy boundary:` keeps it untouched; a repository-wide default that could overwrite a task's stated boundary would make the capsule unreadable on its own. The compiled capsule names `keel/config.yaml` as the source of any entry it supplied, so an inherited authorization is never mistaken for one the task decided. (keel-task-capsule)
- **It authorizes the action and never the proof.** Every gate, evidence requirement, semantic Review, and the write guard run exactly as before: `keel gate task-complete` returns the same status, the same problem set, and the same failure text whether or not anything is declared. This is asserted, not asserted-to — the test compares an authorizing repository against an identical silent one and first proves the two actually differ, because a declaration that failed to reach the capsule would make every comparison trivially equal.
- **It is not a trigger.** `keel context` returns the same selection and next action either way. Nothing schedules itself and no next task is chosen for you; the declaration removes a confirmation, not the step that reaches the action.
- **An unrecognized action name is reported with the accepted set and authorizes nothing** — including the valid entries beside it. Silently dropping a typo would leave the author believing they had granted something they had not.
- **The apply and archive overlays now route confirmations to the declaration** instead of asking again, and say in the same breath that an undeclared action still requires today's confirmation and that authorization never substitutes for a gate. A repository that declares nothing sees no change on any surface.
- Four documents stated the hard-stop default and the unauthorized-action list unconditionally — the compact-task template and the schema, in both their source and installed copies, plus the resident protocol. All now state the condition. `keel/config.yaml`'s own header no longer introduces the file as if `fast_check` were its only key.
- No behavior change without a declaration: an absent, blockless, or empty `authorize:` block leaves every action hard-stop, which is exactly 5.4.0's behavior. Nothing to do on upgrade.
- No new dependency. The reader is line-oriented like `fast_check`'s, in a new `src/core/config.js` shared by the CLI and capsule compilation; the package still carries one runtime dependency and zero devDependencies.
- Validator at **93 scenarios**, with three added for the declaration, its inheritance, and its inertness.

## 5.4.0 - the projection reaches the human

Closes **#32**, whose analysis of the available channels was correct when written and wrong for Claude Code 2.1.220.

- **The SessionStart projection now reaches the person, not only the agent.** It was delivered entirely through `additionalContext`, which the host injects into the model and never renders, so the only path to the user was an instruction asking the agent to restate it — which requires the agent to comply and requires the user to send a first message. Someone who opened a session and waited was told nothing, which is exactly how the issue was reported. (keel-native-runtime-projection)
- **The channel already existed and Keel was not using it.** The host's common hook-output schema declares `systemMessage` beside `continue`, `suppressOutput`, and `decision`, and consumes it in the same handler as `additionalContext` with no gating by event. Issue #32 concluded the only human-visible seam was `exit 2` plus stderr — true of earlier versions, and the reason it proposed a statusline instead. That proposal is **not** built; its author withdrew it in favour of this.
- **Every branch carries it, degraded ones included.** Idle, ambiguous, blocked, missing CLI, malformed output, and timeout each emit their status, their explicit next command, and the authority note. A fallback that stays silent to the human is indistinguishable from a hook that never ran, which is the failure this change exists to close.
- **Both channels ship, and neither is redundant.** The host's line says what the state is; the instruction to restate it is what surfaces the state the agent is actually working from. Only the second can expose the two disagreeing — as one did during development, when the projection selected a task that `tasks.md` already showed complete.
- **An opt-in panel**, off by default: `KEEL_SESSION_PANEL=1` frames the message in a titled box with a Keel mark, sized to its content so a long change name widens the frame instead of being truncated. The default single line is unchanged and carries the same information, which is enforced rather than intended — the tests strip the frame and the mark away and require the status and next command to survive.
- Three documents asserted that the projection reaches only the agent. All three now state both channels and why the agent still restates the projection; the requirement they justified survives for a different reason.
- No behavior change for a host that does not recognise `systemMessage`: the field is optional in the host's own schema, and the `additionalContext` payload is byte-identical to 5.3.9's. Nothing to do on upgrade.
- Validator at **90 scenarios**, with `native-plugin-session-start` grown to exercise all six branches in both panel modes.

## 5.3.8 - the gate reads what it promises

Closes **#29** and **#30**. Both are cases where a structure was read differently from how it is documented, and the gap stayed invisible until it misfired.

- **A task body now ends at the next task or the next `##` heading** (closes #29). `parseTasks` gave a task every line up to the next task or end of file, and a heading did not stop it, so `## Invalidates` and `## Expectation Coverage` were appended to whichever field was open last — the `Evidence`, in every shipped template. A token quoted in either section made that Evidence non-concrete, and the gate then reported a task whose own Evidence was fine. A task group heading leaked into the preceding task's last field the same way. (keel-task-capsule)
- **That also dissolves the contradiction, rather than papering over it.** `invalidation-phrase` requires the searchable wording in double quotes; the concreteness test rejects an angle-bracket slot outside inline code. Once the section is no longer read as Evidence, the same text satisfies both — the two checks were never in conflict, the parser only made them appear so. A control fixture asserts the phrase check was not simply weakened. This mattered most under #16, which requires an invalidation to quote exactly the kind of prose that carries such tokens.
- **Measured, not assumed:** the compiled fingerprints are byte-identical before and after the extent change, so no live change drifts. Both values are now pinned in the suite, so a later extent or capsule-shape change cannot move an anchor silently.
- **`task-complete` refuses a task that recorded no start fingerprint** (closes #30). `anchoredFingerprint` returns null for a non-digest anchor and completion then skipped the comparison entirely, so a task with `Contract: pending` passed with zero problems. It could be implemented against one contract, have its Touch or Verify rewritten mid-flight, and complete clean, purely by never running `task-start --record`. 5.3.7 closed the inferred-selection path; this closes the explicitly named one. (keel-core-gates)
- The missing anchor joins a named task's problem list rather than short-circuiting it, so it cannot hide everything else the task has wrong — the masking shape 5.3.7 removed twice. Selection ambiguity still short-circuits, because there the gate does not know which task the caller meant.
- The change broke 11 existing validator scenarios, every one a fixture that completed a task without ever starting it. That is the behavior being introduced, not collateral damage; each now runs the real loop.

### Upgrade notes

**This is a narrowing.** `keel gate task-complete` now refuses any task whose Evidence `Contract` anchor holds no compiled fingerprint. A repo that never ran `task-start --record` must now run it before completing — the refusal names the command, and `--record` rewrites the anchor in place, so recovery is one command with no manual edit. The step was already the documented loop in `AGENTS.md` and the bootstrap block; it is now enforced rather than assumed.

The `## Invalidates` fix has no upgrade action: it only stops a section from being read as a field it never belonged to, and the compiled fingerprints are unchanged, so no live change drifts.

## 5.3.7 - the diagnostic and the template both name what to do

### Diagnostics name the cause (closes #28 items 4, 5, 6, 9)

All four are gate diagnostics that knew what was wrong and reported something else. Three of the changes **widen** what is accepted; the fourth adds one refusal, described below.

- **Citing a resolved question no longer re-opens it** (closes #28 item 9). The question scan ran over the whole `Covers` field, so a task whose entry read `F13 (Q1 resolved: …)` was told to declare a pre-authorized fallback for a question it does not carry. The only fix available to the reporter was deleting the strings `Q1`/`Q2` from their traceability text — the check punished the authoring it exists to protect. A `Q<n>` is now read only where it opens a `Covers` entry. (keel-task-capsule)
- **A non-concrete `M<n>` check names the slot it matched** (closes #28 item 5). `unfilledToken` already identifies the matched slot and the `Verify` diagnostic already reports it; the per-check message said only that the check "must define a concrete public check", which is the consequence rather than the cause. An author with several slots in one check had to guess which one was read. An empty or `pending` check keeps the unqualified wording, because there is no slot to name. (keel-task-capsule)
- **A missing verification form is one problem, not nine** (closes #28 item 4). Compact detection read only `isConcrete(Verify)`, so a task that simply had no verification field was reported as an expanded v3 task missing nine fields — ten diagnostics in the reproduction, the one actionable line last. Of those fields `Owner`, `Mode`, `Read`, and `Acceptance` resolve to documented defaults or derive from `Covers`, `Report` is consumed nowhere, and `Candidate Boundary` and `Stop Rules` belong to the coupling contract, which requires them when `Coupling: required`. - **`task-complete` refuses to infer a task that never started** (closes #28 item 6; the one narrowing). The reporter asked for the most recently completed task instead, but the documented order is gate-then-checkbox — `assets/bootstrap/AGENTS.md`, `keel-single-task-goal-execution`, and `keel-run-single-task-goal` all put the gate before the box — so first-unchecked is correct there and stays. The narrower hazard is inferring a task that has not started and printing its readiness problems under a heading the author reads as their own task's failure. A started task records a fingerprint in its Evidence `Contract` anchor, and without one there is nothing for completion to compare, so no-arg `task-complete` now returns `ambiguous-completion-selection` naming the inferred task, the most recently checked task, `--task`, and `task-start --record`. An explicit `--task` is never second-guessed. (keel-core-gates)
- **Filed #30 from that task's red.** The unstarted task did not report the wrong problems — it passed clean, zero problems, with `Contract: pending`. `anchoredFingerprint` returns null for a non-digest anchor, so completion compares nothing and says nothing; the fingerprint guarantee reads as unconditional but holds only for tasks that recorded an anchor. (Taken in the next release: it is now refused.)
- **A narrowed refusal is now asserted from both sides** (keel-validation-runner). Each of the three widenings ships a scenario that also asserts the shape which must still be refused, because a scenario checking only the newly-passing shape would be satisfied by deleting the check outright — which is the defect family issue #18 opened.
- **#29 bit three times while authoring this change, and the third time was a hard contradiction.** `invalidation-phrase` requires the searchable wording in double quotes; the concreteness test rejects an angle-bracket slot outside inline code; and `## Invalidates` is absorbed into the last task's `Evidence`. So an entry quoting wording that contains `<n>` cannot satisfy both checks at once, and the resulting failure names a task whose Evidence is fine. Worked around by quoting a slot-free excerpt. (Fixed in the next release, which ends a task body at the next `##` heading; the two checks were never in conflict.)
### Following the template no longer guarantees a refusal (closes #28 items 2, 3, 7)

Both remaining findings are the same shape: an author who copies the shipped template exactly produces something the gate then refuses. Neither gate changes; the templates were disagreeing with rules that were already correct.

- **A requirement written from the spec template validates on first run** (closes #28 item 7). The template's requirement body was the comment `<!-- requirement text -->` with no modal verb, and `openspec validate` requires `SHALL` or `MUST`, so the reporter's 16 requirements produced 16 errors. The body now carries the literal line `The system SHALL` before its behavior slot.
- **The tasks template shows the red-green shape it describes** (closes #28 items 2 and 3). The prose has said since 5.3.4 that `.red`/`.green` come *in addition to* the bare `M<n>` entry, but the only example was the flat form — so the reporter tried annotated labels, was refused, landed on the flat form, and was refused again for the missing bare entry. The untagged check is annotated as load-bearing, since a red-green group whose every check is tagged refuses itself.
- **Both are asserted by running the template, not by reading it** (keel-validation-runner). The scenarios fill each template's author-facing slots and hand the result to the tool that consumes it — the real `openspec validate`, and `task-start` over all three template groups. A prose assertion would be satisfied by a template that mentions the rule only in a comment, which is exactly the state that produced the reported failures; and a structural assertion alone would still pass for an example the gate refuses. The templates can no longer drift from the gates without the suite noticing, which is the durable property — the two findings are only today's instances.
- The mechanical slot filler needed three rules the templates taught it: a task title is itself a comment, so own-line comments are stripped while inline ones are filled; a slot may quote an identifier shape like `Q<n>`, whose inner brackets block the outer match unless substitution runs innermost-first to a fixed point; and `Strategy:` is a fixed-vocabulary slot, so it is named explicitly.

- The one behavior to know about: `keel gate task-complete` **without** `--task` now refuses when the first unchecked task has recorded no fingerprint in its Evidence `Contract` anchor. A repo that checks the box before gating, or that never passes `task-start --record`, needs `--task` — which the refusal names. `task-start` is unchanged.

## 5.3.4 - refusals that name what they accept, and checks that actually run

Closes issues #15, #18, #20, #21, #22, and #23. Both gate changes **widen** what is accepted, so every currently passing tasks.md keeps passing; two narrowings are called out below.

### Statements that stopped being true (closes #15, #22, #23)

- **The consumer bootstrap now names the record-write exemption** (closes #15). It said Touch is the write boundary "for product files" and left the reader to infer what the qualifier excluded; the inference actually made is that `tasks.md` belongs in Touch, the trap #8 reported. It now says "Touch bounds product writes; the change's own dir is exempt." Room was made by listing one guard opt-out instead of two — `keel guard clear` is unchanged as a command, it just no longer costs resident bytes — so the block **shrank** to 1012 against an unchanged 1024-byte budget. (keel-openspec-surface-overlay)
- **Live specs stopped requiring versions that already shipped** (closes #22). A sweep found **seven** version-pinned statements across two capabilities — `3.0.0`, `4.0.0`, a forbidden `2.7.0` — all false at 5.3.4, one of them asking for version markers on the retired `dist/` tree. The requirement naming a version is replaced by the invariant it was reaching for: every shipped marker agrees with the package version. Zero version literals remain in live specs.
- **That invariant is now enforced rather than asserted** (closes #23). Baseline validation walks every shipped `.md`/`.json`, extracts each `keel:… version=` marker, and fails naming the file when one disagrees. The marker list is discovered, not declared, so it cannot become the next thing to fall behind, and `bump_version.js` sweeps the same set — all twelve markers move in one step instead of `.codex/` waiting for someone to remember.
- **Correction to the 5.3.3-era account of that drift.** It was recorded as "the release bump carries `.claude/` along and leaves `.codex/` behind". That was wrong: `bump_version.js` never touched either. The validator scenario `source-repo-bootstrap-skip` runs a real `keel --install --target claude` against the repository root, and that install silently refreshed the Claude overlays. So it was "a test installs one target and nothing installs the other" — and a test mutating the working tree is its own defect, filed as **#26**.
- **The contract-anchor guarantee states its bound** (closes #24 as documented). An anchor is reverifiable while its change is live; once archived it is a historical record. The boundary turned out to be **enforced** rather than merely undocumented — the gates reject a change name under `archive/`, so no CLI path recompiles an archived task. **Second narrowing:** `bump_version.js` compared an LF changelog header against a CRLF working copy and aborted after every marker had been written, leaving the repository half-bumped; fixed.

### A regression check can stand on its own (closes #21)

- **A red-green strategy no longer demands a red that cannot exist.** It required `.red` and `.green` for every `M<n>`, but a regression check asserts that something already green is still green and has no honest red. The author's only options were to fabricate one or to fold the guard into the behavior check — this repository took the fold twice while shipping 5.3.2 and 5.3.3, and recorded both times that it cost expressiveness. The gate's shape was deciding the task's decomposition. (keel-task-capsule)
- An `M<n>` may now carry a comma-separated tag set after its label: `fast`, `full`, and the new `regression`. The set form exists because a regression check is exactly the kind you want in the fast pre-push loop, so `M3 (fast, regression): …` had to be sayable.
- Two properties keep the tag from becoming an escape hatch. A red-green strategy must retain **at least one untagged check**, refused at task-start as `regression-only-strategy`. And the tag lands in the compiled capsule, so the exemption is a visible term of the contract rather than a silent skip. A tagged check is exempt from red-green, **not** from evidence: its bare `M<n>` entry is still required.
- Untagged checks emit no tag key at all, following the 5.2.2 layer-tag precedent, so **no recorded contract fingerprint moves**. Proven on real tasks rather than fixtures: this change's own 1.1 and 3.1 recompile to the values captured before any of the code existed, and emitting the key unconditionally moves both.

### A durable owner can be a file the repository keeps (closes #20)

- **`Durable owner:` accepted three prefixes and the refusal said only "lacks a durable owner".** An author pointing at their own ledger — `openspec/FOLLOWUP.md` in the report — was told the entry had no owner while it plainly named one, and could only find the boundary by trial. (keel-expectation-slice-evidence-gates)
- The whitelist verified nothing: a gate runs without network, so it cannot resolve a URL, and it never confirmed a `keel/archive/…` path either. A repo-relative path is the one form it *can* check, which made it the least defensible thing to refuse. Now a URL is accepted on shape and **any repo-relative path is accepted on existence**, across all three places the form is shared — Review `Findings`, `## Expectation Coverage`, and `## Invalidates`.
- **Narrowing, deliberate:** a path with no file behind it is now refused by name (`invalidation-owner-missing` / `expectation-owner-missing`). Previously a `keel/archive/…` path passed without existing. A note nobody wrote owns nothing.
- `keel/HANDOFF.md` is still refused although it exists — existence is necessary, not sufficient, for something the protocol defines as a pointer. In `Findings`, which is free prose, a path counts only when it follows `Durable owner:`, because mentioning the file a finding concerns does not give that finding an owner. That rule bit its own author within the hour: the first draft of task 2.1's Findings named an archive note in passing and `task-complete` refused it.

The new scenario reads the instruction the way an author receives it — install into a temp repo, scaffold a change, ask the CLI — rather than from the schema file it is composed from, so a change that never reaches the author fails. Also fixed there, #21's second report: the template read as though `.red`/`.green` **replace** the bare `M<n>` entry, when the gate has always wanted all three.

- Filed #24 from task 1.1: recompiling an archived task no longer reproduces its recorded fingerprint, all 47 of them. It blocks nothing — archived tasks are never resumed — but it is why the fingerprint evidence above uses before-and-after values rather than the archive as a corpus.

## 5.3.3 - a change declares what it makes stale

Closes issue #16. **Migration: every change in flight gains a required `## Invalidates` section in tasks.md**, and `keel gate task-start` refuses without it. The migration is one line — `- None.` — and the template supplies it for new changes.

- **The Task Authoring Gate now asks what a change invalidates** (closes #16). Follow-up Ownership governs work a change left undone; nothing governed the opposite shape — statements left standing by work the change *completed*. A fix is correct and still makes every sentence describing the old behavior wrong, and no gate, spec, or checklist asked. On the day that produced this issue, ten changes shipped and the closing audit found stale statements created by that same day's fixes. `task-start` now requires a `## Invalidates` section: one `- I<n>: "the wording that is now wrong" — where it lives.` entry per stale statement, closed by `Updated by:` naming tasks of this change, a `Durable owner:`, or a `Discard reason:`, or `- None.` when nothing is invalidated. (keel-expectation-slice-evidence-gates)
- **An entry must quote a searchable phrase, not merely list paths.** This is the load-bearing constraint rather than a formatting preference. The text that goes stale is the text the author was not already holding in mind — every miss in the recorded case was a file that merely mentioned the behavior, while every catch was a file already open — so a list of remembered locations reproduces the failure it is meant to prevent. A location-only entry is refused as `invalidation-phrase`.

Closure is checked for form, not completion — at authoring time the named updater has not run, so completion is structural: that task carries the paths in its Touch and passes its own gate. Nothing re-verifies at the close, which is the accepted cost of a single checkpoint.
- The section is a sibling heading, so it stays outside every task body and **moves no capsule fingerprint**. The compact parser slices a task body to the next task or EOF, so a trailing block that is not a `##` heading would be absorbed into the last task's final field.
- Authoring surface: the shipped tasks template carries the section with a `- None.` default and its example inside the guidance comment, the `tasks` artifact instruction describes the entry and closure forms, and the resident protocol names it under Completion gates. Two resident sentences were **corrected** rather than supplemented — `task-start` was described as returning the capsule and fingerprint, and Follow-up Ownership read as the complete account of what a change owes at its close.

That is the argument for searching by symptom rather than recalling by filename, demonstrated by the change that introduced it.

## 5.3.2 - the session projection stops talking only to the agent

- **SessionStart projection now instructs the agent to disclose what it found.** The projection is emitted as `additionalContext`, which the host injects into the agent and never renders for the human, so a session would open, the hook would fire, and the user would still have to ask where the work stood. ## 5.3.1 - the full gate runs in CI; a finished task no longer fails the next one

Closes issues #10 and #13. With #8 and #15 item 1, every issue opened against 5.2.x is now resolved except the resident-block byte budget.

- **A finished task's uncommitted work is no longer the next task's scope failure** (closes issue #13, its last item): `task-complete --base HEAD` diffed the worktree and attributed every changed path outside the selected task's Touch, so when the previous task of the same change had finished but was not yet committed, its files landed on whoever ran next. A path is now withheld from the selected task when a **checked** task of the same change declares it in Touch — derived from `tasks.md`, which the gate had already parsed, so no new state and no fingerprint change. Only a checked sibling counts: an unchecked task's Touch is a plan, not a record. The exclusion is **reported, not silent** — a base comparison cannot establish which task wrote a path, so a warning names the path and the owning task. The per-task commit habit stays the better practice; forgetting it no longer produces a diagnostic naming a file the author never touched. (keel-core-gates)
- **Keel runs its own full gate in CI** (closes issue #10): the 70-odd validator scenarios' only regression net was a pre-push hook on one Windows machine, which is also what `keel-verification-layering` already said should not be the case — it places the full gate "at CI or `keel gate change-close`". Two things blocked it, both smaller than the comment in `publish.yml` implied: **two** scenarios hard-required local `codex`/`claude` CLIs, and **six** assertions hardcoded Windows path separators. `.github/workflows/test.yml` now runs `npm test` on `ubuntu-latest` for every push and pull request; `publish.yml` is untouched and keeps only its tag/version guard. (keel-validation-runner)
- **An absent external runtime skips instead of failing.** A scenario exits `3` when a runtime it probes is not installed — `0` pass, `1` fail, `2` unknown scenario, so conflating an unavailable runtime with either would hide both. `--all` counts skips separately, names each with its reason, and **excludes them from the verified count**, so the number in evidence is the number actually run. The reason is narrow by design: an inconvenient assertion, a hard fixture, or a platform difference is a failure, never a skip. (keel-validation-runner)
- **Assertions no longer encode the host path separator**: a `posix_paths` helper folds captured output and assertions state the forward-slash form — not branching on the platform, and not accepting both spellings, which would pass on a platform printing neither correctly. (keel-validation-runner)
- **Resident-block topics are matched as topics, not as prose** (closes issue #15 item 1): the ten required entries were a flat substring list, so the consumer bootstrap's wording was pinned character-for-character by a check whose purpose is only that the block still covers its topics. An entry may now be a **literal** — for a command, marker, or identifier, where a rename must fail — or a **pattern**, for prose whose wording may move; the diagnostic says which kind was missing. Only the entry that had demonstrably blocked work is converted. (keel-validation-runner)
- The consumer bootstrap now says Touch is the write boundary **for product files**, so a consumer no longer infers that Touch bounds every write. Naming the record-layer exemption outright still does not fit the block's 1024-byte budget — measured at 3 bytes over — which is what remains of issue #15.

## 5.3.0 - Touch layering: records are not product, and a repository action is a legal task

Closes issue #8. Minor rather than patch: the write guard's decision changes, and there is a new task mode.

- **A task's own change directory is a record-write layer** (issue #8 example 1, and the five reauthorization cycles in its comment): `keel-core-gates` already required that `keel/guard.json` and paths under the selected change's own `openspec/changes/<change>/` directory not be attributed as outside-Touch failures — they are the authoring artifacts the completion gate is completing against — and `task-complete` implemented exactly that. The write guard did not: it denied writes there, and it hashed that directory's `tasks.md` as authority, so **ticking a checkbox or appending Evidence locked the task out of its own bookkeeping**. Declaring `tasks.md` in Touch, the more careful act, produced the worse experience. The guard now derives the same record prefix from the manifest field it already carries — writes under it are allowed undeclared, and recorded authority entries under it are skipped for drift. **No manifest schema change**, so an older plugin hook against a newer CLI keeps its previous behavior instead of failing closed. (keel-touch-write-guard)
- **Post-completion denial is now stated, not inferred**: byte hashing was also what incidentally stopped a checked task from writing. A checked task now gets no further product writes by an explicit checkbox check, while its own records stay writable so it can finish the Evidence its completion gate requires. (keel-touch-write-guard)
- **Write-time drift detection is narrowed, deliberately.** A hook that cannot compile a capsule cannot tell a contract edit from a record write in the same file. Contract drift inside the change directory — a moved Touch, Verify, Covers, title, or boundary — is now caught by `keel guard status` and `keel gate task-complete`, which compile and compare the fingerprint, rather than at the next write. Authority *outside* the change directory still denies at write time. A new spec scenario states where each is caught. (keel-touch-write-guard)
- **`Mode: repo-action`** (issue #8 example 2): a task whose whole effect is an authorized repository-level action — a commit, a tag — writes no worktree file, so it had no concrete Touch; it is not `diagnose-only`, because it has real side effects needing evidence; and `Touch: none` was accepted for no other mode. The reporter was forced to name a path the task did not write, which then tripped the drift defect above. `repo-action` requires `Touch: none`, carries `must not write product files`, and is the one mode whose prohibitions omit `must not commit`. Push, sync, archive, and marking tasks complete stay prohibited. Whether the action performed was the authorized one remains a Review judgment; the capsule fixes the write posture, and the mode is recorded in the fingerprint. Rejected: `Mode: implementation` with `Touch: none`, since `implementation` means "modify only Touch files" and a mode meaning the opposite should not share its name. (keel-task-capsule)
- Authoring surface: the shipped `keel-spec-driven` tasks template and the resident protocol name the new mode and the record layer. The consumer bootstrap could not carry the record-layer qualifier — it is 1013 bytes against a 1024-byte budget and its wording is a literal required topic — so that gap is tracked as issue #15.
- Version alignment: the npm package, both native plugin manifests, protocol docs, and this changelog share Keel 5.3.0; the OpenSpec dependency pin stays `^1.4.1`.

## 5.2.2 - verification layering: fast inner-loop pre-push vs full gate

- Verification layering (closes issue #5): a new `keel-verification-layering` capability and a "Verification layering" section in both READMEs document splitting verification into a **fast inner-loop check** (seconds, run at a local pre-push and during iteration) and the **full gate** (the complete or slow suite — golden byte-determinism tests, cross-platform runs — run at CI or `keel gate change-close`), so a slow suite never blocks `git push`. Generic pre-push hooks that run the full suite are the trap this convention avoids. (keel-verification-layering)
- Fast-check declaration and opt-in pre-push: projects declare their fast inner-loop command as `fast_check:` in a new `keel/config.yaml` that `keel --install` scaffolds once (a commented template it never overwrites). `keel --install --with-git-hooks` — an explicit, opt-in flag — reads `fast_check`, writes a `#!/bin/sh` `.githooks/pre-push` that runs it, and sets `core.hooksPath` to `.githooks` (per-clone, repo-local, reversible); it refuses when no `fast_check` is declared, a plain `keel --install` never touches git config, and `keel --uninstall`/`--clear` unset `core.hooksPath` only when Keel set it to `.githooks`. `keel --doctor` gains a read-only "Fast pre-push surface" section reporting the `fast_check`, the pre-push hook, and `core.hooksPath`.
